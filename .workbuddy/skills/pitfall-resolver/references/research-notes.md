# 研究资料落盘与检索输出恢复

> 主题：长周期研究/写作任务中，如何把网络检索结果可靠落盘，避免上下文压缩后丢失数字与链接。
> 实测日期：2026-11-15（00091 Agent Harness 深度比较课程资料暂存）。

## 1. 检索结果合并成单个大文件，用户纠正「单文件体量过大也不好」

- **触发症状**：为满足「查询到的资料必须先落盘暂存」要求，把一批 12 条 `WebSearch` / `WebFetch` 的原始返回机械导出成单个 `raw-01.md`，文件 **238,707 字节**；用户随即纠正「可以多文件暂存，单文件体量过大也不好」。同时证据台账单文件 30,350 字节，也不便于按主题取用。
- **根因**：按「批次」聚合而非按「单次检索」聚合；一次批次里既有 7 KB 的短文，也有 32 KB 的搜索结果，合并后任何一次查阅都要载入整批，且上下文压缩后无法按条恢复。
- **已实测处理**：
  1. 目录改为 `research/raw/<批次>-<序号>-<来源短名>.md`，**一条检索一个文件**，头部写核实日期、调用参数、callId、可信级别提示；证据台账按主题拆 `research/evidence/<批次>-<主题>.md`（可信级别 / 来源清单 / 基准事实 / 架构事实 / 待补清单）。
  2. 单文件上限约 **32 KB**；超限时按 `^## ` 二级标题切分（本次 53.8 KB 官方文档切成 3 片：15.7 / 26.9 / 14.9 KB）。
  3. 拆分后做**零丢失校验**：脚本逐条断言「原合并档中每条返回原文正文」与「每个台账章节正文」完整出现在对应分片里，全部通过才删除合并档。
  4. 建立 `research/README.md` 活索引，记录现行口径与批次登记；索引允许追加批次行，其余分片**只新建、不改写、不追加**（遵守「历史记录不可矫正」）。
  5. 查询节奏固定为：检索 → 立即机械导出分片 → 读分片提炼带来源 ID 的台账 → 再发起下一批查询。
- **实测结果**：12 个原文分片（最大 31,924 B）+ 5 个台账分片（最大 11,415 B）+ 索引 1 个；238 KB 合并档移除后内容零丢失。后续批次 02/03 沿用同一结构，最大分片 26,889 B。
- **关键词**：资料暂存、上下文压缩、单文件过大、多文件分片、逐条落盘、零丢失校验、证据台账。

## 2. `WebFetch` 大输出被折叠成 `<persisted-output>`，机械导出 transcript 只拿到占位

- **触发症状**：抓取 `https://code.claude.com/docs/en/permissions` 时，工具结果返回约 53.8 KB；从会话记录 `*.jsonl` 增量导出的分片只有 **2,064 字节**，内容形如 `<persisted-output> Output too large (53.8KB). Full output saved to: C:\...\tool-results\chatcmpl-tool-8b31fc00a8a649e1.txt`，只带首 2048 字节预览与末尾片段。若直接拿这个分片当资料，正文会缺失大半。
- **根因**：工具输出超过阈值时，系统把全文写到会话目录下的 `tool-results/<callId>.txt`，只在消息流里保留占位与预览；会话记录 `function_call_result.output.text` 存的是占位文本，不是全文。
- **已实测处理**：
  1. 导出脚本检查文本是否含 `Full output saved to:\s*(\S+\.txt)`，把 Windows 反斜杠路径转成 `/` 后读取全文（本次 **55,105 字节**）。
  2. 全文按 `^## ` 切分成 <20 KB 的多个分片，头部分明「来源为持久化文件、内容未改写」。
  3. **外层代码围栏用 5 个反引号**：部分官方原文自身以 4 个反引号开头（本次 `openai/codex` README 首行即 ````），用 4 反引号包裹会破坏 markdown 结构；课程数据层也有同类校验（围栏 info-string 不得含反引号）。
  4. 落盘后抽查分片首尾，确认不是预览片段。
- **实测结果**：恢复 55,105 字节全文，切成 3 片（15,735 / 26,889 / 14,919 B），并把本条坑记入 `docs/00091-.../research/evidence/02-corrections.md` 第 4 节。
- **关键词**：`<persisted-output>`、`Output too large`、`Full output saved to`、`tool-results`、大输出折叠、预览 2048 字节、五反引号围栏。

## 3. 相关但不同的边界

- 官方文档站是动态 SPA 时（本次 `huggingface.co/spaces/harness-hub/harness-lens`），`WebFetch` 只拿到 632 字符外壳（标题 / Like / Running / Fetching metadata…），**不是**折叠输出，读 `tool-results` 也没用；应改抓 Space 的 `/raw/main/README.md` 或 `/tree/main` 文件列表，或从转述该 Space 的一手公告取证。已列入待补清单。
- 搜索结果摘要（二手）与页面抽取（模型对原文的提取）都可能失真，落盘后仍须按 A/B/C 分级，关键结论要升级到官方仓库/文档再写入正文。

## 4. 按来源 slug 子串批量导出 transcript 分片，前缀误配导致文件互相覆盖

- **触发症状**：批次 05/06 的机械导出按「URL 含某 slug 子串」给检索结果分配文件名，出现两类覆盖：① `06-04-hermes-docs-root.md` 被三条 Hermes 结果轮流覆盖（`'nousresearch.com/docs/'` 子串把 architecture 页也匹配进去），`learn.chatgpt.com/docs/sandboxing.md` 因「无 slug」被整体跳过；② `06-04-codex-config-md-404.md` 被 config-reference 结果覆盖（`codex-config` 前缀误配）。恢复时只有最后一条写入的内容幸存，前几条静默丢失。
- **根因**：导出映射用「包含关系」而非「精确对应」；一条检索一个文件的前提是 callId/URL 与文件名一一对应，子串匹配破坏了这个不变量，且覆盖是静默的（无报错、文件数不减）。
- **已实测处理**：
  1. 按 **callId 精确重写**受影响分片（每条检索的 callId 唯一），按 URL 精确映射重建文件名；清理由误配产生的 stale 文件后再登记批次。
  2. 导出脚本加自检：**文件数 = 检索条数**，任何一条结果找不到唯一目标文件即报错停止，而不是跳过或就近写入。
  3. 配套的文档站陷阱同批实测：`developers.openai.com/codex/*` 301 重定向到 `learn.chatgpt.com/docs/*`，无 `.md` 后缀路径返回 404 导航壳（抓 `*.md` 版本解决）；SPA 路径（如 `/docs/architecture`）要从 `/docs/` 根页拿真实入口；中文关键词检索返回 `[SENSITIVE_CONTENT_UNAVAILABLE]`（589 B）时换英文关键词重查即可恢复。
- **实测结果**：批次 05/06/07 全部 44 条检索零丢失落盘；`raw/` 分片数与登记表条数一致。
- **关键词**：slug 误配、前缀匹配、分片覆盖、callId 精确映射、文档站迁移 301、SPA 404 导航壳、SENSITIVE_CONTENT_UNAVAILABLE、检索导出自检。
