Letta Code: The Memory-First Coding Agent That Topped Terminal-Bench for Open Source AgentMarketCap。Every time you start a new session with Claude Code, Cursor, or GitHub Copilot, you're handing amnesia to a highly capable engineer and asking them to figure out the codebase all over again. For most coding agents today, each session is a blank slate. Letta Code is built around the premise that this is the wrong design. In March 2026, the memory-first open-source coding agent reached #1 on Terminal-Bench among open-source agents and 4th overall — outscoring proprietary systems including Claude Code's standalone scaffold — with a 42.5% success rate on the benchmark's most challenging CLI tasks. The score was achieved using fewer than 200 lines of agent code. What makes the result interesting isn't the number itself. It's the architectural bet behind it. The Stateless Agent Problem Most AI coding tools share a fundamental constraint: they operate within a fixed context window that resets at the end of each session. When that window fills up, earlier conversation history gets compressed or dropped. When the session ends, everything goes with it. Engineers work around this with workarounds that shouldn't need to exist: CLAUDE.md files that restate project conventions every session, repeated onboarding prompts, manual copy-pasting of architecture decisions into system prompts. GitHub Copilot remembers preferences across sessions through shallow summarization. Claude Code offers server-side context compression that enables "effectively infinite conversations" within a session. But neither builds up a persistent, queryable memory of the codebase and working patterns that improves over time. The problem compounds at scale. A team running ten concurrent agent sessions across a monorepo generates zero shared institutional memory. Every agent starts from scratch. Every convention has to be re-explained. Every bug pattern has to be rediscovered. Letta's team, which grew out of the MemGPT research project at UC Berkeley, calls this the "stateless agent" problem. Their solution is an architectural model borrowed from operating systems — and it's what distinguishes Letta Code from every other coding agent on the market. The OS-Inspired Memory Model Letta's memory architecture draws directly from how an operating system manages RAM and disk. The agent doesn't just have a context window — it has a tiered memory system that actively moves information between layers depending on relevance and recency. Core Memory is the in-context layer, analogous to RAM. It holds memory blocks pinned directly into the model's active context window: the current task, user preferences, project conventions, and the agent's own working notes. These blocks are capped in size (typically by character limit) to prevent context bloat, and they're editable — the agent can rewrite them as it learns. A block for "repository architecture" updates as the agent discovers new patterns. A block for "team preferences" accumulates stylistic conventions across sessions. Recall Memory is the conversation archive. Every interaction is persisted to disk automatically and made searchable. When the agent needs to reference something from a session three weeks ago — "what was the pattern we used for the payment service retry logic?" — it queries recall memory and surfaces the relevant turns without having to load the entire history into context. Unlike most frameworks that leave session persistence to the developer, Letta handles this automatically. Archival Memory is the long-term knowledge store. Processed, indexed information lives here — in vector databases or graph databases — and gets retrieved into context on demand via specialized query tools. This is where architectural decisions, debugging solutions, and cross-repository patterns accumulate into something resembling genuine organizational knowledge. The key insight is that the agent manages these layers actively. Rather than passively filling a context window until it overflows, the Letta agent reasons about what to keep in core memory, what to archive, and what to retrieve — the same way an experienced engineer manages their working memory during a complex task. Terminal-Bench: Why CLI Autonomy Is the Right Test Terminal-Bench is not a bug-fix benchmark. SWE-bench, the most-cited coding agent leaderboard, evaluates models on isolated GitHub issue resolution — find the change, make it, submit the patch. It's a useful test of code generation accuracy. It's not a test of whether an agent can actually operate autonomously in a terminal environment over extended tasks. Terminal-Bench 2.0 tests something harder: 89 containerized CLI tasks drawn from real engineering workflows. Compiling code repositories from source. Building and configuring Linux kernels. Training models. Debugging systems across multiple tool invocations. Each task runs in a sandboxed Docker environment, and the agent must navigate it without human intervention. These are multi-step, multi-tool tasks where session context matters. An agent that forgets what it compiled in step three by the time it reaches step seven will fail.
