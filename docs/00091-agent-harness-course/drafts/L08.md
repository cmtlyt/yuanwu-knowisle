### 榜单首秀：五个评估全部并列第一，然后被一个细节拖住

Harness Leaderboard 在 **2026-11-09** 加入 DSH，11-11 排进所有视图。首秀成绩（官方公告口径，快照 2026-11-15）：**5 个评估全部与第一名统计并列**；三模型均分下 DeepSWE v1.1 拿第 **2**（落后 Hermes 仅 **0.5** 分）；Terminal-Bench 2.1 第 **6/10**；成本口径 **$0.53 / solved trial**。

TB 2.1 的第 6 名不是能力问题，而是**终止面与验收时序的假设差异**：DSH 在任务结束时会关闭自己启动的**所有后台程序**，而这批 TB 任务里有 3 个是在 agent 退出**之后**才去验收 server 的——DSH 把自己起的 server 清干净了，验收自然失败。榜单没有掩饰这一点，反而把它变成了选型建议：**仓库代码改动选 DSH；需要后台服务在 agent 退出后继续存活的场景选 Hermes / Pi / OpenCode**。这是本课程第一次完整看到「终止面设计写出分数」的案例——L02 四问的配置伪影检查，在这里有了具象。

### 独立复测：3.6 分的「一致倾向」

Bug Hunt 系列独立复测（[Product Compass](https://www.productcompass.pm/p/deepseek-harness-vs-claude-code)，89 次干净运行）给了 DSH 与 Claude Code 正面较量的数据。max effort 档 DSH 比 Claude Code 差距 **3.6 分**（原始 7 次：DSH 42/41/47/47/40/43/39，Claude 34/37/45/46/35/39/38），exact permutation test **p = 0.14**，bootstrap 95% 区间 −0.4 ~ +7.3。原文的定性值得原样记住：***a consistent lean, not a proven gap*** / *Seven runs a side cannot separate them*。两个更有意思的次级指标：DSH 标准差 **3.2** vs Claude **4.7**（更稳）；DSH 最差一次 **39 ≈ Claude 的平均 39.1**（下限更高）。真正越过噪声的对照是 DSH 与 Pi 对 OpenCode 的优势（p = 0.02 / 0.01）。

### 设置不等价与 token 账本

这次复测还留下两条方法论级别的观察。其一，**设置不等价**：bench 对所有 Claude Code 行统一关闭 subagent tool，而 DSH 按出厂默认开启（7 次 max 共启动 **35 个** subagent）；控制变量是 Pi——完全没有 subagent 却拿到 42.2 分，说明「子代理数量 → 分数」的简单因果不成立，但对比表的读者必须知道设置没对齐。其二，**token 账本**：max 档 DSH 每 run 发送 2.55M 未缓存输入 / 316.5M 缓存输入 / 0.85M 输出，Claude Code 分别为 1.04M / 207.5M / 0.41M（两者输入 >99% 命中缓存）；DSH 还顺带修了约 **44 个**非预置真实 bug / run（Claude Code 23 个），记为 extras 不计入分数——「分数之外的产出」也是选型信息。

### 优缺点裁决与适用边界

**优点**：① MIT + 官方出品，插件树架构的扩展性天花板高（L07）；② append-only 事件流让 resume/fork/replay 是同一份数据（可审计性强）；③ 起步即与榜首统计并列的基准表现；④ Creator Mode（2026-11-02 官宣）用自然语言生成可安装插件，官方 7 组演示里番茄钟插件从开发到安装验证约 5 分 24 秒（官方同时声明部分演示经多轮调整、一条提示词不保证复现）。

**缺点**：① **developer preview**——README 大写警告破坏性变更，37 个 release 全是 prerelease，生产采用必须 pin 版本并预留迁移成本；② 后台进程清理的终止面假设对长驻服务场景不友好；③ 中文社区二手资料失真率高（「五种 profile」「三段管线」等未经官方证实的展开），排查问题时要以 [官方文档站](https://deepseekharness.github.io/deepseek-harness/) 与 [仓库](https://github.com/deepseek-ai/deepseek-harness) 为准；④ star 数在 15 万 → 25 万 → 27.8 万之间随日期漂移（台账 F-A9），**不作为能力论据**。

**适合**：开源自托管 + 插件化扩展需求；以仓库代码改动为主的任务域；想要「配置可自省、行为可重放」的工程团队。**排除**：需要后台服务跨任务存活的编排（选 Hermes/Pi/OpenCode）；无法接受 RC 级 API 变动的生产环境；把 star 数或单场榜单排名当唯一依据的决策。

下一个系统的关键词是「记忆」：Hermes 把 harness 做成了**会成长的 agent**——而且它恰好是 DSH 在 DeepSWE 上以 0.5 分之差屈居第二的那位第一名。

### 追问与辨析：preview 期的采用策略与版本钉

developer preview 的正确姿势不是「等稳定」，而是「带约束地采用」。三条可落盘的约束，直接对应 DSH 的现状（37 个 release 全是 prerelease、README 大写警告破坏性变更、快照时版本线 0.2.2-rc）：

```bash
# DSH preview 期采用清单（每条都有本课证据支撑）

# 1. 版本钉死：npx 会拉最新，preview 期必须显式 pin
npm install -g @deepseek-ai/dsh@0.2.2-rc.3
dsh web                      # 本地验证后再进 CI

# 2. 配置快照进 CI：插件树漂移在合并前暴露
dsh --profile web --dump-config > .ci/dsh-config.snapshot
#    diff 超出预期 → 升级评审，而不是静默升级

# 3. 升级走双轨：preview 环境先跑一遍基准用例
#    （README 警告 THERE WILL BE COMPATIBILITY-BREAKING CHANGES）
pnpm run build && pnpm dsh web   # 源码轨：对应仓库构建流程
```

三条约束分别对准 preview 期的三种风险：**API 漂移**（pin 版本）、**配置漂移**（快照 diff）、**静默破坏**（双轨验证）。对照 L05 的 Codex preset（参数级 pin）与 L20 的 Grok Build pin（周更节奏），「preview/RC 期 harness 的版本纪律」可以总结成一条通用规则：**凡是 release 历史里带 rc/beta/preview 字样的 harness，一切自动化都必须显式钉版本 + 快照配置**。

另一个值得记录的采用信号：DSH 的 Creator Mode 演示（番茄钟插件 5 分 24 秒从开发到安装验证）展示的是插件树的**开发体验上限**，而官方自己注明「部分演示经多轮对话调整、一条提示词不保证复现」。这种「官方先给上限再自降预期」的诚实披露，在评估 vendor 声明时应当作为加分项——对照 L02 评分卡，它至少在「口径诚实」这一项拿了分。把它和「37 个 prerelease」放在一起看，才是 DSH 的完整画像：上限很高、地基未稳、态度诚实。

```bash
# DSH 的两种启动路径与运行前置（DS-2/DS-3，官方 README）
npx @deepseek-ai/dsh web            # 包路径启动，默认 http://127.0.0.1:3080（--no-open 不开浏览器）
pnpm install && pnpm run build && pnpm dsh web   # 源码构建路径（pnpm workspace monorepo）
# 运行前必读 SAFETY.md —— 仓库同发 SAFETY.zh.md / SAFETY.i18n.yaml（2026-08-23 加入）
# 版本纪律：developer preview，37 个 release 全是 prerelease，README 自述必有破坏性变更
```
