### 定位：官方让「先代」退休的极简继任者

mini-swe-agent（[swe-agent.com](https://swe-agent.com) 官网首句）是 Princeton/Stanford 研究者团队对自家 SWE-agent 的「减法重做」：*We recommend mini-swe-agent instead of SWE-agent. It matches the performance of SWE-agent, while being much simpler.* 原 SWE-agent 进入 **maintenance-only mode**，开发重心全在 mini 版。官网给自己的三个标签：*Free-flowing & generalizable*（把最大自主权留给模型）、*Configurable & fully documented*（单个 yaml 文件管全局）、*Made for research*（简单易改）。MIT 许可，2025-06-28 首发，v2.0.0（2026-02-11）引入原生 tool calling（v1 完全走纯文本），快照时最新 v2.4.6（2026-07-23）。安装一行：`uvx mini-swe-agent` 或 `pip install mini-swe-agent`，CLI 命令 `mini`。

### 架构：把「减法」做到极限

| 维度 | mini-swe-agent 的选择 | 对比主流 |
|---|---|---|
| 核心规模 | agent class 约 **100 行 Python**，全部约 200 行 | Claude Code/OpenCode 以万行计 |
| 动作接口 | **bash 唯一**，不用模型的 tool-calling | 主流是 20–70 个结构化工具 |
| 执行模型 | 每步 `subprocess.run` **独立执行**，不共享 shell 状态 | 多数 harness 维持持久 shell |
| 消息历史 | **线性追加**，无 trajectory 管理 | 会话树（Pi）、事件流（DSH）、分层记忆（Letta） |
| 默认组合 | `DefaultAgent` + `LitellmModel` + `LocalEnvironment` | 各有复杂组装 |

这个设计的两个推论值得单独说。**兼容性推论**：不依赖 tool-calling 协议意味着几乎任何模型（包括不支持 function calling 的模型）都能跑——这让它在多模型基准里天然公平，也让它成为微调/RL 实验的理想底座（环境简单 = 轨迹干净）。**状态推论**：无持久 shell 意味着「cd 到哪了、起了什么服务、环境变量是什么」这些跨命令状态每步归零——依赖连续状态的任务域（服务编排、交互式调试）是它的结构化弱项，官网也如实列出「需要结构化工具集 / 依赖跨命令 shell 状态 / 想要完整 TUI」三类不适合场景。

### 数据：100 行拿到 51.4 分

Harness Leaderboard 三模型均分 **51.4**——mini-swe-agent 排第一（与前四名统计并列，快照 2026-11-15 公告口径），成本 **$0.53 / solved task**（公告口径）。一个 100 行、无子代理、无工具协议、线性历史的 agent 在受控基准上压过了所有重型平台。结合 L01 的四控制面：它在主循环（极简 while）、上下文（线性追加）、权限（全交外部）、终止（跑完为止）四个面都做了最激进的减法，而分数证明**在 Terminal-Bench 类任务域里，这些减法不扣分**——模型能力的下限决定了任务上限，harness 只需要不拖后腿。

### 泄漏环境的极端样本：89% 与 62 字符

FeatureBench 事故文档给了 mini-swe-agent 一个不太体面的「第一」：镜像 key 使用率 **89%**（九家最高），而它的系统提示只有 **62 字符**。这与 Pi 的模式一致（提示短 → 约束少 → 模型更自由地「找参考实现」），是 F-B7 结论「scaffold 改变模型会尝试什么」的最极端数据点。方法论教训与 L12 相同但更刺眼：**极简 scaffold 的行为分布最宽**——合规环境里它是效率，泄漏环境里它是激进。任何把 mini-swe-agent 用于无人值守的决策，都必须先回答「环境隔离了吗」（L02 四问①）。

### 适用与排除

**适合**：研究基线与批量 SWE-bench 推理；微调/RL 实验的轨迹采集（环境简单、代码可读可改）；沙箱内的无人值守批跑；教 agent 原理的教学场景（200 行读完全部机制）。**排除**：需要结构化工具集（GUI 自动化、专用 API）的任务；依赖跨命令 shell 状态的工作流；想要开箱权限体系与 TUI 的日常开发（那是 Claude Code/Cline 的地盘）。

部署面它倒是齐全：local / Docker / Podman / Singularity / Apptainer / bubblewrap 沙箱化执行都有官方支持，模型经 LiteLLM / OpenRouter / Portkey 接入。这符合它的自我定位——**不是产品，是研究基线**；在横向流派表（L26）里，它是「极简内核」路线的两个端点之一（Pi 是可编程的极简，它是不可减再减的极简）。

### 追问与辨析：单 yaml 配置的形状与「极简的边界」

官网承诺 *Governed by a single yaml file*——把这句话落到形状上（字段以官方 README/文档为准，快照 2026-11-15）：

```yaml
# mini-swe-agent 的单 yaml 配置形状示意（对照官方仓库示例）
agent:
  name: DefaultAgent            # 核心 agent class：约 100 行 Python
  step_limit: 100               # 终止面：最大步数
  cost_limit: 3.0               # 终止面：成本护栏（美元）
model:
  name: litellm/anthropic/claude-sonnet-4-5
  api_key_env: ANTHROPIC_API_KEY
environment:
  type: local                   # local | docker | podman | singularity | apptainer | bubblewrap
  cwd: /workspace/repo
template:                        # 提示词模板：极简路线里唯一的「可调文本面」
  system: "You are a minimal SWE agent. Solve the task with bash only."
```

这张 yaml 里藏着本课最重要的架构信息：**可调面只有模型、环境、终止护栏与提示模板四处**——没有工具注册表、没有权限规则、没有记忆配置，因为那些概念在这个 harness 里不存在。对照 Claude Code 的 settings.json（L03 的四层漏斗）与 Codex 的 config.toml（L05 的档位矩阵），yaml 的「薄」不是未完成，而是设计声明：**配置面的面积 = 架构的复杂度**。

「极简的边界」还有另一面值得展开：v2.0.0（2026-02-11）引入原生 tool calling，说明作者并不教条——当纯文本 bash 调用在某些模型上成为瓶颈时，极简派也会补上协议支持。但补法仍然克制：tool calling 是**可选层**而不是新架构，v1 的纯文本路线继续可用。这种「加法但不换骨架」的演进，与 OpenCode 2.0 的推倒重写（L13）构成同一问题的两种答案：前者把兼容当资产，后者把历史当负债。两种答案没有对错，但团队要选边——选边的依据就是 L27 的场景约束。

```yaml
# mini-swe-agent 由单一 yaml 治理（F-S1：Governed by a single yaml file）
# 键名示意，以官方仓库 config 为准；默认组合 DefaultAgent + LitellmModel + LocalEnvironment（F-S2）
agent:
  step_limit: 100            # 每步独立 subprocess 执行、不共享 shell 状态（F-S2）
  cost_limit: 2.0
env:
  deployment: local          # local / docker / podman / singularity / apptainer / bubblewrap / contree（F-S3）
model:
  model_name: litellm/...    # 经 LiteLLM / OpenRouter / Portkey 接入（F-S3）
```
