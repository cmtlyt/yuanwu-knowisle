### 落差数据：三组数字讲一个完整的故事

OpenCode 在快照时的成绩单有点难看：Harness Leaderboard 三模型均分 **35.5**，显著低于头部五家（49+）；全盘聚合 cost per solved task **$0.904**（独立复算口径中最贵）；FeatureBench 联网取答案率 **7.7%**（九家最高）。但把三组数字与版本背景放在一起，故事就完整了（全部为快照 2026-11-15 口径）：

```text
OpenCode 的落差 = 三种成分的叠加
① 版本因素   bench 测的是 1.19.3 / 2.0.32 双版本线（F-B17）；
             2.0 是三个月 Beta 的全新架构（常驻服务/Code Mode/插件重写）
② 行为因素   scaffold 自由度高 + trial 时间最长（中位 38 次工具调用）
             → 取答案率 7.7% 最高、归一化 1.35 次高；成本也随暴露时间上升
③ 成本因素   $0.904 的聚合口径把「trail 长」直接换算成贵
             （公告口径 $3.35 更极端，因 Flint 7% 解决率拉大极差）
```

这个案例的教学价值在于**拒绝单因解释**：「OpenCode 不行」和「榜单不公平」都太便宜了。正确的姿势是拆成分——版本因素等 2.x 稳定后的复测；行为因素是设计取舍（与 Pi 同款自由度、更长的暴露时间）；成本因素随前两者走。

### 安全面：规则语法完备，企业层缺席

OpenCode 的权限规则层是完备的：官方文档提供 **allow / ask / deny** 三态细粒度规则，可按工具与路径配置——语法上与 Claude Code 的规则层同构（L03）。差距在**治理层**：没有 managed settings 级的不可覆盖强制、没有 workspace trust 的完整体系。加上它取答案率最高的行为数据，给安全团队的结论是：**OpenCode 适合「人盯着用」或「配好容器再用」，不适合零治理直接下发全员**。

### 迁移时代的代价：三方都疼

2.0 重写的代价清单（L13 表）不止疼 Anomaly 自己：**用户**要迁移配置与插件；**生态**要重写集成；**分叉者**最疼——InfoQ 报道点名小米基于 1.x 代码库的 MiMo Code（带项目记忆与自进化蒸馏）面临同步重构难题。这是「平台化重写」的结构性风险：**你越鼓励别人在你的 harness 上建设，重写的代价就越大**。对照三个版本策略案例：DSH 用 developer preview 警告（L07）、Pi 用立场演变文章（L11）、OpenCode 用三个月 Beta + 明确的破坏性变更清单——没有无痛的选项，只有诚实与否的差别。

### 优缺点裁决与适用边界

**优点**：① 模型中立 + MIT，75+ providers，被锁定用户的第一去处；② 2.0 架构在「工具上下文膨胀」这个行业瓶颈上给出了领先答案（Code Mode 默认化）；③ 常驻服务 + 后台 subagent + 无默认超时后台 shell，编排能力强；④ 声明式配置自动迁移，升级体验对普通用户友好；⑤ 生态规模大（21.4 万 star 快照、80+ 内部插件）。

**缺点**：① 榜单成绩与头部差距显著（35.5 vs 49+），且 2.x 时代数据尚待复测；② 聚合成本口径最贵（$0.904 / $3.35 两个口径都垫底）；③ 插件生态断代（1.x 全废）；④ 无 LSP 诊断、只读 AGENTS.md，从其他工具迁入有摩擦；⑤ 权限治理层弱于 Claude Code，行为自由度需要外部约束兜底。

**适合**：多厂商模型团队（核心受众）；愿意写脚本、接 MCP 大生态的进阶用户；需要终端/桌面/Web 多端共享会话的个人工作流。**排除**：企业合规强制下发（治理层不足）；对成本极敏感的无人值守批跑（暴露时间推高成本）；把 1.x 插件资产当核心的团队（先评估重写量）。

至此，「重装平台」路线的两面都拆完了。下一章进入单课系统群：mini-swe-agent——100 行 Python、bash-only、却在榜单拿第一的极端样本。

### 追问与辨析：迁移清单与「落差读法」的实操

把 L13 的破坏性变更表转成一份可执行的迁移清单，并给 1.x → 2.0 的评估顺序：

```bash
# OpenCode 1.x → 2.0 迁移清单（对照官方发布说明的三项破坏性变更）

# 0. 先盘资产：插件 > 服务端集成 > 配置（自动化迁移只覆盖最后一项）
ls ~/.config/opencode/plugin/          # 1.x 插件：全部要按新 API 重写
grep -r "opencode" scripts/ ci/        # 服务端 API 调用：对照新 @opencode/client

# 1. 配置自动迁移（声明式财产）：先装最新 1.x 再升
opencode upgrade --major               # tui.json → 全局 cli.json 自动转换

# 2. 指令文件改名：CLAUDE.md → AGENTS.md（2.0 只读后者）
mv CLAUDE.md AGENTS.md                 # 内容需人工核对（不启动 LSP 的补偿见下）

# 3. LSP 补偿：2.0 无 LSP 工具/诊断，官方建议改用本地检查器
#    CI 里把 tsc / eslint / ruff 挂在 agent 之后跑，诊断回到确定性的世界

# 4. 沙箱内试跑：三项破坏性变更叠加，别在主力机直接升
docker run -it -v "$PWD:/w" node:24 npx opencode@2 --version
```

清单之外，把 L14 正文的「落差三成分」变成一个口头禅式的自查顺序：**看到 OpenCode 的任何弱项数据，先问版本线（1.x 还是 2.x？）、再问暴露时间（trial 多长？）、最后才问能力**。这个顺序在 L02 四问里对应②③④的展开，在 OpenCode 身上因为「两代架构并存」而格外重要——同名字 OpenCode 的 1.19.3 与 2.0.32 是两个不同的被测对象。

再补一个采纳决策的小结：OpenCode 适合「模型中立刚需 + 愿意跟 2.x 新生态」的团队；不适合「1.x 插件资产深厚」或「需要榜单能力背书才能立项」的组织。前者看 L13 的迁移清单，后者等 2.x 稳定后的复测数据——两条路都成立，混着走不成立。

### 迁移暗坑与降级决策的再确认

OpenCode 2.0 的破坏性变更清单（O-3）值得单独背下来，因为它是迁移决策的直接输入：1.x 插件全部失效；服务端 API 重写、客户端换 `@opencode/client`；`tui.json` 迁到全局 `cli.json`；**不再启动 LSP**（无 LSP 工具与诊断，官方建议改用 lint/类型检查器补位）；只读 AGENTS.md、不再读 CLAUDE.md。五条里有三条（插件、LSP、指令文件）会直接改变既有工作流，迁移评估不应只看功能清单。运行时从 Bun 换 Node.js、桌面从 Tauri 换 Electron（O-4）则解释了为什么 1.x 基础上的分叉生态（如小米 MiMo Code）面临同步重构难题——上游大版本断裂时，下游分叉的维护成本会瞬间超过自建。
