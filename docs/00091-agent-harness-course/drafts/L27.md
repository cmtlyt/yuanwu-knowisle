### 选型三步法：把 26 课压缩成一个流程

全课的知识可以压缩成一个可执行的流程。它刻意从「场景」开始而不是从「排行榜」开始——因为 L25 已经证明排行榜回答不了「对你最好」：

```text
选型三步（每步都有本课程的证据支撑）
① 场景约束过滤流派     合规 → 排除「交还用户」派（Pi/mini-swe）
                       研究预算 → 排除重型平台
                       任务时长 → 长期项目才考虑记忆优先
                       模型仓 → 先过协议派系（L24 视角二）
② 交叉数据校验候选     L25 总表：候选者是否落在断层之下？
                       有无未解伪影（重跑中/超时/版本因素）？
                       成本口径对齐了吗？
③ pilot 验证配对       用自己的模型 × 自己的任务域跑小规模试点；
                       arXiv 秩相关 0.36 ⇒ 任何跨环境外推都不可靠；
                       稳定配对（如 openJiuwen+Kimi）可作为试点起点
```

### 六场景决策表

| 场景 | 首选候选 | 理由（证据） | 先排除 |
|---|---|---|---|
| 个人日常（重交互） | Claude Code / Pi / Grok Build | 权限产品化（L03）或可编程（L11）或全屏形态（L20）；榜单头部并列（L25） | mini-swe-agent（无 TUI 体验） |
| 企业合规与管控 | Claude Code 或 Codex CLI，管控层加 OpenHands | managed settings 不可覆盖（L03）；OS 沙箱 + Apache-2.0（L05）；VPC/air-gapped（L22） | Pi/mini-swe（权限交还）；OpenClaw（官方自认无 SSO/RBAC，L23） |
| 研究基线与实验 | mini-swe-agent 或 Pi | 100 行可读可改（L15）；原语化 + MIT（L11）；轨迹干净 | 重型平台（编排是干扰变量） |
| 消息平台 24/7 助理 | Hermes（自托管）或 KiloClaw（托管） | 25+ 平台网关 + cron（L10）；托管化免运维（L19）；安全基线四件套必备 | 裸跑 OpenClaw（宿主机执行 + 公网暴露史，L23） |
| 多 IDE 混合团队 | Kilo（VS Code+JetBrains 双官方）或 Cline（+SDK 嵌入） | 多端 + 开放承诺分层（L19）；审批优先 + checkpoint（L18） | 单端工具（Claude Code 无 JetBrains 官方支持路径） |
| 本地隐私 / 自托管 | OpenCode 2.0 / DSH / OpenHands（VPC） | 75+ providers + MIT（L13）；插件树自省（L07）；企业 VPC 部署（L22） | 专有订阅制（Claude Code）； Responses-only 绑定（Codex 接 Chat-Completions-only 模型受限，L06） |

三处需要显式声明的边界：**Cline 暂无榜单分数**（L18，候选靠机制不靠分）；**OpenCode 的推荐带版本前提**（2.x 落差待复测，L14）；**OpenClaw 的推荐带安全前提**（四件套配置完成才进入候选）。候选表的每一行都对应前文的一章证据——这就是「每格可回溯」的全景表方法在决策层的复用。

### 课程回顾：方法论是资产，数字是快照

27 课走完，本课程真正希望你带走的是三层东西。**第一层：框架**——四控制面（主循环/上下文/权限/终止）能拆解任何现有或未来的 agent 系统；**第二层：纪律**——四问（环境隔离？显著性？成本口径？交互效应？）能拆穿任何对比数据，FeatureBench 事故与 OpenClaw 配置伪影是永久有效的反面教材；**第三层：快照**——15 个系统的具体机制与数字全部绑定 2026-11-15，它们的保质期以周计，但这正是课程反复演练「从证据到结论」的原因：**框架与纪律不变，快照可以按 research/README 的批次纪律随时重采**。

最后一件事：去跑你的 pilot。带上三步法、决策表和四问清单——这 27 课的价值，从你用自己的模型跑出第一组自己数据的时刻开始兑现。

### 追问与辨析：pilot 的三步法与底账清单

决策表给出候选与排除，pilot 给出最终裁决，三步法要落成底账。**第一步固定环境**：pin harness 与模型版本、固定 effort、声明网络策略（榜单的处置方式值得抄——metering proxy 在每次调用上强制 effort、由外部代理计量成本，harness 无法自报，F-B1）；隔离到沙箱或容器，因为 FeatureBench 与 Bug Hunt 的作弊教训都发生在「联网可达答案」的环境里（FB-1~FB-4）。**第二步设计任务集**：用你自己的真实任务 20 个以上，每任务 3 次尝试——重跑翻转 24–28% 的噪声数据（F-B3）说明单次结果不可作决策依据；任务要含你场景里的真实约束（审批点、超时、代码库规模）。**第三步双口径记账**：成本按 $/solved 并声明聚合顺序（F-B4 教训）；无人值守场景必须记「三次全解率」而不仅是「至少解一次」（F-B5：差距 25–43 个百分点）；顺手记录取答案率与 token 构成。跑完再用四问审一遍自己的数据，最后回到决策表核对：候选理由成立吗？排除理由真发生了吗？

```bash
# pilot 底账清单（每行都要落盘；结构参照榜单公开回执 F-B1/F-B8）
git rev-parse --show-toplevel   # 0) 记录代码版本；harness/model/effort 版本号一并 pin
# 1) 环境: 沙箱(容器/Landlock/Seatbelt 级), 网络策略(默认 offline), 代理计量
# 2) 任务: >=20 个自有真实任务, 每任务 3 次, 记录 pass/tokens/cost/wall-clock
# 3) 口径: $-per-solved(声明聚合顺序) / 三次全解率 / 重跑翻转率 / 取答案率
# 4) 复核: 用四问(隔离?显著性?口径?交互?)审自己的结论后再进决策表
```

最后回答一个「为什么要跑 pilot 而不是直接抄榜单第一」的机制问题。arXiv 2610.00917（AX-3/AX-5）给出了两层证据：其一，模型排名跨 harness 反转——Terminal-Bench 4 上 Claude 在 OpenHands 下领先 GPT 7.94 分，在 Pi 下落后 30.16 分；5 个模型中 4 个的「最优 harness」随基准变化，两模型下 harness 排名的秩相关只有 0.36（FB-5 同源结论）。其二，机制解释：模型几乎总是自己发起修复，成败取决于 harness 是否把失败**以模型可用的形式交回**——GPT 适合 Pi 的精简 scaffold，常发 malformed tool calls 的 Kimi 适合 openJiuwen。也就是说，你的模型与 harness 之间存在只有你自己跑得出来的交互效应，任何排行榜（包括本课程引用的所有数据）都只能排除明显断裂的底部、提示值得试的稳定配对（如 openJiuwen 给 Kimi 的三基准 +5.61~+11.11），不能替你做最终选择。厂商自家 harness 未必是自家模型的最优（AX-4）——这句反直觉结论是整个 pilot 方法论的立足点。
