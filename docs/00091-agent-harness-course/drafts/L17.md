### 身世：从 Gemini CLI 的分叉出发

Qwen Code（[github.com/QwenLM/qwen-code](https://github.com/QwenLM/qwen-code)，Apache-2.0）是阿里 Qwen 团队的开源 coding agent。第三方资料普遍记载它**最早从 Google Gemini CLI 分叉**，自 v0.1 起不再跟随上游（此细节属 B/C 级转述，正文标注）。快照时稳定分支 **v0.27.2**（2026-11-10）——这是「分叉后自走」路线的成熟样本：继承了上游的交互骨架，长出了自己的模型生态与多端形态。

### 1.0 Preview：宣布「基座化」的独立分支

2026-11-11，官方以独立分支 `v1.0.0-preview` 开放 1.0 Preview（稳定线继续保留、该阶段暂不接社区 PR，预计 12 月后开放）。发布稿（经 [IT之家](https://m.ithome.com/html/1025393.htm) / UCloud / EOGEE 转述，B/C 级）给出三个架构关键词：

**① 统一事件总线**：从**进程内内存事件总线**起步，沿统一事件模型向分布式演进——与会话事件流（DSH 的 append-only 日志，L07）不同，事件总线是**控制面**的统一抽象，所有组件（模型、沙箱、MCP）经事件模型协作。

**② 手脑分离**：推理编排（脑）与工具执行（手）独立管理，从「一个进程、多个会话」走向「多个节点、更多会话」。这与 DSH 的「单进程插件树 ≠ 微服务」辟谣（L07）形成了有趣对照：DSH 刻意留在单进程，Qwen 1.0 公开走向分布式——两者的任务域假设不同（个人终端 vs 企业基座）。

**③ 集中管控**：模型接入、沙箱资源、MCP 配置/授权/连接改为**集中管控与按需复用**。定位原话是「可嵌入第三方产品的 **Agent 运行基座**」，提供 CLI 与 SDK 双形态。

### 能力面与生态位

| 维度 | 覆盖 |
|---|---|
| 开箱能力 | Auto-Memory / Auto-Skills / SubAgents / Agent Teams / MCP |
| 模型接入 | 多协议：OpenAI / Anthropic / Gemini / Qwen API，任意第三方或 Ollama / vLLM 本地，**运行时切换** |
| 界面 | 终端 + macOS/Windows/Linux 桌面 + 实验性 Web UI（`qwen serve`，HTTP+SSE，多客户端共享会话）+ VS Code / Zed / JetBrains 插件 |
| 集成 | TypeScript / Python / Java SDK + Telegram / 钉钉 / 微信 / 飞书 |
| 安装 | npm（Node ≥22）或 Homebrew，`/auth` 设 provider 与 key |

这个广度对标的是 OpenHands（L22）与 Kilo（L19）的平台路线，但有一个明确的重心声明：**围绕 Qwen 模型调优**——换其他 provider 可用，体验以其为中心。选型时要把这条当硬约束读。

### 数据：约束与断层的中间带

Harness Leaderboard 三模型均分 **44.7**（快照 2026-11-15）——在头部并列组（49+）的「断层」之下，但明显高于 OpenCode（35.5）与 OpenClaw（27.3）。FeatureBench 取答案率 **0.5%**（九家最低）：它与 Claude Code / Codex 同属「长而规范性强的编码提示词」家族（F-B7），scaffold 对模型行为的约束最强。两组数据合起来的画像：**行为最可预测的中游 harness**——在安全敏感、行为审计要求高的环境里，低自由度是优点；在需要模型自主发挥的开放任务里，它可能不如头部并列组的短 scaffold。

### 与 DSH 的可比点：趋同与起点

横向章（L26）会用这一对讲「架构趋同与起点差异」：两家都在讲统一事件/集中管控/可嵌入，但 Qwen Code 是**从 IDE 编码 agent 长成运行基座**（先有产品后有基座），DSH 是**从零设计的插件树运行时**（先有架构后有产品）。起点决定了遗留包袱的形状：分叉出身意味着上游兼容惯性，从零设计意味着 preview 期破坏性变更。**没有哪种起点更高级，只有哪种包袱你的团队能背。**

### 适用与排除

**适合**：Qwen 系模型用户（体验中心）；需要钉钉/微信/飞书触达的中国团队；想要可嵌入基座、能接受 preview 风险的平台建设者。**排除**：第三方模型为主且不愿迁就 Qwen 中心的团队；把 Web UI 当生产依赖的团队（官方标注实验性）；对上游客谱（Gemini CLI 血统）敏感的审计场景。

下一课回到「人审优先」的路线：Cline——把每一次文件编辑都变成一次 diff 审批的 IDE agent。

### 追问与辨析：双版本线的切换命令与基座化评估单

Qwen Code 的双版本线（v0.27 稳定 / v1.0 preview）需要不同的安装与验证路径，命令面（官方仓库与发布稿形状）：

```bash
# 稳定线：npm 或 Homebrew，Node >= 22
npm install -g @qwen-code/qwen-code@latest
qwen                     # TUI；/auth 设 provider 与 key

# 多 provider 运行时切换：OpenAI / Anthropic / Gemini / Qwen API + Ollama/vLLM 本地
/auth                    # 运行中切换 provider——切换不换工具链

# 1.0 preview 线：独立分支，暂不接社区 PR，预计 12 月后开放
npm install -g @qwen-code/qwen-code@1.0.0-preview
#   评估基座化：统一事件总线 / 手脑分离 / 集中管控（模型、沙箱、MCP）
qwen serve               # 实验性 Web UI：HTTP + SSE，多客户端共享会话

# 多端入口速览（1.0 方向）
#   桌面（macOS/Windows/Linux）· VS Code/Zed/JetBrains 插件
#   TS/Python/Java SDK · Telegram/钉钉/微信/飞书
```

给「要不要押 1.0 基座线」一张评估单，逐项打分后再决策：① **需求真实性**——你是要「嵌入第三方产品的运行基座」，还是只要一个好用的 CLI？（基座能力对纯 CLI 用户是纯负担）；② **preview 风险承受**——独立分支 + 暂不接 PR 意味着 API 会漂移（对照 DSH 的 preview 纪律，L08 的版本钉三条全部适用）；③ **模型中心接受度**——体验围绕 Qwen 调优，第三方模型「可用但非一等公民」；④ **替代项对比**——同样的「可嵌入基座」需求，OpenHands 的 Agent Server（L22）是更成熟的候选。四项里有两项存疑就先留在稳定线。

最后补一个跨章的观察：Qwen Code 的「手脑分离」（推理编排与工具执行独立管理、向多节点演进）与 DSH 的「单进程插件树」辟谣（L07）是同一问题的相反答案——前者假设用户会横向扩容，后者假设单机够用。横向章（L26）把这条并进平台化流派的内部光谱：**平台化 ≠ 都要分布式**，扩容假设本身就是一种场景约束。
