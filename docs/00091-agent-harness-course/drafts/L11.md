### 定位：一份公开的「拒绝清单」

Pi（[pi.dev](https://pi.dev/)，源码 [earendil-works/pi](https://github.com/earendil-works/pi)，MIT）的口号有三句：*Pi is a minimal agent harness* / *There are many agent harnesses but this one is yours* / *Change the harness, not your workflow*。它对「极简」的表达不是营销话术，而是一份公开的**不做清单**（What we didn't build）：

| 刻意不做 | 官方替代方案 |
|---|---|
| sub-agents | tmux 派生 Pi 实例，或写扩展 |
| permission popups | 跑在容器里，或自建确认流程 |
| plan mode | —（扩展示例里有） |
| 内置 to-dos | 用 `TODO.md` |
| background bash | 用 tmux——官方理由：*Full observability, direct interaction* |

这份清单的工程含义在后半句：Pi 把这些「产品功能」降维成**扩展原语**。官方扩展哲学只有一句：*Primitives, not features*——扩展是可访问 tools / commands / keyboard shortcuts / events / **full TUI** 的 TypeScript 模块，官方仓库提供 **50+ 示例**，其中恰好包括 sub-agents、plan mode、permission gates、path protection、SSH execution、sandboxing、MCP integrations、custom editors。也就是说：**能力一个不缺，但每一个都要自己装配**。这与 L03/L05 形成鲜明对照——Claude Code 把权限做成四层漏斗，Codex 把权限做进操作系统，Pi 把权限交还用户。

### 上下文工程：最小提示 + 一切可替换

Pi 的上下文控制面可以用四个「可替换」概括（[官方文档](https://docs.pi.dev/latest)）：

```text
Pi 的上下文面（官方 F-P7）
① 系统提示：minimal system prompt（源码 system-prompt.ts 可读）
   └ SYSTEM.md 按项目替换或追加默认系统提示
② 项目指令：AGENTS.md 启动时从 ~/.pi/agent/、父目录、当前目录加载
③ 压缩：接近上下文上限时自动摘要旧消息——
   └ 可被扩展完全替换（主题式压缩 / 代码感知摘要 / 换摘要模型）
④ 动态上下文：扩展可在每轮前注入消息、过滤历史、做 RAG 或长期记忆
   └ Skills 渐进披露（按需加载，不破坏 prompt cache）
   └ Prompt templates：Markdown 文件，/name 展开
```

对比 Claude Code 的七种指令载体（L04），Pi 的答案是「少而全部可编程」：没有内置的 rules 目录体系与 output styles，但 Dynamic context + 可替换 compaction 给了扩展作者比内置方案更大的自由度。两条路线的取舍很清楚：**开箱一致性（Claude Code）vs 可编程性（Pi）**。

### 会话树与人工介入

Pi 的会话存成**树**：`/tree` 回到任意历史点继续，全部分支存在单一文件里；可按消息类型过滤、加书签；`/export` 导出 HTML、`/share` 上传 gist 得到可渲染链接。人工介入有两个粒度：`Enter` 发 **steering message**（当前工具执行后立即送达，并**中断排队中的剩余工具**——真正的中途纠偏）；`Alt+Enter` 发 **follow-up**（等 agent 完成）。这个设计把「人何时插话」从一个模糊的产品决策变成了两个明确的按键。

### 立场演变：从「拒绝 MCP」到「内置 MCP + Codemode」

Pi 曾以「拒绝 MCP」闻名——社区文章普遍引用它「用 CLI 工具 + Skills + TypeScript 扩展替代 MCP」的立场。但 [pi.dev 官网](https://pi.dev/) 现行版本的标题已经改成 **`No MCP` → `Now with MCP+Codemode`**：MCP 内置，Codemode 让 agent 在 JavaScript 沙箱里组合工具调用（思路与 OpenCode 2.0 的 Code Mode 相同，L13），MCP 扩展机制仍然保留，并且官方附了一篇 *Why we changed our minds* 解释转变原因。

这不是丢人的反复，而是本课程**最有教学价值的方法论案例**：一个以立场鲜明著称的项目，在生态压力下公开修改了自己的架构决策。它验证了 L02 的第四问——任何「XX 不支持 YY」的结论都有保质期，引用前必须看官网当前版本。本课程在台账（corrections C-1）里把这个演变单独登记，所有章节统一按现行口径写。

### 四种运行模式（Pi 的，不是 DSH 的）

`Interactive`（完整 TUI）、`Print/JSON`（`pi -p "query"`，`--mode json` 事件流）、`RPC`（stdin/stdout JSON 协议，供非 Node 程序集成）、`SDK`（嵌入应用，官方以 OpenClaw 为真实世界集成实例）。再次强调：**与 DSH 的 Standard/PTC/Minimal/Creative 完全是两套概念**（C-2 台账），L07 已各自写对，横向表（L24）里也会分开列。

下一课给 Pi 做优缺点裁决——它的基准成绩（49.4，头部并列组）与成本（Pi 是 Bug Hunt 三档最便宜的 harness）会让「极简也能打」这五个字有数据支撑，而 Kimi Code 直接复用 pi-tui 的事实会让「内核即基础设施」有生态佐证。

### 追问与辨析：写一个最小扩展的形状与「能力责任」清单

「Primitives, not features」的最好理解方式是自己写一个。Pi 扩展是可访问 tools / commands / shortcuts / events / TUI 的 TypeScript 模块，一个最小 permission gate 的形状（对照官方 50+ 示例里的 permission gates，API 以 docs.pi.dev 为准）：

```typescript
// ~/.pi/agent/extensions/confirm-git-push.ts —— 形状示意（对照官方示例）
export default function (pi) {
  pi.registerTool({
    name: "confirm_git_push",
    description: "拦截 git push：先展示将推送的 commit，等人确认",
    async run(args, ctx) {
      const plan = await ctx.exec("git log --oneline @{u}..HEAD");
      const ok = await ctx.confirm(`即将推送 ${plan.trim()}，允许吗？`);
      if (!ok) return { result: "aborted by user" };
      return ctx.exec(`git push ${args.remote ?? "origin"}`);
    },
  });
}
```

安装即生效：`pi install git:github.com/you/pi-tools` 或直接放进扩展目录后 `/reload`（运行时原地自改）。这个例子替 Pi 回答了一个尖锐问题：**没有 permission popups 的 harness 怎么做安全？**——答案是「权限逻辑也是扩展，自己写、自己审、自己装」。它与 Claude Code 内建四层漏斗的差别不在能力，在**责任链**：Claude Code 的漏洞是 Anthropic 的 bug，Pi 扩展的漏洞是你的 bug。

顺着责任链，给出极简内核的「能力责任清单」——采用 Pi（或任何交还用户的 harness）前逐项确认：① 沙箱由谁提供（官方建议容器，选型时验证你的容器方案）；② permission gate 由谁写（官方示例可抄，但要 review）；③ sub-agent 编排由谁管（tmux 派生实例的生命周期归你）；④ to-do/任务状态归谁维护（官方建议 TODO.md 进 git）。四项都 answered 才进入候选——这正是 L27 决策表里 Pi 的行有前提条件的原因。
