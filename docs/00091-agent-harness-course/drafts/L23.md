### 沿革：三个月内两改名的个人 agent

OpenClaw 的出身自带戏剧性（百科/媒体口径，C 级）：Peter Steinberger **2025-11** 以 `Clawdbot` 发布；2026-01-27 因 Anthropic 商标问题改名 `Moltbot`；01-29/30 再改 **OpenClaw**；2026-02-15 Sam Altman 宣布创始人加入 OpenAI，项目转由**独立基金会**运营并继续开源（MIT、TypeScript）。口号是「让 AI 通过你已经在用的聊天 App 跟随你」——它是本课程 15 个系统里**唯一不以编码为中心**的：WhatsApp / Telegram / Slack / Discord / Signal / iMessage / Matrix / IRC / 飞书 / Zoom / MS Teams / SMS 等 **20+ IM 通道**、**150+ 扩展**，伴侣应用还能把语音/相机/屏幕/设备控制接到 agent。

### 架构：Gateway 即控制面

第三方深度分析（C 级，需官方核实）给出的架构画像：**Gateway 统一管理一切**——会话、工具解析、事件、通道连接、插件引导、Cron、节点/伴侣管理、MCP、认证与审批。协议基于 WebSocket（版本 4），由 **16 个 Schema 片段**组合（Board / ProgressCard / Transport / AgentControl / Node / Integration / SessionCore / … / Approval / PluginLifecycle / Portal），演进原则 *Additive first*（只加不改）。工程纪律上有一条值得单独记住的：**SQLite-First**——运行时状态一律进 `state/openclaw.sqlite`（每 Agent 一个 DB），明确禁止用 JSON/JSONL 存运行时状态。

与 Hermes 的网关（L10）对照：两者都是「消息平台 agent」，但 Hermes 的网关是全功能 agent 的入口之一（CLI/ACP/batch 并存），OpenClaw 的 Gateway 就是系统本体——**控制面即产品**。生态位置上，pi.dev 官网把 OpenClaw 列为 Pi RPC/SDK 模式的真实世界集成：Pi 内核 + OpenClaw 网关的分层组合，是「harness 可组合」的官方背书。

### 榜单：一个配置值写出的末位分数

OpenClaw 在 Harness Leaderboard 三模型均分 **27.3%** 垫底（快照 2026-11-15）。但榜单披露的机制细节让这个末位变得可疑（F-B6）：它的 **8,192-token 输出上限**（模型条目未声明 maxTokens 时的 fallback）终止了 **333 次 Flint DeepSWE trials 中的 289 次**——将近九成的 trial 死于一个默认值，榜单已在解除上限后重跑。这是 L02 四问之「配置伪影」的教科书案例：**分数是 harness 配置、模型能力与任务域三者共同写出的，末位 ≠ 最差**。事故文档还给了另一条审计教训：OpenClaw 日志只有每 trial 工具摘要、没有 shell 命令明细（1,603 个摘要中 1,602 个含 `exec`）——**日志可见性决定你能否审计它**，取答案率对它「不可见」不等于零。

### 安全面：个人 agent 的风险基线

媒体报道汇总的安全数据（C 级，快照 2026-11-15，官方修复动作一并列出）：

```text
结构性风险（模式决定）        不在浏览器沙盒内运行，宿主机 OS 层直接执行 shell、
                             读写文件、控制浏览器
历史配置风险（已改）          Gateway 旧版默认监听 0.0.0.0:18789 → 新版改 localhost
存储风险                     长期记忆明文 Markdown/JSON 存宿主机
暴露面（媒体口径）            Shodan 扫出近千个无认证实例；
                             卡巴斯基审计称 512 个漏洞（8 个严重）；
                             CVE-2026-25253（CNVD-2026-13289）v2026.1.29 修复
官方自认的边界                无多租户 / 无 SSO/RBAC / 无内置知识库/RAG / 单 Agent 架构
```

这组数据的教学价值是把 L10（Hermes 安全面）与 L02 四问①推向结论：**给个人 agent 做安全基线，四件套缺一不可**——容器隔离（别让 shell 直达宿主机）、默认只监听 localhost、凭据与记忆的加密或权限收敛、公网零暴露。OpenClaw 的每一个风险点都有对应的工程对策，问题从来不是「这类工具能不能用」，而是「你有没有做这四件事」。

### 适用与排除

**适合**：本地优先的个人助理玩家（自托管 + 愿意配安全基线）；需要 20+ IM 通道触达的个人自动化；研究「Gateway 控制面 + SQLite 纪律」架构的工程师。**排除**：企业生产环境（无多租户/SSO/RBAC 是官方自认）；公网暴露部署；把榜单末位当能力结论的决策（等解除上限重跑的数据）。

至此 15 个系统全部拆完。下一章开始横向综合：先用一张全景对照表把 15 个系统钉进同一坐标系（L24），再交叉四套基准数据（L25）、归纳四大架构流派（L26）、最后给出场景化选型决策表（L27）。

### 追问与辨析：把安全事件折算成部署基线

OpenClaw 的价值一半在架构示范（Gateway 即控制面、SQLite-First），一半在安全反面教材。把澎湃新闻与卡巴斯基审计（F-S19，媒体报道口径）折算成自托管基线，可得到四条硬约束：①版本——`CVE-2026-25253`（CNVD-2026-13289）在 v2026.1.29 修复，部署必须高于此版本；②绑定面——旧版 Gateway 默认监听 `0.0.0.0:18789`，新版改 `localhost:18789`，部署后要用端口检查确认实际监听面；③网络位——Shodan 曾扫出近千个无认证实例，公网直连等于把宿主机 shell 交出去；④记忆落盘——长期记忆以明文 Markdown/JSON 存宿主机，需要自行加密或定期审计。卡巴斯基称 512 个漏洞（8 个严重）的总量级提醒我们：**「权限哲学宽松 + 宿主机执行 + 20+ IM 通道」的组合本身就是一个攻击面设计问题**，不只是单个 CVE 的修补问题。

```bash
# OpenClaw 自托管安全基线（依据 F-S19 公开报道整理；具体配置以官方 security 文档为准）
# 1) 版本：高于 CVE-2026-25253 修复版 v2026.1.29
# 2) 绑定面：确认 Gateway 监听回环而非全网卡
ss -tlnp | grep 18789        # 期望 127.0.0.1:18789，出现 0.0.0.0 即违规
# 3) 网络位：防火墙/WireGuard 之后，禁止公网直连（Shodan 曾见近千无认证实例）
# 4) 记忆：审计 state/ 与长期记忆目录中的明文敏感字段，必要时自行加密
```
