### 场景：编译导出这条路线解决什么

L106 的 GGUF 走的是「量化 + 轻量运行时」路线，主打 CPU 与消费级显卡的便携性。本课走另一条：**编译导出**——把模型转成计算图中间表示（ONNX），或进一步编译成针对具体 GPU 高度优化的 engine（TensorRT-LLM）。它追求的是**极致吞吐与低延迟**，代价是构建流程更复杂、产物与硬件绑定。两条路线不是互斥：ONNX 是通用中间表示，TensorRT 能作为它的后端之一；GGUF 则服务于 llama.cpp 生态。选型取决于你的硬件与性能目标。编译路线的收益来自两处：一是**算子融合**——把原本多次核函数调用的线性层、激活、归一化熔成更少的 kernel，减少显存往返；二是**编译期特化**——按目标 GPU 的 Tensor Core 能力、显存层级与形状上限挑选最优实现，避免运行时猜测。代价是构建流程重、产物绑定硬件、迭代周期长。因此编译路线更适合「模型稳定后追求极致性能」的生产阶段，而在探索阶段用 ONNX 或 GGUF 快速验证更划算。编译产物也不利于 A/B 快速切换——每换一版权重都要重新 build，迭代速度天然慢于解释执行的 ONNX 或 GGUF。

:::deep

### 三种产物的定位：图、编译产物、量化文件

把 L105 之后的几种产物放在一张谱里，避免混淆：

- **HF safetensors（L105）**：训练生态的通用权重格式，框架无关，但加载时还要重建计算图。
- **ONNX 图**：把计算图**固化**成标准算子序列，跨语言、跨后端可加载；导出快，但仍需推理运行时解释执行或二次编译。
- **TensorRT-LLM engine**：在图基础上**针对具体 GPU 编译**——算子融合、kernel 自动选型、显存预分配，产物是「为这张卡量身定做」的二进制，速度最快但不通用。
- **GGUF（L106）**：带量化的单文件格式，配 llama.cpp 运行时，主打便携与低资源。

一句话：**ONNX 是「可移植的图」，TRT engine 是「绑定硬件的编译结果」，GGUF 是「量化打包」**。本课重点在前两者。

:::

### ONNX：optimum 一键导出

Hugging Face 的 `optimum` 把 ONNX 导出封装成一行：把 `ORTModelForCausalLM` 的 `from_pretrained` 参数 `export=True`，它就会从 HF 权重导出 ONNX 图，`save_pretrained` 再把图、配置、分词器一起落盘。

```python
# 依赖：pip install optimum onnx onnxruntime
from optimum.onnxruntime import ORTModelForCausalLM
from transformers import AutoTokenizer

model_id = "./merged-model"          # L105 的合并模型目录（三件套齐备）
onnx_dir = "./onnx-model"
# export=True：从 HF 权重导出 ONNX 图；ORTModel 同时保存配置
ort_model = ORTModelForCausalLM.from_pretrained(model_id, export=True)
ort_model.save_pretrained(onnx_dir)
AutoTokenizer.from_pretrained(model_id).save_pretrained(onnx_dir)
print("ONNX 导出完成，目录:", onnx_dir)
# 导出时 opset 与动态轴（batch/seq）已固定，下游编译受此约束
assert ort_model.config.model_type in ("llama", "gemma", "qwen2"), "确认模型类型可导出"
```

导出前必须确认模型是 L105 合并后的标准权重——带 LoRA 适配器的模型无法直接导出，因为 ONNX 图里没有「旁路适配器」这一概念，必须先把增量折进主矩阵。若你拿到的目录里同时有 `adapter_config.json` 与 `model.safetensors`，说明它还是适配器形态，回到 L105 先合并。导出时还要注意 **opset 版本**与**动态轴**：动态轴允许 batch 与 seq 变化，但过多动态维度会让下游编译难以优化，实践中常把 batch 固定为几个档位、seq 设上限。opset 太低会缺少新算子导致降级拆分，太高则可能不被目标运行时支持，一般跟随 optimum 默认值即可，除非有明确的兼容性需求。另一个高频坑是导出大模型时 ONNX 文件超过 2GB 限制——protobuf 单文件有此上限，optimum 会自动切成多个外部数据文件（`.onnx` 加 `.data`），加载时须保证这些文件在同一目录、相对路径不变，单独拷走 `.onnx` 会报权重缺失。导出完成后把整个目录当成一个整体交付，别只拷贝主图文件。

**ONNX Runtime 推理验证**

导出后用 ONNX Runtime 加载图，跑一次会话建立与数值一致性检查。算子融合会带来微小差异，所以比对 logits 要设容差而非要求逐位相等。

```python
import numpy as np

# 用 onnxruntime 建立会话，确认图可加载
try:
    import onnxruntime as ort
    sess = ort.InferenceSession("./onnx-model/model.onnx",
                                providers=["CPUExecutionProvider"])
    print("ONNX 输入:", [i.name for i in sess.get_inputs()])
    assert len(sess.get_inputs()) >= 1, "ONNX 图应有输入"
except Exception as e:
    print("ONNX Runtime 未装或图为分片，跳过会话验证:", type(e).__name__)

# 数值一致性：导出前后 logits 应在容差内（量级示意）
logits_hf  = np.array([0.12, -0.44, 0.88, 0.03], dtype=np.float32)
logits_onx = np.array([0.12, -0.43, 0.87, 0.03], dtype=np.float32)
diff = float(np.max(np.abs(logits_hf - logits_onx)))
print("导出前后 logits 最大差:", diff)
assert diff < 0.05, "ONNX 导出不应显著改变数值"
```

这段把「导出成功」从「文件生成了」升级为「图能加载 + 数值在容差内」。若差异超过容差，优先查 opset 与算子降级（某些 HF 算子在 ONNX 里被换成近似实现），而不是急着往下走 TRT 编译。

### TensorRT-LLM：编译 .engine

若目标是 NVIDIA GPU 上的极致吞吐，就把权重交给 TensorRT-LLM 编译成 `.engine`。流程分三步：转换 checkpoint、build engine、冒烟生成。

```bash
# TensorRT-LLM：HF 权重 -> checkpoint -> engine（针对具体 GPU 编译）
# 1) 转换权重为 TRT-LLM 格式
python convert_checkpoint.py --model_dir ./merged-model \
  --output_dir ./trt_ckpt --dtype float16 --tp_size 1
# 2) 编译 engine：gemm_plugin 融合矩阵乘；形状上限决定 KV/激活显存预算
trtllm-build --checkpoint_dir ./trt_ckpt --output_dir ./trt_engine \
  --gemm_plugin float16 --max_batch_size 16 \
  --max_input_len 2048 --max_seq_len 4096
# 3) 冒烟：用官方 run.py 生成一段文本
python ../run.py --engine_dir ./trt_engine --tokenizer_dir ./merged-model \
  --max_output_len 32 --input_text "Hello"
ls -lh ./trt_engine/*.engine
```

`--max_batch_size` 与 `--max_seq_len` 是**编译期固化**的形状上限：它们决定 KV 与激活的显存预分配。留太大浪费显存、留太小则拒绝超长输入，需按 L110 压测得到的真实流量分布来定。`--tp_size` 是张量并行度，多卡时按卡数设置；`--gemm_plugin` 启用融合 kernel，一般开启。

### ONNX 与 TRT-LLM 的取舍

把两条路线放到决策台上：

- **导出成本**：ONNX 导出快、命令简单，适合快速验证与多后端分发；TRT engine 构建慢，且**必须在部署同款 GPU 上构建**，换架构要重编。
- **性能**：TRT engine 经算子融合与 kernel 自动调优，吞吐与延迟通常明显优于通用 ONNX Runtime；ONNX 胜在平台无关。
- **灵活性**：ONNX 动态轴灵活，适合输入形状多变的场景；TRT engine 形状固化，适合形状稳定、追求极致性能的生产服务。
- **组合关系**：二者可叠加——ONNX 作中间表示，TensorRT 作为其优化后端；也可各自独立走（optimum 导出给 ORT，TRT-LLM 走原生编译）。

一句话判据：**要快速跨平台就 ONNX，要单卡极致吞吐就 TRT-LLM**。两者都以 L105 的合并模型为起点，所以合并与规范保存是共同前置。

给一个可执行的决策顺序：先把 ONNX 导出跑通并验证数值，作为「模型可编译」的基线；再在一张目标 GPU 上 build 一个最小 engine（max_batch=1、max_seq=1024），测出单请求延迟；确认收益符合预期后，按 L110 压测得到的真实并发与序列分布调整形状上限、正式构建。若最小 engine 都没有明显提速，先查算子是否大量降级、dtype 是否被回退到 fp32，而不是盲目加大 batch。这套「先基线、再最小验证、最后按流量定形」的节奏，能把编译路线的试错成本压到最低。

工程上还有一条容易被忽视的判据：**可复现性**。ONNX 导出受 optimum、transformers、opset 版本影响，同一模型在不同版本下导出的图可能不同；TRT engine 则额外绑定 CUDA、TensorRT、驱动与 GPU 架构。因此生产环境要么把这些版本**锁死**并随模型一起归档，要么接受「换个环境就重编」的代价。构建脚本应把版本号、构建参数（`max_batch_size`、`max_seq_len`、`dtype`、`tp_size`）与模型 hash 一起写进产物目录的元数据文件，这样出问题时能精确复现当时的构建条件。若你所在团队有多款 GPU，建议为每款卡各自构建 engine 并打上硬件标签，运行时按机型选择——永远不要在 A 卡上 build 完拿去 B 卡跑，那只会得到加载失败或性能异常。

:::tip

### 实操记忆：先 ONNX 验证，再 TRT 冲刺

推荐节奏：先用 `ORTModelForCausalLM(export=True)` 导出 ONNX、用 ORT 跑通数值一致性，确认「图是对的」；再决定是否需要 TRT-LLM 冲刺性能——若需要，在同款 GPU 上 build engine、按压测形状设 `max_batch/seq`，并用 `run.py` 冒烟。任一环节的模型都必须先是 L105 的合并成品。下一课 L108 把这些导出产物（以及 L106 的 GGUF）接到统一的服务化框架上，起一个 OpenAI 兼容端点。
