### 场景：把合并模型变成可本地加载的 GGUF

L105 产出的标准 HF 模型（safetensors + config + tokenizer）适合训练生态，但在本地/边缘推理场景里，llama.cpp 的 **GGUF** 格式更受欢迎：它把权重、元数据、分词器打进**单一文件**，配合量化能用极小体积跑在 CPU 或消费级显卡上。本课走通从 HF 模型到可加载 GGUF 的完整流程，并给出 llama.cpp 官方量化档位表与「甜点位」判据。GGUF 的典型用武之地是本地助手、离线推理、嵌入式与边缘设备：这些场景的共同约束是显存/内存有限、不能依赖云服务，因此「单文件 + 量化 + 轻量运行时」的组合特别合适。相比 L107 的编译路线，GGUF 的构建门槛低得多——不需要特定 GPU、不需要漫长的编译，一台普通机器就能转换并量化出可分发的文件，这也是它在开源社区流行的根本原因。

:::deep

### 为什么转换与量化要分两步

GGUF 导出是**转换**与**量化**两件事的叠加，分开做有工程上的好处：

- **转换（convert）**：把 HF 的 safetensors 张量按 GGUF 结构重新组织，产出高精度的 **F16 中间文件**。这一步保留全部信息，是可反复回退的「母版」。
- **量化（quantize）**：从 F16 母版压成目标档位（如 Q4_K_M）。不同档位是从同一母版**独立**量化出来的，互不影响。

分开的好处是：你只需转换一次，就能从同一份 F16 试出 Q8_0、Q5_K_M、Q4_K_M、Q2_K 多个档位，逐档实测质量后选最合适的。若只有一步到位，换档位就得从头转换，浪费大量时间。

另一个细节是量化**有损且不可逆**：一旦从 F16 压到 Q4_K_M，原始精度就回不来了；若后续想换档，必须回到 F16 母版重新量化。这也是母版要单独留存、不要覆盖的原因——不少团队踩过「把唯一的 F16 直接量化掉、想升档时找不到母版」的坑。母版体积大，但它是你唯一的回退点，值得多留一份磁盘空间。

:::

### 实操：convert + quantize 两步流程

下面是标准命令（路径按你的 llama.cpp 安装位置调整）。第一行把 L105 的合并模型目录转成 F16 GGUF，第二行量化到 Q4_K_M，第三、四行查看体积验证压缩效果。

```bash
# 依赖：llama.cpp 仓库（含 convert_hf_to_gguf.py 与 llama-quantize）
# 1) HF 合并模型（L105 三件套目录）转 GGUF F16 母版
python llama.cpp/convert_hf_to_gguf.py ./merged-model \
  --outfile ./model-f16.gguf --outtype f16
# 2) F16 母版量化到 Q4_K_M（甜点位）
./llama.cpp/build/bin/llama-quantize \
  ./model-f16.gguf ./model-Q4_K_M.gguf Q4_K_M
# 3) 列出 GGUF 元数据结构，确认档位与张量信息
./llama.cpp/build/bin/llama-gguf-hash ./model-Q4_K_M.gguf
# 4) 对比转换前后体积
ls -lh ./model-f16.gguf ./model-Q4_K_M.gguf
```

转换脚本要吃 L105 的三件套，所以**合并与规范保存是前置条件**——若目录里缺 tokenizer 文件，转换会在分词器环节报错。量化命令末尾的 `Q4_K_M` 就是目标档位，换成 `Q8_0` 或 `Q2_K` 即可从同一 F16 母版产出别的档位。转换命令里的 `--outtype f16` 建议保留——直接从 bf16 或 fp32 母版量化会引入额外舍入，F16 是量化工具最稳妥的输入精度。转换脚本会读取 config.json 判断架构与张量布局，所以 L105 的三件套缺一不可；若模型用了自定义架构，脚本可能不认识，需要先确认该架构在 llama.cpp 的支持列表里。量化过程本身是纯 CPU 的张量扫描与分块，7B 模型通常几分钟内完成，与 GPU 无关，这使得「一次转换、多档量化」的试错成本很低。

### 量化档位表：F16 到 Q2_K

下表是 **llama.cpp 官方文档的 k-quants 档位**（A 级，可写死），给出每档的平均位宽（bpw）与相对 F16 的体积比例：

| 档位 | 位宽 bpw | 相对 F16 体积 | 质量特征 |
|---|---|---|---|
| F16 | 16.00 | 100% | 无损母版，体积最大 |
| Q8_0 | 8.50 | 53% | 几乎无损，常用作高质量上限 |
| Q6_K | 6.56 | 41% | 高质量压缩，体积质量兼优 |
| Q5_K_M | 5.69 | 36% | 高质量，略大于 Q4_K_M |
| Q4_K_M | 4.85 | 30% | 甜点位，通用首选 |
| Q4_0 | 4.55 | 28% | 老式 4bit，质量略逊 k-quants |
| Q3_K_M | 3.91 | 24% | 中低档，质量可感知下降 |
| Q2_K | 3.35 | 21% | 体积最小，质量下降明显 |

读表要点：**位宽决定体积，块大小与重要性分配决定质量**。k-quants 系列（带 `_K_`）比老式 `Q4_0`、`Q5_0` 更聪明——它按张量块的重要性和数值范围分配位宽，关键块多给几位、次要块少给，所以同为 4bit 级，`Q4_K_M` 质量好于 `Q4_0`。后缀 `S/M/L` 表示同一档位里的体积档（Small/Medium/Large），`M` 是默认平衡档。

下面用代码把这张表与体积换算跑一遍，固化「F16 → Q8_0 → Q4_K_M → Q2_K」的体积阶梯。

```python
# llama.cpp 官方量化档位（A 级，可写死）：档位 -> (平均位宽 bpw, 相对 F16 体积)
QUANTS = {
    "F16":    (16.00, 1.00),
    "Q8_0":   (8.50, 0.53),
    "Q6_K":   (6.56, 0.41),
    "Q5_K_M": (5.69, 0.36),
    "Q4_K_M": (4.85, 0.30),
    "Q4_0":   (4.55, 0.28),
    "Q3_K_M": (3.91, 0.24),
    "Q2_K":   (3.35, 0.21),
}
BASE_GB = 14.0   # 7B 模型 F16 约 14 GB（量级示意，随模型变动，不担关键结论）
print(f"{'档位':<8}{'bpw':>6}{'体积GB':>9}{'相对F16':>9}")
for name, (bpw, ratio) in QUANTS.items():
    print(f"{name:<8}{bpw:>6.2f}{BASE_GB*ratio:>9.2f}{ratio:>9.0%}")
assert QUANTS["Q4_K_M"][0] < QUANTS["Q5_K_M"][0] < QUANTS["Q8_0"][0] < QUANTS["F16"][0]
assert QUANTS["Q4_K_M"][1] < 0.35, "Q4_K_M 应压到 F16 的约 30%"
print("Q4_K_M：约 4.2 GB，体积压到 30%，被称为甜点位")
```

以 7B 模型约 14 GB 的 F16 母版计，Q4_K_M 压到约 4.2 GB——一张 8GB 显卡就能轻松跑，质量却接近原始模型，这就是它成为默认推荐的原因。Q2_K 虽然只有约 2.9 GB，但质量下降明显，只适合极端显存受限或质量不敏感的场景。

需要强调的是，体积比例是**可写死的档位属性**（A 级），但「质量是否可接受」是**任务相关**的：同一个 Q4_K_M，跑日常问答几乎无损，跑精确数学推理或长文一致性就可能出现可感知退化。所以选档不能只查表，必须配一套质量抽测——选 20 到 50 条覆盖你真实任务的 prompt，对 F16 母版与候选项各跑一次，人工或规则比对输出，确认退化在可接受范围再定档。下面把这套抽测固化成可跑的清单。

```python
# 量化质量抽测清单：同一组 prompt 对比 F16 与 Q4_K_M 的输出
prompts = [
    "解释 RLHF 的三个阶段",
    "写一段 Python 快速排序",
    "用一句话说明什么是对齐税",
]
def smoke_check(engine, tag):
    # 真实：engine.generate(prompt)；这里打印计划，强调"必须实跑"
    for p in prompts:
        print(f"[{tag}] prompt={p[:12]}... -> 记录输出与延迟")
    return len(prompts)

n = smoke_check("F16", "F16 母版")
assert n == 3, "抽测集应覆盖多类任务"
print("验收动作：逐条对比 F16 与 Q4_K_M 输出，明显退化则升档")
```

### 验证导出模型可加载

生成文件不等于导出成功。验证分三层：① **文件头魔数**——GGUF 文件以 `GGUF` 四个字节开头；② **实际加载**——用 `llama-cli` 跑一次短生成；③ **质量抽测**——在几个代表性 prompt 上看输出是否合理。下面把文件头校验写成可跑代码。

```python
import struct, os

def read_gguf_magic(path):
    with open(path, "rb") as f:
        return f.read(4)

# 造一个示意文件（真实 GGUF 由 convert 产出），跑通校验流程
demo = "./demo.gguf"
with open(demo, "wb") as f:
    f.write(b"GGUF" + struct.pack("<I", 3))   # 魔数 + 版本 3
magic = read_gguf_magic(demo)
print("GGUF 魔数:", magic, "版本:", 3)
assert magic == b"GGUF", "文件头必须是 GGUF 魔数"
print("文件头校验通过；实际加载请跑：llama-cli -m model-Q4_K_M.gguf -p 'hi' -n 16")
```

实际加载那一步不可省：文件头对但张量名映射错、分词器缺失、元数据版本不匹配，都只有在 `llama-cli` 真正读入时才会暴露。高频坑还有两个：一是**分词器版本不匹配**，转换时从 HF 目录抄来的词表若与训练时不一致，生成会输出乱码或异常 token，务必在冒烟阶段用一句中文和一句英文各测一次；二是**上下文长度设置**，加载时的 `ctx_size` 若小于模型支持的上限，长 prompt 会被截断，表现为「记不住前面说了什么」，这不是模型能力问题而是运行参数没设对。把这两项连同量化档位记进部署清单，能省掉大量「模型好像变笨了」的误报。冒烟命令跑通后，再按 L104 的验收思路抽测质量——尤其对比 F16 与 Q4_K_M 在同一批 prompt 上的输出，确认量化没有带来不可接受的退化。

:::tip

### 档位选择判据

按显存预算选档：① **显存充裕、质量优先**（如 24GB 卡跑 7B）用 Q8_0 或 Q6_K，几乎无损；② **通用默认**（8 到 16GB 卡）用 **Q4_K_M**，约 30% 体积、质量损失小，是最稳的甜点位；③ **显存极紧**（CPU 或 4GB 卡）降到 Q3_K_M 或 Q2_K，但必须实测质量；④ **要反复试档**就从同一 F16 母版多量化几个，逐档跑质量抽测再定。记住量化是「体积换质量」的交易，没有普适最优档，只有「在你硬件与任务上的最优点」。下一课 L107 走另一条部署路线：ONNX 与 TensorRT-LLM 的编译导出。
