### 从「看需求」到「可量化判据」

选型的难题从来不是「有哪些架构」，而是「我这个需求到底该选谁」。L55 给了五维矩阵，但矩阵要能用，前提是先把需求翻译成矩阵能吃的量。这一课演示这套翻译，并给出 MoE、SSM、扩散的适用边界与常见误区，最后产出一份「有依据的推荐」。所谓有依据，是指结论附带可量化理由（哪个阈值让哪个架构出局）、反例边界（什么情况下推荐反转），能被别人复算与反驳，而不是「我觉得」。整套方法可以用一句话概括：**约束先量化、量化后代入、代入后排序、排序后写明边界**。下面用一个贯穿场景来走一遍：假设你要为一个产品选架构，约束是「每月推理预算有限、P95 延迟要低、上下文 32K、且产品核心功能包含在长文里改字段」。

### 第一步：把四类约束翻译成阈值

模糊需求必须变成数字，否则无法判断「满足/不满足」。四类约束的翻译方式如下：

**预算**：翻成「每百万 token 的可接受成本」或「单卡可承载的并发数」。若已知硬件（如单张 24GB 卡）和模型，预算进一步翻成显存上限——权重显存加 KV 显存不能超过卡容量。这直接关联 L57 的成本模型。

**延迟**：翻成分位数，而非平均值。用户感知的是尾延迟，所以定「P95 首 token 延迟低于 X 毫秒」「P95 每 token 延迟低于 Y 毫秒」。平均值会被大量短请求拉低、掩盖长尾，绝不能作为选型承诺。

**上下文**：翻成「最大序列长度」与对应的 KV 显存预算。32K 上下文下，自回归 KV cache 会占用可观显存（L57 量化），这决定了能不能塞进目标硬件。

**编辑需求**：翻成「是否需要局部改稿、infilling、约束填充」。这是扩散的开关型判据——只要产品核心功能包含局部编辑，可控性维度权重就拉满，扩散进入候选；若完全没有编辑需求，扩散的多步延迟就是纯负担。

:::deep

### MoE / SSM / 扩散的适用边界

每类架构都有「占优区间」和「反转区间」，写出边界才算真懂。

**MoE 的边界**：占优在「需要大容量、但每 token 算力预算紧」——用低激活参换低成本（DSV3 671B 总参、37B 激活）。反转在「模型本就小、或无法承担专家并行的通信与显存」——小模型上 MoE 的路由开销占比过高，得不偿失；此外 MoE 的显存要装全部专家（总参大），若显存是硬约束，稠密或 SSM 更稳。工程代价还包括路由不均衡、专家并行的 all-to-all 通信（M3/M4）。

**SSM 的边界**：占优在「超长上下文、流式、显存敏感」——固定递推状态、O(1) 推理内存。反转在「需要精确检索远处 token 的强注意力任务」——纯 SSM 在需精确回指的检索上弱于注意力，需上混合架构；另外 SSM 生态与工具链不如 Transformer 成熟。

**扩散的边界**：占优在「局部编辑、填充、约束生成、任意顺序」——可控性主场（L54/L55）。反转在「纯低延迟逐 token 流式生成」——多步去噪的延迟与步数代价无谓付出，自回归更合适。

把边界写成「若……则选 X；若……则排除 X」的条件句，就是可执行的判据。

:::

### 常见误选：四种最容易踩的坑

即便懂了边界，实操仍常踩四类误选。

**误选一：用短文本基准推断长上下文能力。** MMLU、GSM8K 都是短文本，分数高不代表 32K 长文好用。必须用 needle-in-haystack、PG19 等长上下文基准（L61）单独测，否则会把 AR 的短文本优势误当成全场景优势。

**误选二：只看平均延迟、不看 P95。** 平均延迟低但长尾严重的架构，上线后用户投诉集中在慢请求上。选型承诺必须写 P95/P99。

**误选三：忽略架构的隐性工程代价。** MoE 的专家并行通信、扩散的多步调度、SSM 的算子生态成熟度——这些不在「质量分数」里，却决定项目能否按时跑通。矩阵的质量维度高，不等于落地成本低。

**误选四：把「能力展示」当「产品就绪」。** L51 讲过，扩散谱系不少模块是展示型（验证范式可行），不等于产品化最优。别因为「某扩散模型能做酷炫编辑」就选它，要看它在你的约束下是否真的达标。

### 可跑代码：把约束翻译成判据并自动筛选

把上面的翻译与边界写成可跑的筛选器：输入约束，输出合格架构，并给出淘汰理由。

```python
# 约束（贯穿场景）：32K 上下文、P95 延迟紧、需局部编辑、显存 24GB
constraints = {
    "max_seq": 32768,
    "p95_latency_ms": 120,
    "need_edit": True,
    "gpu_gb": 24,
}

# 各架构在该约束下的能力估计（示意；真实值来自 L57 成本模型与 L58 实测）
arch_spec = {
    "自回归AR": {"p95": 95, "kv_gb_32k": 18, "edit": False, "long_ok": False},
    "MoE":      {"p95": 70, "kv_gb_32k": 18, "edit": False, "long_ok": False},
    "SSM":      {"p95": 45, "kv_gb_32k": 2,  "edit": False, "long_ok": True},
    "扩散":     {"p95": 210, "kv_gb_32k": 22, "edit": True,  "long_ok": False},
}

def screen(constraints, specs):
    passed, rejected = [], {}
    for arch, s in specs.items():
        reasons = []
        if s["p95"] > constraints["p95_latency_ms"]:
            reasons.append(f"P95 {s['p95']}>{constraints['p95_latency_ms']}ms")
        if constraints["need_edit"] and not s["edit"]:
            reasons.append("不支持局部编辑（需求硬开关）")
        if s["kv_gb_32k"] > constraints["gpu_gb"]:
            reasons.append(f"32K KV {s['kv_gb_32k']}GB>显存")
        if reasons:
            rejected[arch] = reasons
        else:
            passed.append(arch)
    return passed, rejected

ok, no = screen(constraints, arch_spec)
print("合格架构:", ok)
for arch, why in no.items():
    print(f"淘汰 {arch}: {'; '.join(why)}")
assert "扩散" in no, "扩散应因 P95 延迟过高被淘汰"
```

```python
# 若把「需要编辑」设为 False、P95 放宽到 240ms，扩散重新进入候选
relaxed = dict(constraints, need_edit=False, p95_latency_ms=240)
ok2, no2 = screen(relaxed, arch_spec)
print("\n放宽后合格架构:", ok2)
assert "扩散" in ok2, "需求变化后扩散应进入候选"
# 结论：推荐随约束变化而反转——这就是「有依据的推荐」必须写边界的原因
```

第一段把四类约束变成可执行的淘汰规则：P95 超上限淘汰、需求硬开关（需编辑但不支持）淘汰、KV 超显存淘汰。在这个贯穿场景里，扩散因 P95 过高（210 大于 120ms）被淘汰，AR/MoE 因不支持编辑被淘汰，SSM 胜出。第二段把约束一放松，候选立刻变化——这正说明推荐不是绝对的，而是约束的函数，所以报告必须写明「在什么约束下推荐谁、约束变了会怎样」。注意所有数值是示意，真实值由 L57 成本模型和 L58 实测填入。

### 权重敏感性：推荐到底有多稳

一份推荐若对权重极度敏感（权重微调就换冠军），说明决策不可靠，必须显式检查。做法是让每个维度权重在上下一个区间内扰动，统计每个架构「夺冠」的频率——频率高的推荐更稳健。

```python
import random
random.seed(0)

def rank_first(scores, weights):
    """返回加权第一名的架构名。"""
    return max(scores, key=lambda a: sum(v*w for v, w in zip(scores[a], weights)))

# 以「知识问答」权重为中心做扰动
base = [5, 2, 3, 1, 1]
scores5 = {
    "自回归AR": [5, 3, 4, 3, 2],
    "MoE":      [5, 4, 5, 3, 2],
    "SSM":      [3, 4, 5, 5, 2],
    "扩散":     [4, 3, 2, 2, 5],
}
wins = {a: 0 for a in scores5}
for _ in range(1000):
    w = [max(1, x + random.randint(-1, 1)) for x in base]
    wins[rank_first(scores5, w)] += 1
print("知识问答权重扰动下的夺冠次数:", wins)
assert max(wins, key=wins.get) in ("自回归AR", "MoE"), "质量主导场景应由 AR/MoE 夺冠"
print("推荐稳健性检查通过：AR/MoE 在质量权重扰动下稳定领先")
```

这段把「推荐有多稳」量化：1000 次权重扰动里谁夺冠次数多，谁的推荐就稳。若结果显示两个架构各赢一半，就该如实告诉决策者「这两者在该场景下接近」，而不是武断选一个——这本身就是有依据的推荐的一部分。

### 产出有依据的推荐

一份合格的选型推荐至少含三块：① **约束清单**（量化阈值）；② **筛选过程**（谁因哪个阈值出局）；③ **边界与反例**（约束变化时推荐如何反转）。以上面的场景为例，推荐 SSM/混合架构，理由是：需 32K 长上下文（SSM 的 O(1) KV 优势）、P95 紧（SSM 递推快）、24GB 显存装得下；淘汰扩散是因为编辑需求虽被识别，但其 P95 延迟超标——若产品能接受 240ms 尾延迟，编辑需求就让扩散重新进入候选。这种「带着边界的推荐」比一句「选 SSM」有价值得多：它告诉决策者结论的成立条件，以及条件变化时该怎么办。到 L57 会把这里的延迟/显存估计换成严格的成本模型，L58 用实测数据填格子，L59 把这些拼成完整的决策报告。

:::tip

### 收束：选型 = 约束量化 + 边界写明

把真实约束翻译成可量化阈值（P95 延迟、$/token、KV 显存、上下文长、编辑开关），代入五维矩阵筛选，淘汰理由逐条写明。MoE 赢在「大容量低激活参」但付工程复杂度，SSM 赢在长上下文但精确检索需混合，扩散赢在可控性但延迟是代价。记住四类的反转条件，别用短文本基准评长上下文、别只看平均延迟。推荐必须带边界——因为它只是约束的函数，约束变了结论就会变。下一步 L57 建立成本模型，把这些量化判据算得更准。

:::
