### 从 FFN 的「全激活」说起

要理解 MoE 为什么出现，先看 Transformer 层里那个最「老实」的模块——前馈网络 FFN。在 L11 的谱系里，每个 Transformer 块都由一层注意力和一层 FFN 组成，FFN 通常是「升维到 4 倍隐藏维、过激活、再降回」的两层感知机。它的一个根本特点是**对所有 token 一视同仁地全量激活**：不论输入是一个常见标点、一个高频虚词，还是一个罕见的专业术语，都要经过同一份完整权重、消耗同样的乘加运算。这意味着 FFN 的参数量、显存占用、计算量三者是严格绑定的——想让模型「知道得更多」就得把 FFN 加宽，而加宽直接按比例推高每个 token 的 FLOPs。

这种绑定在稠密模型时代尚可接受，但当模型规模冲向千亿、万亿参数时，就撞上一堵墙：训练与推理的计算预算是有限的，不可能让每个 token 都穿过一个越来越庞大的 FFN。于是研究者提出一个朴素而关键的问题——**能不能让不同 token 走不同的计算路径，只激活与该 token 相关的那一小部分参数？** 这就是条件计算（conditional computation）的思想，也是整个 MoE 家族的源头。把 FFN 从「所有 token 共用的一份稠密网络」改造成「一组专家 FFN 加一个负责分配的门控」，每个 token 只被送到少数几个专家手里，模型总容量可以大幅增长，而单个 token 实际消耗的计算保持在一个小模型的水平。

### Shazeer 2017：把 FFN 换成专家库加门控

稀疏门控 MoE 的严格起点是 Shazeer 等人在 2017 年的工作《Outrageously Large Neural Networks: The Sparsely-Gated Mixture-of-Experts Layer》（arXiv:1701.06538，ICLR 2017）。它的改造非常清晰：把 LSTM/Transformer 层里那一个 FFN，替换成一个**由 N 个专家 FFN 组成的专家库**，再加一个**门控网络（gating network，也叫 router）**。门控网络对每个输入 token 的隐藏向量 x 做一次线性打分，得到 N 个专家的分数，取分数最高的 top-k 个（论文里 k 远小于 N，常见 k 取 2 到 4），把这 k 个分数做 softmax 归一化得到门控权重，最终输出是这 k 个专家输出按门控权重的加权和：

y = sum_i G(x)_i · E_i(x)，其中只有 top-k 个 G(x)_i 非零。

这里两个设计缺一不可。第一，**专家库提供容量**：N 个独立 FFN 各占一份权重，模型总参数量近似随 N 线性增长，知识被分散存储在不同专家里。第二，**门控提供稀疏性**：G(x) 中只有 k 个非零项，未被选中的专家这次前向完全不参与计算，梯度也不更新（或其专家权重梯度为零）。于是「专家库」负责把蛋糕做大，「门控」负责让每次只吃一小块——两者配合才实现了「总参数暴涨、单 token 计算基本不变」的魔术。论文在语言建模与机器翻译上把参数量推到当时难以企及的规模，同时保持每 token 的计算量可控，第一次展示了稀疏门控的可行性。

值得注意的是，Shazeer 的原始实现为了保证每个专家都被用到，引入了一个额外的**噪声项与负载均衡损失**（在专家分数上加高斯噪声、并对专家使用不均衡施加惩罚）。这已埋下后续整条「负载均衡」主线的伏笔——门控若放任自流，会迅速塌缩到总是选同几个专家，其余专家永远学不到东西。这个问题将在 L30 系统展开。

:::deep

### 门控加权和的数学拆解与 Top-k 的意义

把前向公式再拆细一点，能看清稀疏性到底省在哪一步。设隐藏向量维度为 d，专家数 N，每个专家是一个 d 到 4d 再到 d 的两层 FFN。门控是一个 d 到 N 的线性层 W_g：对 token x，先算 logits = W_g · x（N 维），再用 top-k 选出最大的 k 个索引 S，对 S 内的 logits 做 softmax 得到归一化权重 G_i，最终 y = sum_{i in S} G_i · E_i(x)。

关键在于**计算量的分水岭**：一个专家 FFN 的乘加量约为 d 乘 4d 乘 2 等于 8d²（忽略偏置），k 个专家就是 8kd²；而如果是一个「融合」了 N 个专家的稠密 FFN，计算量是 8Nd²。当 N 取 8、k 取 2 时，稀疏路由的专家计算量只有稠密的 2/8 等于 1/4（门控本身 d 乘 N 的开销极小，可忽略）。这就是 top-k 的全部意义——**用一个几乎免费的路由器，换取只对 1/4（乃至更小比例）的专家做昂贵的 FFN 计算**。top-k 越小省得越多，但可承载的容量与路由表达力也越弱，这是 L29 要仔细权衡的旋钮。

:::

### 可跑代码：稀疏路由如何「大参数、小计算」

下面用 NumPy 写一个最小稀疏门控层，把「总参数随专家数增长、每 token 计算随 top-k 增长」这件事量化出来。代码里显式数出两种口径的参数量与专家乘加量，并断言稀疏层的每 token 专家 FLOPs 远小于稠密融合层。

```python
import numpy as np

rng = np.random.default_rng(0)
d, E, k, T = 16, 8, 2, 5          # 隐藏维、专家数、每 token 选 2、5 个 token
# 专家权重：E 个 d->4d->d 的两层，总参数随 E 线性增长
W1 = rng.standard_normal((E, d, 4*d)).astype('float32')
W2 = rng.standard_normal((E, 4*d, d)).astype('float32')
Wg = rng.standard_normal((d, E)).astype('float32')   # 门控 d->E

def gelu(z):
    return 0.5 * z * (1 + np.tanh(np.sqrt(2/np.pi) * (z + 0.044715*z**3)))

def sparse_moe_forward(x):
    logits = x @ Wg                       # [T, E] 打分
    top = np.argpartition(-logits, k, axis=1)[:, :k]   # 每 token 的 top-k 索引
    weights = np.take_along_axis(logits, top, axis=1)
    weights = np.exp(weights - weights.max(axis=1, keepdims=True))
    weights = weights / weights.sum(axis=1, keepdims=True)   # 门控归一
    out = np.zeros_like(x)
    for t in range(x.shape[0]):
        for j, e in enumerate(top[t]):
            h = gelu(x[t] @ W1[e])
            out[t] += weights[t, j] * (h @ W2[e])       # 只算被选中的 k 个专家
    return out, top, weights

x = rng.standard_normal((T, d)).astype('float32')
y, top, w = sparse_moe_forward(x)
total_params = W1.size + W2.size + Wg.size
active_expert_params = k * (d*4*d + 4*d*d)      # 每 token 只激活 k 个专家
dense_fused_params = E * (d*4*d + 4*d*d)         # 若做成稠密融合 FFN
print(f"输出 shape={y.shape}, 每 token 选中专家={top[0].tolist()}, 门控权重和={w[0].sum():.4f}")
print(f"总专家参数={total_params}, 每 token 激活专家参数={active_expert_params}, 稠密融合={dense_fused_params}")
assert abs(w.sum(axis=1) - 1).max() < 1e-6, "门控权重必须逐 token 归一"
assert active_expert_params < dense_fused_params, "稀疏激活参数应远小于稠密融合"
print(f"激活占比={active_expert_params/dense_fused_params:.0%}（k/E={k/E:.0%}）")
```

代码里三个数字最关键：`total_params` 随 E 增长（专家库做大容量）、`active_expert_params` 只乘 k（每 token 计算被门控限制）、激活占比正好是 k 除以 E。断言 `w.sum(axis=1)` 约等于 1 钉死了门控权重逐 token 归一这条性质——它保证加权和不会因权重缩放而放大或缩小输出尺度，是训练稳定的前提。

### 为什么容量跟内存走，而不是跟 FLOPs 走

把上面的账推广到真实规模，就能理解本课标题那句「容量随内存增长而非随 FLOPs」。所谓**容量**，指模型能存储与记忆的知识总量，主要由可训练参数的数量决定；而每处理一个 token 的**计算成本（FLOPs）**，由该 token 实际穿过的乘加运算量决定。稠密模型里这两个量被一根等号锁死：参数翻倍，每个 token 的 FLOPs 也翻倍。MoE 用门控把这根等号剪断了。

具体来说，专家参数无论有没有被选中，都必须常驻 GPU 显存——你在代码里创建的 W1、W2 是完整的 E 个专家，一块都不会少。所以**总参数量、模型权重占用的显存、可存储的容量，三者同步随专家数 E 增长**。但前向时每个 token 只碰 k 个专家，FLOPs 约等于一个「k 倍专家大小」的小模型，与 E 几乎无关（门控打分那点 d 乘 E 的开销可忽略）。结果就是一条反直觉但极其重要的曲线：**横轴加专家，显存占用与知识容量一路上扬，单 token FLOPs 却基本水平**。这正是「用内存换容量、不换计算」的本质。

工程含义非常直接：如果你受限于显存，MoE 会把这个限制放大（要装下所有专家）；如果你受限于计算预算（训练/推理的卡时），MoE 是天赐的——同样的卡时能训练一个总参数量大得多的模型。这也是为什么近年的大模型几乎集体转向稀疏 MoE：在算力墙面前，它是继续扩大容量最经济的路径。

:::warn

### 「省计算」不等于「省显存」

这是新手最容易踩的认知坑：看到 MoE「每 token 只算 2 个专家」，就以为模型很省资源。实际上 MoE **极耗显存**——全部专家权重都得装进显存（或做专家卸载），只是**省 FLOPs**。Mixtral 8x7B 总参数 46.7B、每 token 只激活约 12.9B（A 级数字），它的显存占用接近一个 47B 稠密模型，但推理 FLOPs 只接近 13B 稠密模型。所以部署 MoE 的第一道门槛往往是「显存放不放得下所有专家」，而不是「算力够不够」。后面 L32 的专家并行、L28 的激活参占比账，都是围绕这条约束展开的工程解法。

:::

### GShard / Switch / GLaM：稀疏门控的谱系

Shazeer 2017 点燃火种之后，这条主线沿着几条清晰的脉络演进，把它们排成谱系能看清每一步在解决什么问题：

- **GShard（Google，arXiv:2006.16668）**：把稀疏门控 MoE 真正扩展到超大规模多语言模型（600B 级）。它最重要的贡献是**专家并行（expert parallel）**——把不同专家切分到不同设备上，配合 all-to-all 通信把 token 分发给对应专家（L32 详述）。它用 top-2 门控并引入辅助负载均衡损失，把「MoE 能大规模训练」这件事工程化落地。
- **Switch Transformer（Google，arXiv:2101.03961）**：做了一次关键的极简化——**top-1 路由**，每个 token 只送一个专家。论文发现 top-1 在把路由计算与通信减半的同时，质量不降反升，并简化了负载均衡。它把「top-k 的 k 该取多少」这个问题推向极致（k=1），也推动 MoE 进入 T5 系主干。
- **GLaM（Google，arXiv:2112.06905）**：把规模推到 1.2T 总参数，但每 token 只激活约 8% 到 9% 的参数（约 97B 激活）。它最响亮的结论是：**这样一个稀疏模型，用不到 GPT-3 一半的训练算力，在多项任务上超过 GPT-3（175B 稠密）**——这是「稀疏激活与总参数量分离」最有说服力的实证，也是「身份证号记账法」的来源（L28 展开）。

把三者与源头连起来看：Shazeer 提出机制，GShard 解决「怎么扩展到分布式」，Switch 回答「k 取 1 就够」，GLaM 证明「稀疏模型能用小算力胜过大稠密模型」。这条谱系一路通向 L33 要对照的 Mixtral 8x7B 与 DeepSeek-V3——它们都是这条树上结出的果实。

再用一段数值自检把「加专家只增总参、不增单 token FLOPs」钉死。下面固定每 token 选 k 个专家，让专家数 E 从 4 增到 64，看总参数一路上扬而单 token 的专家 FLOPs 保持不变。

```python
d, k = 8, 2                       # 隐藏维、每 token 选 2 个专家
flops_per_expert = 8 * d * d      # 一个 d->4d->d 专家的乘加量
for E in (4, 8, 16, 32, 64):
    total_params = E * flops_per_expert
    active_flops = k * flops_per_expert
    print(f"E={E:2d}: 总专家参数={total_params:5d}, 单token专家FLOPs={active_flops}")
# 单 token FLOPs 恒为 k×8d²，与 E 无关 → 容量随内存涨、计算不涨
assert k * flops_per_expert == 2 * 8 * d * d
assert 64 * flops_per_expert > 4 * flops_per_expert, "总参数应随专家数增长"
print("结论：加专家把总参数做大的同时，单 token 计算量保持恒定")
```

:::tip

### 一句话记住 MoE 的分工

**专家库负责「记多少」，门控负责「算多少」。** 总参数（专家数）决定容量与显存，门控的 top-k 决定每 token 的 FLOPs。Shazeer 2017 把这两件事拆开，GShard/Switch/GLaM 把它做大做稳做省。抓住这条主线，后面所有 MoE 细节——top-k 取舍、负载均衡、专家并行、共享专家——都是在回答「如何让这个分工更高效、更稳定」。

:::
