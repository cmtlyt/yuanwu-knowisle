### 场景：把「能跑」变成「跑得快且稳」

L108 起了服务、做了冒烟，但「能返回」不等于「服务得好」。生产部署要回答量化的问题：给定一张卡，能扛多少并发？P99 延迟能不能压到红线内？加卡之后吞吐是否线性增长？本课把吞吐调优拆成**三旋钮**（batch、并发、流式），给出固定并发的 P95/P99 压测脚本，并把多节点与 M7 的 3D 并行挂接进来，最终产出一份**可复现**的压测脚本。这一课的交付物是一份别人拿去能复现的压测报告，而不是一次性的调参记录。所谓可复现，至少包含三层：脚本本身可跑（不依赖本地临时环境）、变量被显式记录（语料、并发、输出长度、采样参数、版本），数字能被第三方在同等条件下重现。很多团队的性能结论最后无法复用，根因就是压测时没固定变量——换了语料长度分布，吞吐数字就变了，却误以为是某个旋钮的功劳。

:::deep

### 吞吐与延迟是一对矛盾，不是两个独立目标

新手常以为「吞吐和延迟都越高越好」，但二者由同一份算力竞争，存在根本张力：并发越高，GPU 被喂得越满，**总吞吐**上升；但每个请求分到的算力越少，**单请求延迟**上升。同理，batch 越大矩阵乘越高效（吞吐↑），但排队时间变长（延迟↑）。因此调优不是「把每个旋钮拧到最大」，而是在**吞吐目标**与**延迟红线**之间找最优点。压测的目的正是画出这条曲线：固定其他条件、扫并发数，记录每个档位的吞吐与 P99，选「P99 不越线前提下吞吐最高」的那档。

:::

### 三旋钮：batch、并发、流式

**旋钮一：batch（`max_num_batched_tokens`）**——单步优化喂给模型的 token 上限。调大能拼出更大的矩阵乘、吃满 Tensor Core，但增加单步计算时间。长 prompt 场景还要配合 chunked prefill（L22）避免霸占。

**旋钮二：并发（`max_num_seqs`）**——同时活跃的序列数。并发是吞吐的直接来源（L24 的因子 A），但受 KV 显存约束，且超过最优点后 P99 恶化。

**旋钮三：流式（`stream`）**——逐 token 返回。它不直接改变总吞吐，却把**首 token 延迟**从「等整条生成完」降到「第一个 token 就算完就返回」，主观体验提升巨大。

三旋钮之间还有耦合：并发调大后，若 `max_num_batched_tokens` 没跟上，调度器拼不出大 batch，吞吐仍上不去；反过来 batch 调到很大但并发太低，GPU 在等待新请求时闲置。因此扫参应当**成对扫描**——固定并发扫 batch，再固定最优 batch 扫并发，而不是一次只动一个却期望线性收益。流式开关主要影响体验指标（首 token 延迟），对总吞吐影响很小，生产环境一般默认开，只在极端吞吐优先的批处理任务里关掉。

下面把三旋钮写成一个可调配置，强调各自的方向与代价。

```python
from dataclasses import dataclass

@dataclass
class ServingConfig:
    max_num_seqs: int = 16                # 旋钮1：最大并发序列数
    max_num_batched_tokens: int = 4096    # 旋钮2：单步 batch token 上限
    stream: bool = True                   # 旋钮3：流式输出

def describe(cfg):
    return (f"并发上限={cfg.max_num_seqs}, 单步token上限={cfg.max_num_batched_tokens}, "
            f"流式={'开' if cfg.stream else '关'}")

base = ServingConfig()
tuned = ServingConfig(max_num_seqs=64, max_num_batched_tokens=8192, stream=True)
print("基线:", describe(base))
print("调优:", describe(tuned))
assert tuned.max_num_seqs > base.max_num_seqs, "并发应可调大"
assert tuned.max_num_batched_tokens > base.max_num_batched_tokens
print("判据：并发↑吃满算力但单请求延迟↑；stream 改善首 token 延迟体验")
```

### 固定并发压测：P50/P95/P99 与吞吐

压测的标准做法：**固定语料、固定输出长度、固定采样参数、扫并发数**。每组并发跑足够多请求（如 1000 条），记录每条延迟，算 P50/P95/P99，并用总 token 数除以 wall clock 得吞吐。下面是一段**可复现**的压测脚本骨架（示意数据，实测把 `latency_ms` 换成你测到的真实延迟）。

```python
import random
random.seed(0)

def percentile(xs, p):
    ys = sorted(xs)
    i = min(len(ys) - 1, int(len(ys) * p))
    return ys[i]

def load_test(n_requests, latency_ms, output_tokens, concurrency):
    """固定并发压测：返回吞吐与延迟分位数。"""
    latencies = [random.choice(latency_ms) for _ in range(n_requests)]
    total_tokens = n_requests * output_tokens
    wall_ms = sum(latencies) / concurrency        # 并发摊薄 wall time
    tput = total_tokens / (wall_ms / 1000.0)
    return {
        "吞吐tok/s": round(tput),
        "P50": percentile(latencies, 0.50),
        "P95": percentile(latencies, 0.95),
        "P99": percentile(latencies, 0.99),
    }

lat = [45, 52, 61, 70, 88, 120, 200]   # 单请求延迟样本(ms，量级示意)
r = load_test(1000, lat, output_tokens=200, concurrency=16)
print("固定并发压测结果:", r)
assert r["P50"] <= r["P95"] <= r["P99"], "分位数应单调递增"
assert r["吞吐tok/s"] > 0, "吞吐应为正"
print("判据：P99 是长尾体验红线；吞吐看总 tokens/s，二者需同时达标")
```

读结果的正确姿势：P50 看典型体验、P95/P99 看长尾、吞吐看整体产能。**P99 是 Hard 约束**——哪怕吞吐再高，P99 超过红线（如 2 秒）就意味着部分用户经常等到崩溃，必须降并发或优化。扫多条并发曲线后，把「吞吐 vs P99」画成图，拐点就是最优并发档。

### 多节点与 3D 并行：挂接 M7

单卡放不下或吞吐不够时，用 M7 讲过的 **3D 并行**（TP × PP × DP）把模型铺到多卡多节点：

- **TP（张量并行）**：把单层权重切到多卡，每层都要 AllReduce，通信频繁——**限制在节点内**走 NVLink。
- **PP（流水线并行）**：按层切分到不同卡，通信量小——**适合跨节点**，但受网络带宽影响。
- **DP（数据并行）**：复制模型、切分数据，主要扩吞吐。

三者的乘积必须等于总卡数。下面把并行规划写成可跑的校验脚本。

```python
# 多节点/3D 并行规划（挂接 M7）
def parallel_plan(world_size, tp, pp, dp=None):
    dp = dp or world_size // (tp * pp)
    assert tp * pp * dp == world_size, "TP×PP×DP 必须等于总卡数"
    return {"TP": tp, "PP": pp, "DP": dp, "总卡数": world_size}

for ws, tp, pp in [(8, 8, 1), (8, 4, 2), (64, 8, 4)]:
    plan = parallel_plan(ws, tp, pp)
    print(f"world={ws:2d} -> TP={plan['TP']} PP={plan['PP']} DP={plan['DP']}")

plan = parallel_plan(64, 8, 4)
assert plan["TP"] * plan["PP"] * plan["DP"] == 64
print("经验：TP 放节点内走 NVLink，PP 跨节点需高速网络；通信是扩展瓶颈")
```

关键判据：**TP 不要跨节点**。跨节点 AllReduce 走以太网/InfiniBand，带宽远低于 NVLink，TP 的频繁通信会被网络卡死，加卡反而不提速。正确布局是「节点内 TP、节点间 PP」，DP 在最外层。扩展前先测节点间带宽——网络往往才是真正的天花板。

跨节点还要考虑并行策略与 KV 的交互：TP 把权重切开的同时也把 KV 头切到各卡，PP 则按层分布 KV；并行度越高，单卡持有的 KV 越少，但通信开销越大。实际部署要先算出「模型权重 + KV 预算 + 激活缓冲」能否放进单卡显存，再决定是否需要并行——能单卡装下就别急着上多卡，通信成本往往吃掉并行收益。判断依据是 L21/L24 的 KV 账：把目标并发下的 KV 总量算出来，与剩余显存比较，缺口才用并行去补。

**可复现的压测纪律**

压测数字要能横向对比，必须固定并记录这些变量：① 语料（prompt 长度分布，长短混合）；② 输出长度上限；③ 采样参数（temperature、top-p，建议固定为贪心便于复现）；④ 并发档位；⑤ 硬件型号、GPU 数量、框架与 CUDA 版本；⑥ 量化档位与 engine 构建参数（L107）。任何一项变化都可能改变结论。把这份「实验卡」与压测脚本一起归档，别人才能复现你的数字——否则「我调大 batch 吞吐涨了 30%」这种话无法验证，可能是语料变了或框架升级了。压测本身也要跑够时长：几十个请求的结果噪声极大，一个偶发的 GC 或调度抖动就能把 P99 拉偏；至少跑几百到几千请求、持续几分钟，让系统进入稳态后再取数。报告里同时给出均值与中位数也有帮助——若两者差距很大，说明延迟分布长尾严重，此时更要盯 P99 而不是被平均值迷惑。最后，压测结论要写成「在某硬件、某版本、某语料下，并发 X 档吞吐 Y tok/s 且 P99 为 Z」的完整句式，而不是孤零零一个数字；缺了限定条件的吞吐值在决策会上没有任何意义，换个环境就失效。把这份句式连同实验卡一起归档，才算真正交付了可复现的压测。

:::tip

### 调优口诀

三旋钮各管一事：batch 拼大矩阵吃满算力、并发吃满 KV 预算换吞吐、流式改善首 token 体验。调优是在「吞吐 vs P99 红线」间找拐点，不是把旋钮拧到最大。多节点按「节点内 TP、节点间 PP」布局，先测网络带宽再谈加卡。压测必须固定语料、并发、输出长度、采样参数与版本记录，数字才可复现。下一课 L111 把这条链路彻底收口：从 LoRA 合并到导出量化、vLLM 起服务、API 冒烟、吞吐与精度验收，串成端到端 capstone。
