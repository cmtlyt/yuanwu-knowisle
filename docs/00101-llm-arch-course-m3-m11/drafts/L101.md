### 场景：把对齐从论文落到一条训练命令

前面几课讲的是对齐的「是什么」与「为什么」，这一课解决「怎么跑起来」。HF 生态的 `trl` 库把 SFT、DPO、GRPO 三种训练封装成统一接口：`SFTTrainer`、`DPOTrainer`、`GRPOTrainer`。三者共享同一套配置习惯（Config 对象 + Dataset + `peft_config`），连 checkpoint 的存取格式都一致，但**优化目标与数据流完全不同**：SFT 吃单条示范，DPO 吃偏好三元组，GRPO 吃 prompt + 奖励函数并在线采样。本场景按「搭环境 → 备数据 → 三种 Trainer 各跑通 → 对照稳定性」顺序走一遍。

:::deep

### 三种 Trainer 的分工：别把它们当成同一个东西的换名

- **SFTTrainer**：监督式 next-token 训练。输入 `prompt + completion`，目标是最大化示范回答的似然。它是对齐的**起点**（产出 π_SFT 与参考模型），本身不做偏好学习。
- **DPOTrainer**：离线偏好学习（L98）。输入 `prompt/chosen/rejected`，不训 RM、不在线采样，直接算 `log(π_θ/π_ref)` 的隐式奖励差做二分类损失。它需要**参考模型**（可由 trainer 自动持有）。
- **GRPOTrainer**：在线强化学习（L99）。输入 prompt 与奖励函数，每个 prompt 采样 `num_generations` 个回答，用组内相对奖励估优势更新策略。它不需要 RM 训练（奖励可来自函数/规则），但需要在线生成。

一句话区分数据流：**SFT 看一条，DPO 看一对，GRPO 看一组**。选错 Trainer 等于把数据形态和目标函数配错，训练必然不对。

:::

**环境与偏好对数据准备**

先装依赖并准备数据。偏好对数据的最小契约是每条样本含 `prompt`、`chosen`、`rejected` 三列，通常用 `datasets.Dataset` 承载。

```python
# 依赖：pip install trl peft transformers datasets torch
from datasets import Dataset
from trl import SFTTrainer, SFTConfig
from peft import LoraConfig

rows = [
    {"prompt": "解释过拟合", "chosen": "过拟合是模型记住训练噪声、泛化变差，可用正则化和早停缓解。", "rejected": "就是模型很差"},
    {"prompt": "如何写冒泡排序", "chosen": "冒泡排序相邻比较交换，每轮把最大值浮到末尾，复杂度 O(n²)。", "rejected": "不知道"},
    {"prompt": "什么是 KL 散度", "chosen": "KL 散度度量两个概率分布的差异，非对称且非负。", "rejected": "一个数学词"},
]
ds = Dataset.from_list(rows)
print("偏好对条数:", len(ds), "字段:", ds.column_names)
assert "chosen" in ds.column_names and "rejected" in ds.column_names
assert len(ds) == 3

peft_config = LoraConfig(
    r=16, lora_alpha=32, lora_dropout=0.05,
    target_modules=["q_proj", "v_proj"], task_type="CAUSAL_LM",
)
sft_cfg = SFTConfig(
    output_dir="./sft-out", max_length=512, num_train_epochs=1,
    per_device_train_batch_size=2, learning_rate=2e-4, logging_steps=1,
)
# trainer = SFTTrainer(model=model, args=sft_cfg, train_dataset=ds, peft_config=peft_config)
# trainer.train()
print("SFTTrainer 配置就绪: r=16, max_length=512, lr=2e-4")
```

`peft_config=LoraConfig(...)` 是三者共用的省显存开关：只训 `q_proj/v_proj` 上的低秩增量（r=16），基座权重冻结。对一张 24GB 卡，这意味着你能把「一份全量模型 + 优化器状态」的显存，换成「冻结基座 + 极少量 LoRA 参数」，从而塞下更长的序列与更大的 batch。

数据准备阶段最容易被低估的是**质量清洗**：偏好对里如果混进「chosen 其实更差」的标注噪声，DPO 会直接把错误信号学进去（L98 的软肋）。上线前至少做三件事：① 去重与长度过滤，剔除超长或空回答；② 抽检一致性，让两个标注员对同一批对子独立判断，一致率过低的批次返工；③ 检查 chosen 与 rejected 的长度分布是否失衡——若 chosen 系统性更长，模型会学到「长即好」的长度偏置，需在损失里做长度归一化或在数据端配平。这三步做完，再进入 Trainer 才有意义。

### DPOTrainer：偏好对直接进损失

DPOTrainer 吃上面的偏好三元组。它内部对每条样本算 4 个 logprob（π_θ 与 π_ref 各对 chosen/rejected 一次），用 L98 推导出的隐式奖励差做损失。下面同时给出配置与一个**离线损失自检**，确认训练目标与理论一致。

```python
from trl import DPOTrainer, DPOConfig
from peft import LoraConfig
import math

dpo_cfg = DPOConfig(
    output_dir="./dpo-out", beta=0.1,
    max_length=512, max_prompt_length=256,
    num_train_epochs=1, per_device_train_batch_size=2,
    learning_rate=5e-7, logging_steps=1,
)
# trainer = DPOTrainer(
#     model=model, ref_model=None, args=dpo_cfg,
#     train_dataset=ds, peft_config=LoraConfig(
#         r=16, lora_alpha=32, target_modules=["q_proj", "v_proj"],
#         task_type="CAUSAL_LM"),
# )
# trainer.train()

def dpo_loss(pi_w, pi_l, ref_w, ref_l, beta=0.1):
    diff = beta * ((pi_w - ref_w) - (pi_l - ref_l))
    return -math.log(1.0 / (1.0 + math.exp(-diff)))

print("初始 DPO 损失:", round(dpo_loss(-1.0, -2.0, -1.2, -1.1), 4))
assert dpo_loss(-0.7, -2.8, -1.2, -1.1) < dpo_loss(-1.0, -2.0, -1.2, -1.1), "训练应降低 DPO 损失"
```

注意两个工程细节：① `ref_model=None` 时 TRL 会用当前模型副本作冻结参考，若你已用 LoRA，参考可直接用合并前的基座（见 L105 的 `merge_and_unload`）；② 学习率 `5e-7` 比 SFT 的 `2e-4` 小三个数量级——DPO 对 logprob 差极敏感，大学习率会几步就过拟合偏好集。

第三个细节是**参考模型的显存**：DPO 训练时 π_ref 必须驻留显存算两遍 logprob，若用 LoRA 可让参考方直接在冻结基座上跑、避免再加载一份副本；若用全量微调，则参考模型要独占一份权重，24GB 卡往往吃不消。β 与学习率的配合也值得单独扫一遍：固定 β=0.1 时先用 5e-7 跑通，观察 chosen/rejected 的隐式奖励差是否平稳上升；若 loss 几步归零且生成变得极端，立即降学习率或早停。把「偏好胜率上升且通用基准不掉」作为提前停止条件，比死磕固定 epoch 更靠谱。

### GRPOTrainer：在线采样 + 可验证奖励

GRPOTrainer 的数据形态又不同：只需 prompt 与一个奖励函数，不需要提前写 rejected。`num_generations=8` 即 L99 的组大小 G，每个 prompt 在线采样 8 条回答，用奖励函数的输出做组内相对优势。

```python
from trl import GRPOTrainer, GRPOConfig
from peft import LoraConfig
import statistics

def reward_correctness(completions, answer, **kwargs):
    # 可验证奖励：标准答案出现在回答里给 1 分，否则 0 分（示意）
    return [1.0 if a.strip() in c else 0.0 for c, a in zip(completions, answer)]

grpo_cfg = GRPOConfig(
    output_dir="./grpo-out", num_generations=8,
    max_prompt_length=256, max_completion_length=256,
    per_device_train_batch_size=2, learning_rate=1e-6,
    beta=0.04, logging_steps=1,
)
# grpo_ds = Dataset.from_list([
#     {"prompt": "1+1=?", "answer": "2"},
#     {"prompt": "法国的首都是?", "answer": "巴黎"},
# ])
# trainer = GRPOTrainer(
#     model=model, args=grpo_cfg, train_dataset=grpo_ds,
#     reward_funcs=[reward_correctness], peft_config=LoraConfig(
#         r=16, lora_alpha=32, target_modules=["q_proj", "v_proj"],
#         task_type="CAUSAL_LM"),
# )
# trainer.train()

rewards = [1.0, 0.0, 0.0, 0.5, 0.0, 1.0, 0.0, 1.0]   # 8 个 rollout 的奖励
mu, sd = statistics.mean(rewards), statistics.pstdev(rewards)
adv = [(r - mu) / (sd + 1e-8) for r in rewards]
print(f"G={len(rewards)} 组均值={mu:.3f} 组标准差={sd:.3f}")
print("组内相对优势:", [round(a, 2) for a in adv])
assert abs(sum(adv)) < 1e-6, "组内相对优势应近似零均值"
```

`beta=0.04` 是 GRPO 对参考策略的 KL 系数（L99），比 DPO 的 0.1 更低——在线方法本就有裁剪约束，KL 可以放松些。组内相对优势的零均值自检再次印证：奖励高于组均值的 rollout 被强化、低于的被抑制，无需 critic。

GRPO 的真正难点不在 Trainer 调用，而在**奖励函数设计**：奖励若有漏洞，在线采样会把漏洞放大到极致（策略专门钻空子）。数学题用标准答案匹配、代码用单元测试通过率是相对干净的奖励；开放式写作若用一个小 RM 打分，就要警惕 L96 的 Reward Hacking。另外 `num_generations` 别设太小——G=8 是常见的起点，G=2 时标准化噪声大、优势估计不稳；若显存不够，宁可减少 batch 也要保住组大小。在线生成的耗时也要算进预算：GRPO 每步要先生成 G 条回答再训练，wall-clock 通常比 DPO 慢数倍。

### 三种训练稳定性对照

把三者放在一起看「稳不稳、贵不贵、吃什么数据」：

- **SFT**：最稳，就是监督学习；不学偏好，产出对齐起点。
- **DPO**：稳定性中等，离线训练曲线可预测；但**对偏好数据质量与 β 敏感**，rejected 写得不好会把模型带偏，学习率必须极小。
- **GRPO**：在线采样带来探索能力，适合可验证奖励；但组内样本数、奖励函数设计、KL 系数都影响稳定性——组太小噪声大，奖励全对或全错则该组无梯度信号（L99 的 pitfall）。

一个实用的选择顺序：先用 SFTTrainer 跑出能听指令的基座 → 若有现成偏好对、追求稳定，用 DPOTrainer → 若任务奖励可自动验证（数学/代码）、且愿付在线采样成本，用 GRPOTrainer。三者可叠加：SFT 作起点，DPO 或 GRPO 作对齐阶段。

无论选哪条，训练过程都要挂**两类监控**：一类是对齐指标（偏好胜率、人评、奖励函数均值），另一类是通用基准（MMLU、GSM8K 等，见 L97）。只看第一类容易把 Reward Hacking 误当进步；只看第二类会漏掉行为退化。一个实用的节奏是每几百 step 做一次轻量抽测，发现「对齐升、基准掉」的剪刀差就降学习率或早停。三种 Trainer 都能用 `peft_config` 挂 LoRA，这意味着你可以在同一张卡上把「SFT → DPO → GRPO」三段串成一条流水线：SFT 得到基座与参考，DPO 用配对偏好快速对齐，GRPO 在可验证任务上再冲一把，每段结束都存一次 checkpoint（保存方法见 L105）。

:::tip

### 实操记忆口诀

SFT 看一条、DPO 看一对、GRPO 看一组。三者都用 `peft_config=LoraConfig()` 省显存，但 DPO 必须冻结参考模型、学习率要小两个数量级，GRPO 靠 `num_generations` 决定组内比较的可靠性。跑通后不要只看 loss 下降，按 L97 的方法抽测通用基准与偏好胜率，确认对齐没有以能力退化为代价。下一课 L102 把 DPO 的两种变体 IPO/KTO 拉进来对照，看它们怎么修补过拟合与标签成本。
