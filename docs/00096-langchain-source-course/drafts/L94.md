### 外部连接的第一课：把 MCP 服务器变成工具表

模块七的最后一课组讲外部世界：本课 MCP、下一课 provider 包与 Hub。MCP（Model Context Protocol）让外部进程暴露工具给 agent 用；适配器包 `@langchain/mcp-adapters` 的职责是把「MCP 语言」翻译成「langchain 工具语言」。核心结论：**loadMcpTools 把 listTools 的结果归一成 DynamicStructuredTool[]，ConnectionManager 用三传输重载与双 Map 保证连接的合法与复用——外部协议进内后，L21/L22 的全部工具机制原样生效**。practice 课型，边读边跑。

### 走读：loadMcpTools 与默认值的态度

```ts
// tools.ts
const defaultLoadMcpToolsOptions: LoadMcpToolsOptions = {
  throwOnLoadError: true,
  prefixToolNameWithServerName: false,
  additionalToolNamePrefix: "",
};

export async function loadMcpTools(
  serverName: string,
  client: MCPInstance,
  options?: LoadMcpToolsOptions
): Promise<DynamicStructuredTool[]> {
  const parsedOptions = loadMcpToolsOptionsSchema.parse(options ?? {});
  const { tools } = await client.listTools();
  return convertMcpTools(serverName, client, tools, parsedOptions);
}
```

*— langchain-mcp-adapters/src/tools.ts:470-492（commit 7704471）*

函数体三行：解析 options（Zod schema 兜底默认值）→ listTools 发现 → convertMcpTools 归一。**默认值组合值得停下来读**：`throwOnLoadError: true`——加载单个工具失败会抛错而不是跳过，宁可在启动期 fail fast 也不带着残缺工具表运行；但 `prefixToolNameWithServerName: false` 与空的前缀——多台服务器的工具名冲突框架不管。这个组合的态度是「**正确性（缺工具）框架兜底，命名空间（重名）用户负责**」。convertMcpTools（tools.ts:495-519）里前缀逻辑：`additionalToolNamePrefix` 变成 `xxx__` 前缀、服务器前缀变成 `server_` 前缀，拼接后统一挂在每个工具名前。多服务器接入的标准姿势：开服务器前缀，冲突自动消解。

归一过程的核心一步在 convertMcpTools 的 map 里：`JSONObjectSchema.parse(tool.inputSchema)` 校验 MCP 声明的 JSON Schema，再经 `jsonSchemaParser` 转成 Zod schema 喂给 DynamicStructuredTool——MCP 的输入校验直接复用 L21 的 Zod interop 校验双引擎，**外部工具与本地工具在参数校验层是同一套机制**。

### 走读：工具调用路径上的三道闸

归一后每次工具调用经过的工具函数（tools.ts:370-468）有三道闸值得逐个看：

```ts
// 闸一：elicitation 反问（可选）
const result = invocation.elicitation
  ? await callToolWithElicitation(round, prepared.request, serverName, toolName, config?.signal)
  : await round(prepared.request);

// 闸二：服务器要求用户输入但客户端没开 elicitation → 明确报错
if (isInputRequiredResult(result))
  throw new ToolException(
    `MCP tool "${toolName}" on server "${serverName}" asked for input, which only a modern server with elicitation enabled can answer`
  );

// 闸三：output schema 校验（仅成功结果）
if (invocation.output && !result.isError) {
  const parsed = await invocation.output.safeParseAsync(result);
  if (!parsed.success)
    throw new ToolException(
      `MCP tool "${toolName}" on server "${serverName}" returned output its schema rejects: ${z.prettifyError(parsed.error)}`
    );
}

// 闸四：afterToolCall 钩子拦截结果
const interceptedResult = toolCallResultModificationSchema.optional().parse(
  await afterToolCall?.({ name: toolName, args: finalArgs, result: [content, artifacts], serverName }, state, config ?? {})
);
if (!interceptedResult) return [content, artifacts];
if (Array.isArray(interceptedResult.result)) return interceptedResult.result;
return [interceptedResult.result, []];
```

*— langchain-mcp-adapters/src/tools.ts:380-455（commit 7704471，有裁剪）*

四道闸的语义：elicitation 让工具在执行中**向用户反问**（比如确认危险操作），客户端注册回调应答；`isInputRequiredResult` 检查是防御性的——注释说明 SDK 不会随意返回 input_required，但用户传入的 client 未必是 SDK 的，所以「收窄类型而不是强转」。output 校验**只对成功结果**执行（`!result.isError`），错误结果直接走 convertCallToolError 通道——工具自己报错是数据，不该被 schema 拒收（与 L13 的 status 错误即数据哲学一致）。afterToolCall 钩子让宿主应用在结果进入对话前做最后修改（脱敏、裁剪、缓存）。

外层还有统一的错误包装（tools.ts:456-467）：graph interrupt 与 abort 信号原样重抛（不包装），ToolException 原样重抛，其余一切错误包成 `Error calling tool ${toolName}: ...` 的 ToolException——**工具错误的类型边界清晰，middleware 的 toolError/toolRetry（L58）可以按类型分诊**。

两处容易漏看的工程细节。其一，output schema 的解析器是**惰性编译**的：`jsonSchemaParser` 返回 z.transform，内部 validator 在首次 parse 时才由 `fromJsonSchema` 构建（tools.ts:246-269）——注释明确这是刻意的：schema 非法时只炸它自己那台服务器的工具调用，**服务器发现（listTools）不受牵连**，一台坏服务器不会拖死多服务器启动。其二，闸门之前还有对称的 `beforeToolCall` 拦截（tools.ts:326-342）：宿主可以在请求发出前改写 args 甚至换 headers（headers 经 fork 连接实现，协议 era 不一致的 fork 会被拒绝）——before/after 一对钩子把「进与出」两个方向的宿主干预都收齐了。

### 走读：ConnectionManager 的三传输与双 Map

```ts
export interface Connection {
  transport: StreamableHTTPClientTransport | SSEClientTransport | StdioClientTransport;
  client: Client;
  transportOptions: ResolvedStdioConnection | ResolvedStreamableHTTPConnection | ResolvedSSEConnection;
}

export class ConnectionManager {
  #connections: Map<ClientKeyObject, Connection> = new Map();
  #pending = new Map<ClientKeyObject, Promise<Client>>();
  #closing?: Promise<void>;

  async createClient(type: "stdio", serverName: string, options: ResolvedStdioConnection): Promise<Client>;
  async createClient(type: "http",  serverName: string, options: ResolvedStreamableHTTPConnection): Promise<Client>;
  async createClient(type: "sse",   serverName: string, options: ResolvedSSEConnection): Promise<Client>;

  async createClient(...args): Promise<Client> {
    if (this.#closing) throw new Error("MCP connections are closing");
    const [type, serverName, options] = args;
    const key = this.identity(type === "stdio" ? { serverName } : { serverName, headers: options.headers, authProvider: options.authProvider });
    const existing = this.#connections.get(key)?.client;
    if (existing) return existing;
    const pending = this.#pending.get(key);
    if (pending) return pending;
    const acquisition = this.#connect(args, key);
    this.#pending.set(key, acquisition);
    try { return await acquisition; }
    finally { this.#pending.delete(key); }
  }
}
```

*— langchain-mcp-adapters/src/connection.ts:44-141（commit 7704471）*

三个设计点。其一，**三传输用重载签名声明**：`createClient("stdio", name, stdioOptions)`、`("http", name, httpOptions)`、`("sse", name, sseOptions)` 三个重载把 type 与 options 类型绑定在元组里——stdio 配 http 参数的非法组合**编译期**报错，运行时实现签名只是三个元组类型的 union。其二，**身份键**：ClientKeyObject 由 serverName + 序列化后的 headers + authProvider 构成（`identity()` 方法，connection.ts:70-91），注意 headers 先经 serializeHeaders 转字符串再比较——对象引用无关、内容相同即同一连接。其三，**双 Map 去重**：#connections 缓存完成的连接（直接命中返回），#pending 缓存「连接中的 Promise」——同 key 的并发请求返回**同一个** acquisition Promise，finally 清除。这是并发去重的教科书模式：缓存 promise 而不是结果值，天然解决「重复请求但结果还没好」的窗口期。

版本协商细节也在 #connect 里（connection.ts:163-180）：legacy 模式配 `versionNegotiation: { mode: "legacy" }`，注册了 onElicitation 时还声明 `capabilities: { elicitation: { form: {}, url: {} } }`；modern 模式 pin 到 `2026-07-28` 协议版本——**elicitation 能力需要在客户端能力表里主动声明**，不是默认开启。

### elicitation 深读：interrupt 底座与多轮应答循环

闸一里的 callToolWithElicitation 不是简单的回调注册，它有两个值得单独走读的设计。第一是**多轮应答循环**：`while (isInputRequiredResult(result))` 包住整个交互（elicitation.ts:270-302）——服务器每回答案不够就再发 input_requests，客户端先经 `answerableRequestsSchema` 校验（**零问题的应答直接拒绝**，注释原话：nothing can advance a response that asks nothing），再把合法问题交给 answerFor 取回应答，带上服务器给的 `requestState` 重新发起 round。整个循环退出条件只有一个：服务器不再要求输入。

第二是**实现底座就是 hitl 的 interrupt**。answerFor 里直接调 langgraph 的 `interrupt(question)`（elicitation.ts:223-260），注释把边界条件写得非常直白：interrupt 在图外、或编译时没配 checkpointer 的图里会**在挂起前就抛错**，这里统一转成 ToolException 提示「放进带 checkpointer 的 LangGraph 里调用 elicitation」。更硬核的是注释里的两个行为承诺：interrupt() 会让整个工具调用栈回卷，**resume 时工具从第一轮重新发起**，服务器靠 requestState 续接进度——「先干活后提问」的服务器每轮都会重复一次劳动，所以注释警告副作用必须幂等（elicitation.ts:265-268）；resume 传入的应答必须由 `createMCPElicitationResume()` 构造，并按 strictObject **逐键逐题**校验（245-259 行），格式不对的应答直接让调用失败而不是重新提问——因为执行 resume 的是代码，不是填表的人。

还有一个协议层细节：in-band 模式下客户端能力（`CLIENT_CAPABILITIES_META_KEY`）是**随每次工具请求的 `_meta` 广告**的，而不是在初始化时声明 capability（elicitation.ts:155-169）——注释解释：auto 连接的协议 era 要等协商结束才确定，初始化期广告会泄露给不该看到它的 legacy 服务器。elicitation 是否可用，取决于连接落在了 modern era。

### 实战：从零跑通一条 MCP 工具链

```ts
import { MultiServerMCPClient } from "@langchain/mcp-adapters";
import { createAgent } from "langchain";

// 1. 声明多服务器连接（三传输混配）
const mcpClient = new MultiServerMCPClient({
  // stdio：本地子进程传输
  filesystem: {
    transport: "stdio",
    command: "npx",
    args: ["-y", "@modelcontextprotocol/server-filesystem", "./data"],
  },
  // streamable http：远程传输
  weather: {
    transport: "http",
    url: "https://mcp.example.com/mcp",
    // headers: { Authorization: "Bearer ..." },
  },
});

// 2. 归一为 DynamicStructuredTool[]
const tools = await mcpClient.getTools();   // 内部走 loadMcpTools
console.log(tools.map((t) => t.name));

// 3. 接入 agent——外部工具从此与本地 tool() 无差别
const agent = createAgent({ model: "anthropic:claude-sonnet-4-5", tools });

const res = await agent.invoke(
  { messages: [{ role: "user", content: "列出 ./data 下的文件，并查一下北京今天的天气" }] },
);
console.log(res.messages.at(-1)?.content);

// 4. 连接复用验证：同一个 ConnectionManager，同配置并发两次
const [c1, c2] = await Promise.all([
  mcpClient.getConnection("filesystem"),   // 底层 createClient 去重
  mcpClient.getConnection("filesystem"),
]);
// c1 === c2：#pending 确保第二次等待的是同一个 acquisition Promise

// 5. 收尾：优雅关闭所有连接
await mcpClient.close();
```

验收断言五条：工具名列表包含两台服务器的全部工具（stdio 与 http 各自归一成功）；agent 能依次调用 filesystem 与 weather 工具并汇总回答（DynamicStructuredTool 与本地工具走同一执行路径）；并发 getConnection 返回同一 client 实例（双 Map 去重生效）；给 weather 配错 url 时启动期抛连接错误而非静默半可用（fail fast）；close() 后所有传输关闭、再次 getTools 抛 MCP connections are closing（#closing 闸门生效）。排查建议：工具没出现先查 throwOnLoadError 的报错；同名冲突用 `prefixToolNameWithServerName: true`；elicitation 不生效检查是否 legacy 模式且没注册 onElicitation 回调。

### 本课小结

- loadMcpTools：listTools → convertMcpTools → DynamicStructuredTool[]；JSON Schema 经 Zod parser 归一，校验机制与本地工具同源。
- 默认值态度：throwOnLoadError: true（缺工具即抛）+ 无前缀（命名冲突用户负责）；多服务器必开服务器前缀。
- 调用路径四道闸：elicitation 反问 → input_required 防御报错 → output schema 校验（仅成功结果）→ afterToolCall 拦截；错误统一 ToolException 且 interrupt/abort 原样穿透。
- ConnectionManager：三传输重载编译期防非法组合；identity 键 + #connections/#pending 双 Map 完成连接复用与并发去重。
