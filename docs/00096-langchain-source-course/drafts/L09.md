### 本课要打通的两条链路

L03/L08 反复说主包「唯二的新增面」：initChatModel 与 headless tool。本课是实践课——**把这两条链路从源码读到跑通**：链路一是「模型字符串 → provider 包动态装载 → 可调用模型」，链路二是「服务端声明工具 → interrupt 挂起 → 客户端实现 → 恢复执行」。两个文件合计约 1400 行，但核心机制各只有一处，先取证据再动手。

### 取证二：provider 直查优先与撞名兜底

```ts
export async function getChatModelByClassName(className, modelProvider?) {
  let config;
  if (modelProvider) {
    // Direct lookup by modelProvider key - avoids className collision
    // (e.g., google-vertexai and google-vertexai-web both use "ChatVertexAI")
    config = MODEL_PROVIDER_CONFIG[modelProvider];
  } else {
    const providerEntry = Object.entries(MODEL_PROVIDER_CONFIG)
      .find(([, c]) => c.className === className);
    config = providerEntry?.[1];
  }
  if (!config) return undefined;
  try {
    const module = await import(config.package);
    return module[config.className];
  } catch (e) {
    // ERR_MODULE_NOT_FOUND → 改写为「请 npm install 该包」的友好错误
  }
}
```

*— libs/langchain/src/chat_models/universal.ts:190-238（commit 7704471，裁剪）*

逻辑三分支：**有 provider 名直查表**（避免撞名）；**无 provider 名按 className 反查**（向后兼容，但同一类名只命中第一个 provider）；**动态 import 失败时**捕获 ERR_MODULE_NOT_FOUND，从错误消息里抠出缺失包名，改写成 `Unable to import xxx. Please install with npm install xxx` 的可执行提示。注意 import 是**惰性的**——不装 provider 包不影响主包启动，只影响装载那一刻，这是 provider 从 dependencies 里消失（L02 对比 classic）后运行时的接盘方案。

### 取证三：前缀推断表与 ConfigurableModel 的懒缓存

```ts
export function _inferModelProvider(modelName: string): string | undefined {
  if (modelName.startsWith("gpt-3") || modelName.startsWith("gpt-4") ||
      modelName.startsWith("gpt-5") || modelName.startsWith("o1") ||
      modelName.startsWith("o3") || modelName.startsWith("o4")) return "openai";
  else if (modelName.startsWith("claude")) return "anthropic";
  else if (modelName.startsWith("command")) return "cohere";
  else if (modelName.startsWith("accounts/fireworks")) return "fireworks";
  else if (modelName.startsWith("gemini")) return "google-vertexai";
  else if (modelName.startsWith("amazon.")) return "bedrock";
  else if (modelName.startsWith("mistral")) return "mistralai";
  else if (modelName.startsWith("sonar") || modelName.startsWith("pplx")) return "perplexity";
  else return undefined;
}
```

```ts
export class ConfigurableModel<...> extends BaseChatModel<...> {
  private _modelInstanceCache = new Map<string, BaseChatModel<...>>();

  async _getModelInstance(config?: RunnableConfig) {
    const cacheKey = this._getCacheKey(config);
    const cachedModel = this._modelInstanceCache.get(cacheKey);
    if (cachedModel) return cachedModel;
    const params = { ...this._defaultConfig, ...this._modelParams(config) };
    let initializedModel = await _initChatModelHelper(params.model, params.modelProvider, params);
    // queuedMethodOperations：初始化后按序补调方法
    this._modelInstanceCache.set(cacheKey, initializedModel);
    return initializedModel;
  }
  metadata = { ...this.metadata, ls_integration: "langchain_init_chat_model" };
}
```

### 动手一：跑通装载链路（含自愈提示验收）

```ts
// demo/init-model.ts —— 三种入口形态各跑一次
import { initChatModel } from "langchain";

// 形态 1：provider 前缀字符串（冒号分派，不走 _inferModelProvider）
const m1 = await initChatModel("anthropic:claude-haiku-4-5", { temperature: 0 });

// 形态 2：纯模型名（走前缀推断表）
const m2 = await initChatModel({ model: "gpt-4o" });

// 形态 3：显式 provider（撞名场景必须显式）
const m3 = await initChatModel({ model: "gemini-2.0-flash", modelProvider: "google-vertexai-web" });

console.log((m1 as any)._llmType?.() ?? typeof m1); // 壳模型即可序列化打印
```

验收三步：**其一**，删除 node_modules 里的 @langchain/anthropic 后跑形态 1，应得到 `Unable to import @langchain/anthropic. Please install with npm install @langchain/anthropic`——这是 ERR_MODULE_NOT_FOUND 改写逻辑的实测点；**其二**，恢复包后重跑，三次都返回 ConfigurableModel 实例且首次 invoke 时才完成真实装载；**其三**，用一个不在前缀表里的模型名（如 `my-model-x`）不传 provider，应得到 `Unable to infer model provider for { model: my-model-x }`。三条断言全过即打通。

### 动手二：实现 headless tool 的服务端/客户端拆分

```ts
// server/agent.ts —— 服务端：声明一个 GPS 工具，但不在服务端实现
import { createAgent, tool } from "langchain";
import { z } from "zod";

export const getLocation = tool({
  name: "get_location",
  description: "Get the user's current GPS location",
  schema: z.object({ highAccuracy: z.boolean().optional() }),
});

export const agent = createAgent({
  model: "openai:gpt-4o",
  tools: [getLocation],
});
```

```ts
// 客户端：.implement() 配对同名工具
const stream = useStream({
  assistantId: "agent",
  tools: [
    getLocation.implement(async ({ highAccuracy }) => {
      return await requestGps({ enableHighAccuracy: !!highAccuracy }); // 浏览器 GPS
    }),
  ],
});
```

服务端那一侧的关键源码再贴一次（这次是逐行读）：

```ts
const wrappedTool = coreTool(
  async (args, config) => {
    const { interrupt } = await import("@langchain/langgraph");
    return interrupt({
      type: "tool",
      toolCall: { id: config?.toolCall?.id, name, args },
    });
  },
  { name, description, schema, metadata: { headlessTool: true } }
);
const headlessTool = Object.assign(wrappedTool, {
  implement: (execute) => ({ tool: headlessTool, execute }),
});
```

*— libs/langchain/src/tools/headless.ts:58-110（commit 7704471，裁剪）*

五个机制点：**分派**——导出的 tool 包装函数以 `typeof funcOrFields !== "function"` 分流，无函数即 headless（headless.ts:205-215）；**挂起**——工具体不执行业务，只 dynamic import interrupt 并写入载荷，图在该工具节点暂停；**载荷三要素**——type/toolCall.{id,name,args}，客户端按 name 配对、按 id 回填；**元数据标记**——metadata.headlessTool: true 让框架与调试器识别这类工具；**配对**——implement() 只是把 execute 与工具对象打包成 { tool, execute } 交给 SDK，不在服务端运行任何业务代码。

验收两步：**其一**，服务端单独跑 agent 且不接客户端实现，stream 应停在含 `type: "tool"` 载荷的 interrupt 状态而不是报错；**其二**，客户端带 implement 后重跑，模型收到 GPS 结果并继续生成——两端日志里的 toolCall.id 应一致。

### 模块文档注释里的设计宣言

headless.ts 的开头有一段模块级文档注释，是理解「为什么它是主包新增面」的最短路径：

```ts
/**
 * Unified Tool Primitive for LangChain Agents
 *
 * This module re-exports the `tool` primitive from `@langchain/core/tools` with
 * an additional overload: when called without an implementation function, it
 * creates a **headless tool** that interrupts agent execution and delegates the
 * implementation to the client (e.g. via `useStream({ tools: [...] })`).
 *
 * @module
 */

import {
  tool as coreTool,
  DynamicStructuredTool,
  type ToolRunnableConfig,
} from "@langchain/core/tools";
```

*— libs/langchain/src/tools/headless.ts:1-14（commit 7704471）*

两个关键词划出了主包与 core 的分工线。**「additional overload」**：主包的 tool 不是新工具类，而是给 core 的 tool 原语追加了一种调用形态（不传实现函数）——所以类型导出面里 HeadlessTool/HeadlessToolFields/HeadlessToolImplementation 三兄弟都以 core 的 InteropZodObject 为 schema 约束，zod 互操作完全复用 core 的类型体系。**「delegates the implementation to the client」**：执行权跨界是 headless 的全部语义，服务端只有声明。再看依赖方向的一处细节：实现体里的 `await import("@langchain/langgraph")` 是**惰性 import**（headless.ts:58-77），而 L02 的依赖表里主包 dependencies 本来就硬依赖 langgraph——那为什么还要惰性？因为 interrupt 属于「图的运行时能力」，headless 工具类被构造时不该触发图内核模块的加载（浏览器端 import 主包的工具面时尤其如此），把 langgraph 的加载推迟到「工具真的被 agent 调用」那一刻。L62 讲 interrupt 机制时会回到这个载荷：`{ type: "tool", toolCall: { id, name, args } }` 正是图状态里 human-in-the-loop 断点的标准形态，headless tool 只是给它套了一个工具壳。

### _initChatModelHelper：一条装配线的三个出口

装载链路的最后一站是 `_initChatModelHelper`（universal.ts:243-289），它的三个出口正好对应三种失败/成功路径，值得并排读完：

```ts
  const modelProviderCopy = modelProvider || _inferModelProvider(model);
  if (!modelProviderCopy) {
    throw new Error(
      `Unable to infer model provider for { model: ${model} }, please specify modelProvider directly.`
    );
  }

  const config = MODEL_PROVIDER_CONFIG[
    modelProviderCopy as keyof typeof MODEL_PROVIDER_CONFIG
  ] as ModelProviderConfig;
  if (!config) {
    const supported = SUPPORTED_PROVIDERS.join(", ");
    throw new Error(
      `Unsupported { modelProvider: ${modelProviderCopy} }.\n\nSupported model providers are: ${supported}`
    );
  }

  const { modelProvider: _unused, ...passedParams } = params;
  // Pass modelProviderCopy to use direct lookup and avoid className collision
  const ProviderClass = await getChatModelByClassName(
    config.className,
    modelProviderCopy
  );
  return new ProviderClass({
    model,
    ...passedParams,
    ...(modelProviderCopy === "langsmith"
      ? getLangSmithChatModelParams(passedParams)
      : {}),
  });
```

*— libs/langchain/src/chat_models/universal.ts:243-280（commit 7704471，节选）*

**出口一（推断失败）**：前缀表没命中且没显式传 provider，错误消息直接告诉你出路——「please specify modelProvider directly」。**出口二（表外 provider）**：provider 名传了但地址簿里没有，错误消息把 SUPPORTED_PROVIDERS 全量列出来，这是把「文档」编进错误消息的做法，用户不需要查文档就能自纠。**出口三（装配成功）**：注意两个细节——`modelProvider` 从 params 里剥离（`_unused` 命名即声明：这个参数是寻址用的，不该传给 provider 构造器）；langsmith 分支在最后用展开运算符把网关参数（baseURL/useResponsesApi 等由 getLangSmithChatModelParams 生成）合入构造参数。三个出口合起来是一条**可自愈的装配线**：每个失败点都附带下一步动作，动手一里三条验收断言对应的就是这三个出口的行为实测。

### 差异结论：两条新增面为什么值得进主包

initChatModel 与 headless tool 一个共同点：**都依赖「运行时才决定的下游」**——前者动态 import 未知的 provider 包，后者把执行权交给未知的客户端。这类能力不适合 core（core 不能依赖 provider 与 langgraph），也不适合做成 middleware（它们改变的是「谁能执行」而非「如何提示」）。主包作为 harness 层恰好是它们的家：上连应用、下接 provider 与图运行时。L03 的「唯二新增面」至此完成取证闭环。两条链路还共享一种错误设计哲学：**把下一步动作写进错误消息**——initChatModel 的三个出口分别提示「请显式传 modelProvider」「Supported model providers are: 全量清单」「Please install with npm install 包名」，headless tool 则不报错而是挂起在 interrupt 上等客户端配对；一个是失败即指引，一个是等待即协作，都属于把运行时歧义压到最低的努力。排错时记住这个取向：主包新增面的报错信息本身就是文档，先读消息再翻源码，多数情况能直接定位到本课的哪个出口。

### 本课小结

- MODEL_PROVIDER_CONFIG（universal.ts:86）是 provider 地址簿；getChatModelByClassName 按 provider 直查优先，规避 ChatVertexAI 式撞名。
- _inferModelProvider 是模型名前缀表（gpt/o1-o4/claude/command/gemini/amazon./mistral/sonar/pplx）；推断失败报可读错误。
- initChatModel 返回 ConfigurableModel 壳：懒装载 + _modelInstanceCache 按 config 缓存，支撑多模型路由。
- headless tool 链路：无函数分派 → interrupt 载荷 { type:"tool", toolCall:{id,name,args} } → 客户端 implement() 配对执行。
- 两条链路都依赖运行时决定的下游，这是它们「必须住在主包」的结构原因。模块一到此收束，模块二进入 core 数据原语，从 BaseMessage 骨架开始。
