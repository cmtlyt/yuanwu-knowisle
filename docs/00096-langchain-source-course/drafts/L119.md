### 一、底座层：迁移成本最低的地带

模块九走到底座层，这是迁移成本最低的一片——VectorStore/Embeddings/Document/Store 四大抽象全部住在 core，迁移动作几乎只有改 import。但也埋着本课最大的雷：一个搜教程必踩的同名陷阱。先取底座四件套的地址证据：

| 抽象 | core 位置:行 | classic 侧残留 | 新包 re-export |
|---|---|---|---|
| VectorStore | core vectorstores.ts:553（abstract class） | MemoryVectorStore 实现（vectorstores/memory.ts:142） | langchain/src/index.ts:69 Document 等（:64 InMemoryStore） |
| Embeddings | core embeddings.ts:32（abstract class） | — | 经集成包使用 |
| Document | core documents/document.ts（DocumentInterface） | document.ts 转发 | langchain/src/index.ts:69 |
| BaseStore/InMemoryStore | core stores.ts:6 / :56 | storage/in_memory.ts:1 单行转发 | langchain/src/index.ts:64 |

逐行确认过的关键行：`export abstract class VectorStore`（vectorstores.ts:553）、`export abstract class Embeddings<`（embeddings.ts:32）、`export abstract class BaseStore<K, V> extends Serializable`（stores.ts:6）、`export class InMemoryStore<T = any> extends BaseStore<string, T>`（stores.ts:56）、classic 转发壳 `export { InMemoryStore } from "@langchain/core/stores"`（storage/in_memory.ts:1）与 `export * from "@langchain/textsplitters"`（text_splitter.ts:1）。

### 二、实操①：一个检索链的底座迁移

搭一条最小检索链，把底座件全部换成 core 地址：

```ts
// ── 迁移前（0.x 形状）────────────────────────────
import { MemoryVectorStore } from "langchain/vectorstores/memory";  // classic 路径
import { OpenAIEmbeddings } from "@langchain/openai";
import { Document } from "langchain/document";                       // classic 转发
import { InMemoryStore } from "langchain/storage/in_memory";         // 空壳:1

const docs = [
  new Document({ pageContent: "起亚 EV5 续航 620 公里", metadata: { id: "ev5" } }),
  new Document({ pageContent: "现代 IONIQ 5 续航 580 公里", metadata: { id: "ioniq5" } }),
];
const store = new InMemoryStore<string, string>();       // 键值存储（存别的元数据用）
await store.mset([["latest", "ev5"]]);
const vectorStore = await MemoryVectorStore.fromDocuments(docs, new OpenAIEmbeddings());
const hits = await vectorStore.similaritySearch("续航最长", 1);
```

```ts
// ── 迁移后（1.x 形状）────────────────────────────
import { MemoryVectorStore } from "@langchain/classic/vectorstores/memory"; // 实现仍在 classic
import { InMemoryStore } from "@langchain/core/stores";    // core stores.ts:56
import { Document } from "@langchain/core/documents";      // core 文档基座

const docs = [
  new Document({ pageContent: "起亚 EV5 续航 620 公里", metadata: { id: "ev5" } }),
  new Document({ pageContent: "现代 IONIQ 5 续航 580 公里", metadata: { id: "ioniq5" } }),
];
const store = new InMemoryStore<string, string>();
await store.mset([["latest", "ev5"]]);
const vectorStore = await MemoryVectorStore.fromDocuments(docs, new OpenAIEmbeddings());
const hits = await vectorStore.similaritySearch("续航最长", 1);

import { expect, it } from "vitest";
it("迁移后检索行为一致", () => {
  expect(hits[0].metadata.id).toBe("ev5");   // 620 > 580，语义检索命中
});
```

改造只动了三行 import：实现类（MemoryVectorStore）指向 classic 的真实位置，抽象与通用件（InMemoryStore/Document）指向 core。检索行为零变化——这正是「纯换包名」的含义：**底座层的 API 契约没有换代，只是地址簿更新**。要留意的唯一实质差异：MemoryVectorStore 这种内存实现没有新版包，新项目若上生产应直接换集成包（pgvector/qdrant 等），内存库只适合测试。一个常被忽略的次级差异也顺便点破：迁移前后 `similaritySearch` 返回的 Document 实例来自不同的类定义来源（classic 转发 vs core 直引），若项目里同时存在两处来源且锁了不同 core 版本，会出现「同名不同实例」的判型陷阱——单实例 core 纪律（L120）在底座层迁移完成的第一天就要执行，而不是等到出问题再查。

### 三、实操②：同名陷阱对照实验

现在拆本课的雷。三个名字长得像但实体不同：`@langchain/langgraph` 的 createReactAgent、classic 的 createReactAgent、新包的 createAgent。做对照实验，同一份「工具循环」需求用两个入口各实现一遍：

```ts
// 旧入口 A：classic 的 createReactAgent（classic agents/react/，langgraph prebuilt 同源）
import { createReactAgent } from "@langchain/classic/agents/react";
import { ChatOpenAI } from "@langchain/openai";
import { tool } from "@langchain/core/tools";
import { z } from "zod";

const mileage = tool(
  async ({ model }) => ({ ev5: 620, ioniq5: 580 }[model] ?? -1),
  { name: "mileage", schema: z.object({ model: z.string() }) }
);

const legacyReAct = createReactAgent({
  llm: new ChatOpenAI({ model: "gpt-4o" }),
  tools: [mileage],
  // 旧参数面：stateModifier / messageModifier（prebuilt react_agent_executor.ts:70 的 prompt 参数族）
});

const legacyResult = await legacyReAct.invoke({
  messages: [{ role: "user", content: "两款车谁的续航更长？" }],
});
```

```ts
// 新入口 B：langchain 新包的 createAgent
import { createAgent } from "langchain";

const agent = createAgent({
  model: "openai:gpt-4o",            // 字符串模型标识，无需手工实例化
  tools: [mileage],                   // 工具原样可复用
  // 新参数面：prompt / responseFormat / middleware / stateSchema（agents/index.ts:77-83）
});

const result = await agent.invoke({
  messages: [{ role: "user", content: "两款车谁的续航更长？" }],
});
import { expect, it } from "vitest";
it("新入口结果含工具往返后的回答", () => {
  const ai = result.messages.at(-1);
  expect(ai.getType()).toBe("ai");
});
```

跑通后写差异清单（本课必须带走的认知）：

| 维度 | classic createReactAgent | 新包 createAgent |
|---|---|---|
| 源码位置 | classic agents/react/（导出于 agents/index.ts:98），与 langgraph-core prebuilt/react_agent_executor.ts:669 同源 | langchain/src/agents/index.ts:672，实现体一行 `return new ReactAgent(params)` |
| 参数面 | stateModifier/messageModifier/prompt 旧族 | middleware/responseFormat/stateSchema/prompt 新族 |
| 扩展机制 | 无 middleware 概念 | 六 hook + 20+ 预置 middleware（L115） |
| 返回对象 | LangGraph CompiledGraph | ReactAgent（内部 `#graph`，ReactAgent.ts:181） |

判断手上代码属于哪个世界的方法：看构造参数——出现 `stateModifier` 就是 prebuilt/classic 族，出现 `middleware` 就是新包。认参数不认名字，因为搜索引擎抓到的教程三种都可能有。

### 四、实操③：initChatModel 的换包验证

底座层最后一个「两个住址」的例子：initChatModel（classic chat_models/universal.ts:614 / 新包 chat_models/universal.ts，经 langchain/src/index.ts:23 导出）。迁移并验证一致性：

```ts
// 旧：import { initChatModel } from "langchain/chat_models/universal";  // classic 住址:614
import { initChatModel } from "langchain";                              // 新包住址（index.ts:23）

const model = await initChatModel("openai:gpt-4o", { temperature: 0 });
const bound = model.bindTools([mileage]);

import { expect, it } from "vitest";
it("换包后同一模型标识行为一致", async () => {
  expect(bound).toBeDefined();
  const res = await bound.invoke([{ role: "user", content: "hi" }]);
  expect(res).toBeDefined();
});
```

模型标识字符串（\"openai:gpt-4o\"）的语义在两个住址下一致——initChatModel 是精确替代的正面教材，与 createReactAgent 的同名陷阱形成一反一正的对照组：**同样是跨包 API，有的同名同义可放心换 import，有的同名不同义必须逐参数核对**。判断依据永远是源码而不是名字。

### 五、MemoryVectorStore 内部走读：实现为何留在 classic

第二节把 MemoryVectorStore 的 import 指向了 classic，这里走进它的实现看「抽象与实现分离」的具体收益。类声明（classic vectorstores/memory.ts:142）与两个关键路径：

```ts
export class MemoryVectorStore extends VectorStore {
  // :172 批量入库：await this.embeddings.embedDocuments(texts)
  // :259 相似度检索：const queryEmbedding = await this.embeddings.embedQuery(query)
}
```

*— langchain-classic/src/vectorstores/memory.ts:142-259（commit 7704471，路径节选）*

它只做三件事：内存数组存向量、入库时批量调 `embeddings.embedDocuments`、检索时调 `embeddings.embedQuery` 算相似度。所有「抽象契约」都由父类 core VectorStore（vectorstores.ts:553）与 Embeddings 接口承担——**实现里没有任何 classic 协议依赖**，所以它虽然住在 classic，却与 1.x 代码完全互通（L120 的类型互通直接适用）。这也解释了官方为什么不把它搬进新包：内存向量库是教学/测试件，生产形态本就该换成集成包的真实向量库，搬进主线只会增加维护面。Embeddings 契约本身在 core embeddings.ts:32，两个抽象方法 `embedDocuments(documents: string[])`（:52）与 `embedQuery(document: string)`（:60）——迁移自定义 embedding 时实现这两个方法即可，接入面与 0.x 完全一致。底座层「纯换包名」的深层原因至此清楚：**抽象、接口、类型全部下沉且未变，变的只有实现的住址**。

### 六、initChatModel 的推断链：_inferModelProvider 与 ConfigurableModel

第四节用 initChatModel 验证了「换包行为一致」，这里补它的内部推断链，理解同名双实现的迁移边界。classic 侧（chat_models/universal.ts）有三个关键件：

```ts
// :203  const modelProviderCopy = modelProvider || _inferModelProvider(model);
// :236-238 JSDoc 示例：
//   _inferModelProvider("gpt-4");      // returns "openai"
//   _inferModelProvider("claude-2");   // returns "anthropic"
//   _inferModelProvider("unknown-model"); // returns undefined
// :240  export function _inferModelProvider(modelName: string): string | undefined
// :293  export class ConfigurableModel<
```

*— langchain-classic/src/chat_models/universal.ts:203-293（commit 7704471，行号索引）*

推断链的机制：调用方给 `initChatModel("openai:gpt-4o")` 时 provider 前缀显式存在，直接分派；只给模型名（如 "gpt-4o"）时走 `_inferModelProvider` 的名字模式匹配兜底，匹配不到返回 undefined 并抛错。返回的 ConfigurableModel（:293）是一个延迟绑定模型实例的包装——`initChatModel` 异步返回后还能切换底座模型，这是它比直接 new ChatOpenAI 多出来的能力。新包的同名实现（langchain/src/chat_models/universal.ts，经 index.ts:23 导出）保持同一推断链，所以「换包导入」不仅是签名一致，行为语义（推断规则、错误形态、ConfigurableModel 能力）也一致——这正是第四节说它是「精确替代正面教材」的完整含义。对照同名陷阱（createReactAgent），两者的差别现在可以说得更准：**initChatModel 的两个实现是同源复制，createReactAgent 与 createAgent 是两代架构的不同产物**——同名是否可信，取决于实现是否同源，这个判断只能读源码得出。

### 七、底座五件套的补遗：Document 与 loader 的住址

四件套之外还有第五件常被一起迁移：Document 本体与产它的 loader。Document 抽象在 core（documents/document.ts 的 DocumentInterface，retrievers/index.ts:7 处的 import 即证据），新包顶层直接 re-export Document（langchain/src/index.ts:69）；但 **fs 类 loader 的实现全部留在 classic**——DirectoryLoader（document_loaders/fs/directory.ts:47）、TextLoader（fs/text.ts:19）、JSONLoader/JSONLinesLoader（fs/json.ts:11/151）、MultiFileLoader（fs/multi_file.ts:25），core 只留 BaseDocumentLoader 基类（core document_loaders/base.ts）。这组分布与检索层（L118）完全同构：抽象下沉、实现留守，而且 loader 实现只依赖 core 类型（产出的就是 DocumentInterface[]），依赖封闭度高——走查①里 loader 继续从 classic import 正是这个原因，不是临时妥协而是长期形态。

另外两个单行转发件也顺手归位：text_splitter.ts:1 只是一行 `export * from "@langchain/textsplitters"`（指向独立包而非 core），load/serializable.ts:1 转发 core 的序列化层。底座层的完整迁移动作至此可以浓缩成一张速查：**Document/InMemoryStore/BaseStore → core；VectorStore/Embeddings 抽象 → core、内存实现留 classic；fs loader 实现 → classic；textsplitters → 独立包；initChatModel → 两住址选新包**。速查表的每一行都有前文源码取证支撑，拿到任何底座 import 都能秒判住址。

### 本课小结

- 底座四件套的地址：VectorStore（core vectorstores.ts:553）、Embeddings（embeddings.ts:32）、Document（core documents）、BaseStore/InMemoryStore（stores.ts:6/:56）；classic 侧只剩实现（MemoryVectorStore:142）与单行转发壳。
- 三个相似名三个实体：langgraph prebuilt createReactAgent（react_agent_executor.ts:669）、classic createReactAgent（agents/index.ts:98）、新包 createAgent（agents/index.ts:672）；认参数面不认名字。
- initChatModel 是「同名同签名换 import」的正面教材，与同名陷阱构成对照。
- 下一课拉远视角：classic 与新包为什么能同进程并存——共享 @langchain/core 的类型互通机制，是混合运行策略的地基。
