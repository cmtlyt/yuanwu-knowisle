### 旧王国的宪法条文

L102 给出了两块大陆的地图，本课解剖旧大陆的「宪法」——所有 0.x 编排单元共同遵守的 BaseChain 协议。核心结论先放这里：**call/values 协议是一条「字符串字典 + 隐式副作用」的约定，它输给 Runnable 协议不是因为慢，而是因为在类型安全、可组合性、流式与批处理上存在代际差距。**读完这课你应该能自己从源码论证「为什么必须淘汰」，而不是背结论。

### 协议的骨架：一个抽象类管所有编排

BaseChain 的声明与继承关系如下：

```ts
export abstract class BaseChain<
  RunInput extends ChainValues = ChainValues,
  RunOutput extends ChainValues = ChainValues,
>
  extends BaseLangChain<RunInput, RunOutput>
  implements ChainInputs
{
  declare memory?: BaseMemory;
```

*— langchain-classic/src/chains/base.ts:32-40（commit 7704471）*

三个关键点。第一，泛型参数默认是 `ChainValues`——它的定义就是 `Record<string, any>`，也就是说即使你写了泛型，默认契约仍是字符串字典。第二，`memory` 直接挂在链对象上，这是「状态藏在 chain 对象里」的源头（L104 展开协议细节）。第三，它继承 BaseLangChain，也就是旧架构里「可序列化对象」与「回调支持」的底座——注意它并没有继承 Runnable 协议族。

LLMChain 是这个协议最典型的子类，看它的字段声明就明白旧链的全部结构：

```ts
export class LLMChain ... {
  prompt: BasePromptTemplate;
  llm: Model;
  outputKey = "text";
  outputParser?: BaseLLMOutputParser<T>;

  get inputKeys() {
    return this.prompt.inputVariables;
  }
```

*— langchain-classic/src/chains/llm_chain.ts:98-110（commit 7704471）*

一条链 = prompt + llm + outputParser 三件套，输入键从模板变量反推。`get inputKeys()` 这五行是协议缺陷的浓缩样本：**整条链的输入契约取决于模板字符串里写了哪些 {占位符}**，类型系统完全失明，拼错键要到运行时才报错。

### invoke 的样板税：每个编排单元都要交一遍

BaseChain.invoke 的实现里藏着旧协议的第二个缺陷——公共设施全靠手写。摘录主干：

```ts
async invoke(input: RunInput, options?: RunnableConfig): Promise<RunOutput> {
  const config = ensureConfig(options);
  const fullValues = await this._formatValues(input);
  const callbackManager_ = await CallbackManager.configure(
    config?.callbacks, this.callbacks, config?.tags, this.tags,
    config?.metadata, this.metadata, { verbose: this.verbose }
  );
  const runManager = await callbackManager_?.handleChainStart(...);
  let outputValues: RunOutput;
  try {
    outputValues = (await Promise.race([
      this._call(fullValues as RunInput, runManager, config),
      new Promise<never>((_, reject) => { /* abort 监听 */ }),
    ]));
```

*— langchain-classic/src/chains/base.ts:96-113（commit 7704471，有裁剪）*

ensureConfig、CallbackManager.configure、handleChainStart、Promise.race 监听 abort——这套四步样板在 Runnable 协议里由基类默认实现统一供给（L27 的「四大支柱与降级链」），子类只需实现核心逻辑。而在旧协议下，每一个继承 BaseChain 的新链都要重交一遍样板税，或者依赖这个抽象基类的一次性实现。样板本身没错，错在**它写在了具体抽象类里而不是协议默认实现里**，导致 BaseChain 无法获得 Runnable 生态的 batch/stream/transform/pipe 组合能力。

### call 包装层：隐式 memory 的注入点

旧协议最有历史味道的部分是 memory 注入发生在哪。答案：不在子类，不在 invoke 主干，而在 call 的包装层——BaseChain 里 call 会先从输入里摘出 memory 需要的变量（`_selectMemoryInputs`），调 `memory.loadMemoryVariables(values)` 把记忆变量合进 prompt 输入，执行 `_call` 后再调 `memory.saveContext(inputValues, outputValues)` 写回。子类看到的 `_call(values)` 是「纯业务」，状态读写对它完全不可见。

这个设计在单链场景下体验良好，但有两个致命伤。其一，**副作用不可见**：一个链对象一旦挂了 memory，同样的 call 输入会因内部状态不同而输出不同，链失去了「无状态 Runnable」的可测性。其二，**组合即失效**：把两条带 memory 的链 pipe 起来，谁的记忆键喂给谁的输入？字典键名字符串拼装在这种场景下没有任何保护。1.x 的解法是把状态显式化：messages 数组就是状态本体，谁读写它写在明面上（L104 对比协议，L105 起的新世界观里图状态取代 memory 对象）。

### 淘汰判决书的四条罪名

把上面三节的源码证据收拢，call/values 协议的四条罪名齐全：

| 罪名 | 旧协议证据（文件:行） | Runnable 协议的修复 |
|---|---|---|
| 字符串键无类型 | ChainValues=Record<string,any>；inputKeys 由模板反推（llm_chain.ts:108） | invoke 泛型参数锁定输入输出类型 |
| 隐式 memory 副作用 | memory 挂链上，call 包装层自动读写（base.ts:39、call 层） | 状态显式：messages/图状态，无隐藏对象 |
| 样板税 | invoke 手写回调 configure + abort 竞速（base.ts:96-113） | Runnable 基类默认实现统一供给 |
| 无组合原语 | 组合靠子类互相持有（RetrievalQAChain 持 combineDocumentsChain，retrieval_qa.ts:74-75） | pipe/RunnableSequence/RunnableMap 一等公民 |

需要强调「无组合原语」这条：RetrievalQAChain 内部持有另一条 BaseChain 并手动 `.call()` 传字典——旧架构的「组合」就是字典传递，键名对不上只能运行时炸。1.x 的 RunnableSequence 在类型层面就把上一环输出接到下一环输入（L30 讲过吸并与类型接线）。这也是为什么官方在 LLMChain 自己的 JSDoc 里写 `prompt.pipe(llm)`——概念替代从旧类的文档注释里就开始了。

### 本课小结

- BaseChain（chains/base.ts:32）定义了 0.x 一切编排单元的宪法：ChainValues 字典进出 + memory 挂对象 + _call 纯业务。
- 四条淘汰罪名：字符串键无类型、隐式 memory 副作用、invoke 样板税、组合靠字典传递无保护——每条都有源码行号背书。
- 淘汰是架构代差而非性能问题，别用「速度」当理由向团队推销迁移。
- 协议死亡但类型残留：core memory.ts 的 InputValues/OutputValues/MemoryVariables 还在，只供 classic 消费——「core 有不等于 1.x 推荐」。
- 下一课放大镜对准 memory 注入点：loadMemoryVariables/saveContext 的隐式读写协议，它藏在 chain 对象里的状态到底怎么运转。
