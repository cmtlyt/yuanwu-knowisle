### 定位：不做容错、只做断路器的两种闸

L56 的容错件赌「失败是暂时的」，本课的预算闸不赌——**它假设 agent 可能陷入无限循环或失控成本，到次数就断**。这是生产护栏的最后一道：retry 会放大成本（每次重试都是一次计费调用），limit 负责封顶。两种闸共用 thread/run 两个维度，但实现思路完全不同：modelCallLimit 在模型调用**之前**拦（beforeModel 闸门），toolCallLimit 在模型响应**之后**审（afterModel 检查 tool_calls）——因为「工具调用」在模型吐出 AIMessage 的那一刻就已经发生，拦不住，只能审后处置。

一句话结论：**modelCallLimit 是前置闸（计数→超限即断），toolCallLimit 是后置审（数→挑出超限调用注入错误消息）。**

### modelCallLimit：三个 hook 的接力

它把 state schema、闸门、计数、重置拆在三个 hook 里，是「stateSchema + before/afterModel + afterAgent」协作的标准教案。

```ts
const stateSchema = z.object({
  threadModelCallCount: z.number().default(0),
  runModelCallCount: z.number().default(0),
});
// ...
beforeModel: {
  canJumpTo: ["end"],
  hook: (state, runtime) => {
    let exitBehavior = runtime.context.exitBehavior
      ?? middlewareOptions?.exitBehavior ?? DEFAULT_EXIT_BEHAVIOR;
    // @ts-expect-error - throw is deprecated
    if (exitBehavior === "throw") { /* warn + 改为 error */ }
    const threadLimit = runtime.context.threadLimit ?? middlewareOptions?.threadLimit;
    const runLimit = runtime.context.runLimit ?? middlewareOptions?.runLimit;
    if (typeof threadLimit === "number" && threadLimit <= state.threadModelCallCount) {
      const error = new ModelCallLimitMiddlewareError({ threadLimit, threadCount: ... });
      if (exitBehavior === "end") {
        return { jumpTo: "end", messages: [new AIMessage(error.message)] };
      }
      throw error;
    }
    // runLimit 同理 ...
    return state;
  },
},
afterModel: (state) => ({
  runModelCallCount: state.runModelCallCount + 1,
  threadModelCallCount: state.threadModelCallCount + 1,
}),
afterAgent: () => ({ runModelCallCount: 0 }),
```

*— libs/langchain/src/agents/middleware/modelCallLimit.ts:33-207（commit 7704471，有裁剪）*

注意三点：闸门条件是 `limit <= count`（计数器在 beforeModel 检查时还是上一轮的值，本次调用尚未计入，所以语义是「第 limit+1 次调用被拒」）；end 出口注入的 AIMessage 内容就是错误描述，用户能看到「thread level call limit reached with N model calls」；runtime.context 优先于构造参数——预算可在 invoke 时按请求收紧。

separateToolCalls 内部逐个判断 wouldExceedLimit（`count + 1 > limit`），放行的推进临时计数，超限的进 blocked。计数键按工具名分桶（不指定则 `__all__`，常量 DEFAULT_TOOL_COUNT_KEY，toolCallLimit.ts:374），中间件名也随之变成 `ToolCallLimitMiddleware[search]`（287 行的模板字符串）——一个 agent 可以并排放多个实例、每个盯一个工具。

分桶设计的实战价值值得展开：给 search 配 `threadLimit: 50`、给 send_email 配 `threadLimit: 5`、再放一个不带 toolName 的全局闸 `threadLimit: 200`，三个实例各自维护 record 里自己的键，互不读取对方的计数——按工具分级限流的完整方案不需要任何自定义代码。注意中间件改名不是装饰：MiddlewareNode 按名字注册节点，两个同名实例会撞 L53 提过的重名报错，带 `[toolName]` 后缀后每个实例在图里都是独立节点。还有一个隐含边界：record 的键是「当前配置的 toolName」，若你在运行中途（比如 runtime.context 覆盖）换了一个 toolName，record 里会同时存在多个键的历史值——计数不会跨键合并，切键等于换了新账户。

### 三档 exitBehavior 的行为矩阵

两种闸的出口行为放一起对照，差异立刻显形：

| exitBehavior | modelCallLimit | toolCallLimit |
|---|---|---|
| 默认 | end | **continue** |
| continue | —（不存在） | 超限调用注入 error ToolMessage（内容只对模型说「别再调」），其余照常 |
| error | 抛 ModelCallLimitMiddlewareError | 抛 ToolCallLimitExceededError（含 thread/run 明细） |
| end | jumpTo: "end" + 注入 AIMessage | 注入 error ToolMessage + 收尾 AIMessage（含明细）；有其他待执行调用时抛错 |

continue 只属于工具闸，因为工具可以部分放行；end 对两种闸都存在但形态不同——模型闸直接结束 agent，工具闸还要给每个超限 call 配消息（provider 协议要求每个 tool_call 必须有回应）。error 档的两类异常都携带完整计数明细，便于调用方程序化处理。

### thread 与 run：持久化维度的差异

thread 计数随 state 持久化（配合 checkpointer 跨 invoke 累计），run 计数按次归零——但两件套的归零机制不同：modelCallLimit 用 afterAgent 显式清零数字；toolCallLimit 的 run 计数定义是「最后一次 HumanMessage 之后的调用」（toolCallLimit.ts:180-183 的类注释），afterAgent 把 record 重置为空对象（525-527）。使用 checkpointer 时 thread 预算是真正的「账户余额」，不配 checkpointer 时 thread/run 在单进程内近似等价。给 chatbot 配 `threadLimit: 200, runLimit: 20` 的含义因此是：整段对话最多 200 次模型调用，每次回复最多 20 次——两层防爆，缺一不可。

补一层「预算从哪读」的完整优先级，它是本课 quiz 里 runtime.context 覆盖机制的展开：modelCallLimit 的 beforeModel 里每个参数都走 `runtime.context.X ?? middlewareOptions?.X ?? DEFAULT` 三段链（modelCallLimit.ts:145-199 的 hook 体）——invoke 时传 `{ context: { threadLimit: 5 } }` 就能对单个请求临时收紧预算，构造期配置退为兜底。这个设计把预算闸从「部署期常量」升级为「请求期变量」：同一 agent 可以对免费用户传紧预算、对付费用户传松预算，agent 实例不用重建。toolCallLimit 的 exitBehavior 同理。三个出口档位里还有一条容易被忽略的组合约束：end 档对工具闸要求「没有其他待执行调用」（pitfalls 里的报错），所以 **end 与并行工具调用天然冲突**——想让超限工具被拦、其余照跑，continue 是唯一选项；想在超限瞬间硬停，得先保证模型不会并行吐出其他调用。预算闸的选型因此不仅是「限多少」，还包括「怎么停」的拓扑现实。

### 本课小结

- modelCallLimit：beforeModel 前置闸 + afterModel 计数 + afterAgent 清 run；end 是默认出口（jumpTo end + AIMessage）。
- toolCallLimit：afterModel 后置审，按工具名分桶计数；continue 是默认出口，超限调用注入「只对模型说人话」的 error ToolMessage。
- 计数不对称是特性：thread 只记放行（预算不被拦截消耗），run 记尝试（本运行确实发生过）。
- 两件套的超限消息刻意区分受众：给模型的简短（不提 thread/run），给用户的详细（带计数明细）。
- 下一课转到工具层容错三件套：toolRetry/toolError/toolEmulator——retry 回来了，还带来一个用 LLM 假装工具的测试利器。
