### 同一个抽象，两种时序

L30 的序列是「接力」，本课的 RunnableMap 是「扇出」：同一份输入喂给字典里的每个 Runnable，结果按键拼回字典。它最有意思的地方是 **invoke 与 transform 用了完全不同的调度原语**——前者 Promise.all（全对才算对），后者 Promise.race（先到先流出）。两种时序不是实现差异，而是两种消费语义：整批结果 vs 交错事件流。另外两件小事也在这里交代：RunnableParallel 只是纯别名（base.ts:2888 一行空类体），以及支撑流式扇出的 atee 广播技巧。

### 构造与 invoke：Promise.all 的整批语义

```ts
constructor(fields: { steps: RunnableMapLike<RunInput, RunOutput> }) {
  super(fields);
  this.steps = {};
  for (const [key, value] of Object.entries(fields.steps)) {
    this.steps[key] = _coerceToRunnable(value);
  }
}

async invoke(
  input: RunInput,
  options?: Partial<RunnableConfig>
): Promise<RunOutput> {
  const config = ensureConfig(options);
  const callbackManager_ = await getCallbackManagerForConfig(config);
  const runManager = await callbackManager_?.handleChainStart(...);
  delete config.runId;
  const output: Record<string, any> = {};
  try {
    const promises = Object.entries(this.steps).map(
      async ([key, runnable]) => {
        output[key] = await runnable.invoke(
          input,
          patchConfig(config, {
            callbacks: runManager?.getChild(`map:key:${key}`),
          })
        );
      }
    );
    await raceWithSignal(Promise.all(promises), config.signal);
  } catch (e) {
    await runManager?.handleChainError(e);
    throw e;
  }
  await runManager?.handleChainEnd(output);
  return output as RunOutput;
}
```

构造即 coerce（对象字面量的值也能是函数——L30 的分派规则）。invoke 的骨架与序列一致：handleChainStart → delete runId → 并发 → end/error。三个细节值得抠：每个分支的 config 都经 patchConfig 换上 **`map:key:${key}`** 标签的子回调，追踪树里并行分支各自有名有姓；`Promise.all` 决定了**一个分支抛错就整体炸**（其余分支继续跑完但结果丢弃——Promise.all 只认第一个 reject）；raceWithSignal 让 config.signal 能取消整场扇出。对比 L28：batch 的 returnExceptions 语义这里**没有**，要「部分失败容忍」得在分支内部各自包 withFallbacks。

### _transform：Promise.race 的交错流

```ts
async *_transform(
  generator: AsyncGenerator<RunInput>,
  runManager?: CallbackManagerForChainRun,
  options?: Partial<RunnableConfig>
): AsyncGenerator<RunOutput> {
  // shallow copy steps to ignore changes while iterating
  const steps = { ...this.steps };
  // each step gets a copy of the input iterator
  const inputCopies = atee(generator, Object.keys(steps).length);
  const tasks = new Map(
    Object.entries(steps).map(([key, runnable], i) => {
      const gen = runnable.transform(
        inputCopies[i],
        patchConfig(options, {
          callbacks: runManager?.getChild(`map:key:${key}`),
        })
      );
      return [key, gen.next().then((result) => ({ key, gen, result }))];
    })
  );
  while (tasks.size) {
    const promise = Promise.race(tasks.values());
    const { key, result, gen } = await raceWithSignal(
      promise,
      options?.signal
    );
    tasks.delete(key);
    if (!result.done) {
      yield { [key]: result.value } as unknown as RunOutput;
      tasks.set(
        key,
        gen.next().then((result) => ({ key, gen, result }))
      );
    }
  }
}
```

*— libs/langchain-core/src/runnables/base.ts:2375-2414（commit 7704471）*

这就是经典的「N 路 racing generator」调度器：每个分支预先发起第一次 next() 存进 tasks Map；while 循环 race 全场，最快的那个 yield 出去，然后只给它续挂 next()；分支 done 就从 Map 删除，Map 清空循环结束。yield 的形状是 `{ [key]: value }`——单键字典，让下游知道这块来自哪个分支（下游要么是再一层 Map/Assign 拼合，要么直接消费交错事件）。`shallow copy steps` 防的是迭代期间 steps 被改（注释原话：ignore changes while iterating）。每次 race 都套 raceWithSignal，取消语义与 invoke 对齐。

对照表把两种时序钉死：

| 维度 | invoke | _transform |
|---|---|---|
| 调度原语 | Promise.all | Promise.race + tasks Map |
| 返回/产出时机 | 全部成功后一次性 | 先完成先 yield，块间交错 |
| 失败语义 | 首个 reject 炸全场 | 分支 done 即摘除，单块内错误向上抛 |
| 子回调 | map:key:X | map:key:X（同款） |
| 输出形态 | 完整字典 | `{ [key]: value }` 单键块 |

### atee：一份迭代器，N 个消费者

两个分支都需要读同一个输入 generator，直接传两份引用会共享 next() 游标（各自拿到一半的块）。atee 的解法：

```ts
export function atee<T>(
  iter: AsyncGenerator<T>,
  length = 2
): AsyncGenerator<T>[] {
  const buffers = Array.from(
    { length },
    () => [] as Array<IteratorResult<T> | IteratorReturnResult<T>>
  );
  return buffers.map(async function* makeIter(buffer) {
    while (true) {
      if (buffer.length === 0) {
        const result = await iter.next();
        for (const buffer of buffers) {
          buffer.push(result);
        }
      } else if (buffer[0].done) {
        return;
      } else {
        yield buffer.shift()!.value;
      }
    }
  });
}
```

*— libs/langchain-core/src/utils/stream.ts:124-146（commit 7704471）*

机制是「空缓冲才拉源 + 结果广播」：任何副本需要数据且自己缓冲为空时，对源迭代器调**一次** next()，把结果 push 进**所有**副本的缓冲区；之后各副本从自己的缓冲 shift 消费。这保证了（1）源只被真实消费一遍——上游的 invoke/side effect 不重复；（2）慢副本的块在缓冲里排队，不会丢。代价是快分支会拖着一个等慢分支同步的队列——Map 的扇出天文学上永远受最慢分支钳制，流式下表现为块间间隔取决于瓶颈步（呼应 L30 的瓶颈定理）。RunnableAssign（L33）同样用 atee 拉双通道，同一个工具在组合子层反复出现。

stream() 侧的包装（base.ts:2427-2441）与 L27 完全同款：transform 生成器 → AsyncGeneratorWithSetup 首块缓冲 → IterableReadableStream。也就是说 Map 的流式扇出同样享受「错误提前到 await stream()」的待遇。

### stream() 的同款包装与 Map 的边界细节

Map 的 stream() 与 L27/L32 是同一段模板的三份拷贝：

```ts
async stream(input, options?) {
  async function* generator() {
    yield input;
  }
  const config = ensureConfig(options);
  const wrappedGenerator = new AsyncGeneratorWithSetup({
    generator: this.transform(generator(), config),
    config,
  });
  await wrappedGenerator.setup;
  return IterableReadableStream.fromAsyncGenerator(wrappedGenerator);
}
```

*— libs/langchain-core/src/runnables/base.ts:2427-2441（commit 7704471）*

单元素生成器把 invoke 形态的输入伪装成流，transform 复用 `_transform` 的 race 调度，AsyncGeneratorWithSetup 完成首块缓冲——所以 Map 扇出的流式同样享受「错误提前到 await stream()」的待遇，且每个分支的 `map:key:X` 子回调在 race 循环里就已挂好。构造侧还有一个不出错的快捷口径：`RunnableMap.from(steps)`（base.ts:2325-2335）是裸字典的入口，等价于 `new RunnableMap({ steps })`，内部同样不 coerce——注意 from 与构造函数一样会把值交给 `_coerceToRunnable`，裸函数分支照常生效。invoke 的 handleChainStart 传给回调的输入是 `{ input }` 包裹的字典（base.ts:2343-2348）而非裸输入——追踪树上 Map 这个 run 记录的输入形状与 `_coerceToDict` 的字典化约定一致，消费端按 `run.inputs.input` 取原始值。最后补一条 `_transform` 的防御细节：函数第一行的浅拷贝注释（*shallow copy steps to ignore changes while iterating*）与 atee 的 `Object.keys(steps).length` 配合——**迭代期间增删分支不影响本场扇出**，N 在复制那一刻定死；想动态增减分支得开一场新的 Map，而不是往 running 的字典里塞键。invoke 侧的输出字典还有一处并发细节：`output[key] = ...` 在所有分支间共享同一个对象，各分支异步交错写入但**键互不相同**，Promise.all 收束后 `handleChainEnd(output)` 上报的就是完整字典（base.ts:2355-2372）——没有锁、没有竞态，扇出的隔离性完全由「一键一分支」的形状约定保证；若两个分支写出同名键（Object.entries 不会发生，但手工构造 steps 时可能），后写者覆盖先写者，这就是「键即命名空间」的另一面。与 L30 对照还能提炼一条选型口径：**分支之间无依赖用 Map（并行），后一步吃前一步的输出用 Sequence（串行）**；字典输入的形状约定（对象进、同形字典出）让 Map 成为 LCEL 的「结构化节点」，getGraph 的可视化与 assign/pick 的字典手术刀（L33）都建立在这个形状约定之上——理解 Map 的两种时序之后，LCEL 并行编程的剩余问题只剩「分支怎么容错」，那正是 L33 fallback 的领地。

### 本课小结

- RunnableParallel 是 RunnableMap 的**纯别名空类**（base.ts:2888）；真正的机制全在 Map 里。
- invoke 走 Promise.all + raceWithSignal：分支全成功才拼字典返回，首个 reject 炸全场；子回调统一叫 `map:key:X`。
- _transform 走 Promise.race 调度器：先完成先 yield `{[key]: value}` 单键块，分支 done 即摘除——「先到先得」与 invoke 的「全到才得」是同一抽象的两种消费语义。
- atee 用「空缓冲才拉源、结果广播到所有副本」实现单次消费的 N 路分发，是 Map 与 Assign 共享的迭代器基础设施。
- 下一课转向最「自由」也最容易误用的组合子：RunnableLambda——lambda 返回什么决定它的命运。
