### 切分环的入场券：先回答「它凭什么进 LCEL」

上一课的结论是加载器不是 Runnable——那么从加载到检索之间，是谁先把「可组合性」接进来的？答案是切分环。本课核心结论一句话：**TS 版把切分器定义为「文档数组 → 文档数组」的 Runnable，于是切分不再是链外的预处理步骤，而是 LCEL 管道里的一等公民**。这是 TS 相对 Python 版最值得注意的架构差异（Python 的 text splitters 不继承 Runnable）。本课讲形态与契约，下一课逐行拆递归算法。

### 走读：Runnable 子类化的契约

```ts
export abstract class BaseDocumentTransformer<
  RunInput extends DocumentInterface[] = DocumentInterface[],
  RunOutput extends DocumentInterface[] = DocumentInterface[],
> extends Runnable<RunInput, RunOutput> {
  lc_namespace = ["langchain_core", "documents", "transformers"];

  abstract transformDocuments(documents: RunInput): Promise<RunOutput>;

  invoke(input: RunInput, _options?: BaseCallbackConfig): Promise<RunOutput> {
    return this.transformDocuments(input);
  }
}
```

*— langchain-core/src/documents/transformers.ts:15-38（commit 7704471）*

第一眼看类型参数：`RunInput`/`RunOutput` 都被 `extends DocumentInterface[]` 约束。这意味着 Transformer 的输入输出**只能是文档数组**——不能是字符串、不能是向量，类型系统在门口就拒绝了非 RAG 数据的流入。而两个泛型是分开声明的，这正是允许「一进多出」的类型学前提：`RunInput = Document[]` 时 `RunOutput` 完全可以是 `Document[]` 的另一个实例、另一个长度。

JSDoc 里有一句关键承诺：*These arrays do not necessarily have to have the same length.*（输入输出数组长度不必相同。）切分器正是靠这句话合法——一个大文档进来，一百个小 chunk 出去。

再看 `invoke`：直接 `return this.transformDocuments(input)`。也就是说 Runnable 的四大支柱里，Transformer 只覆盖 invoke（batch/stream/transform 走 Runnable 基类默认实现降级），真正的业务逻辑全部收敛在 `transformDocuments` 一个抽象方法上。**子类化 Transformer 的心智负担就是「实现一个数组到数组的变换」**，仅此而已。

### 观测盲区：形式是 Runnable，trace 树上隐身

`invoke` 的第二个参数名是 `_options`——下划线前缀在 TS 社区约定里就是「我收到了但我不用」。对比 L87 将要讲的 BaseRetriever.invoke：那里会手动编排 `CallbackManager.configure → handleRetrieverStart → ... → handleRetrieverEnd` 三相回调。而 Transformer 的 invoke **不做任何回调编排**，不创建 run span。

推论有三条：其一，在 LangSmith 的 trace 树里看不到切分这一步，它不会长出 run 节点；其二，传入的 callbacks/tags/metadata 在这一环静默失效（不影响功能，只影响观测）；其三，这也是一种务实取舍——切分是纯本地计算，开销极小，为它建 span 的观测收益低于成本。但如果你的自定义 Transformer 里有昂贵的远程调用（比如调 LLM 做摘要），**观测盲区就是你的责任**，需要在实现里自己接回调或自己打日志。

### 两种形态：变长与保长

```ts
export abstract class MappingDocumentTransformer extends BaseDocumentTransformer {
  async transformDocuments(documents: DocumentInterface[]): Promise<DocumentInterface[]> {
    const newDocuments = [];
    for (const document of documents) {
      const transformedDocument = await this._transformDocument(document);
      newDocuments.push(transformedDocument);
    }
    return newDocuments;
  }

  abstract _transformDocument(document: DocumentInterface): Promise<DocumentInterface>;
}
```

*— langchain-core/src/documents/transformers.ts:44-58（commit 7704471）*

`MappingDocumentTransformer` 把形态收窄为**一一映射**：类注释写明 *return exactly one transformed document for each input document*。它把「遍历循环 + 收集结果」这个样板代码固化在基类，子类只需实现单文档粒度的 `_transformDocument`。适用场景是**保数量的变换**：去重、metadata 清洗、文档摘要（一篇长文换一篇短文）、标记注入。注意循环是 `await` 串行的——如果单文档变换涉及远程调用，这里没有并发，大批量时可以考虑在 `_transformDocument` 内部自己做批处理。

非 Mapping 形态（直接继承 BaseDocumentTransformer）则面向**变长变换**：切分器（1 → N）、合并器（N → 1）、过滤（N → M）。下一课的 RecursiveCharacterTextSplitter 就属于这一支。

这个二分法本质上是**把「数量不变量」编码进了类层级**：你想写保长变换，编译器/基类循环替你保证不会手滑改变数组长度；你想写变长变换，就得自己面对整个数组。选型时先问一个问题——「我的变换会不会改变文档数量」。

### 桥接确认：TextSplitter 的继承链

切分器家族的根类 `TextSplitter` 直接 extends BaseDocumentTransformer——这就是「切分器即 Runnable」的全链证据。顺带记下三组默认值：chunkSize=1000、chunkOverlap=200、keepSeparator=false（注意 Recursive 子类会把 keepSeparator 覆盖为 true，下一课详拆）。同时构造器里有一道闸门：`if (this.chunkOverlap >= this.chunkSize) throw new Error("Cannot have chunkOverlap >= chunkSize")`（text_splitter.ts:43-45）——重叠不小于块长意味着无限重叠，直接在构造期拒绝。

### 本课小结

- 切分环的契约：`transformDocuments(documents: RunInput): Promise<RunOutput>`，输入输出都约束为文档数组，长度可不同。
- **Transformer 即 Runnable**：BaseDocumentTransformer extends Runnable，可 pipe 进 LCEL——TS 版的架构亮点。
- invoke 丢弃 `_options`、不建 run span：Transformer 在 trace 树上隐身，昂贵变换的观测是开发者自己的责任。
- Mapping/非 Mapping 两形态把「数量不变量」编码进类层级：保长用 Mapping（单文档 `_transformDocument`），变长直接继承基类。
- 下一课拆 RecursiveCharacterTextSplitter 的递归核心与 mergeSplits 滑窗——RAG 效果调优里最常被误用的两个参数就在那里。
