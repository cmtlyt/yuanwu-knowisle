### 一、两条轨道的交接仪式

L96/L97 从设计层面讲过 responseFormat 双策略的原理，本课做迁移实操：把一套典型的旧结构化输出管线（模型 → 文本 → StructuredOutputParser 解析 → 得到对象）迁移到 createAgent 的 responseFormat。先确认「旧 API 去哪了」——与大多数 classic API 不同，解析器一族不是被删除，而是**下沉 core 继续服役**：

| 类 | classic 路径:行 | core 路径:行 |
|---|---|---|
| StructuredOutputParser | output_parsers/structured.ts:30 | output_parsers/structured.ts:34 |
| JsonMarkdownStructuredOutputParser | output_parsers/structured.ts:129 | output_parsers/structured.ts:158 |
| JsonOutputToolsParser | output_parsers/openai_tools.ts:33 | output_parsers/openai_tools/json_output_tools_parsers.ts:124 |

同签名同名，改 import 即可。所以「结构化输出换代」的准确表述是：**解析器轨道继续存在（Runnable 链场景），但 agent 语境下的官方路径换成了 responseFormat 轨道**——schema 从「事后解析」变成「编译进请求」。本课两条轨道都实操，并给出选型判断。

### 二、旧管线复原：StructuredOutputParser 的三步走

旧管线的完整形状（按 classic 版类签名复原）：

```ts
import { z } from "zod";
import { ChatOpenAI } from "@langchain/openai";
import { StructuredOutputParser } from "langchain/output_parsers";
import { ChatPromptTemplate } from "@langchain/core/prompts";

const schema = z.object({
  sentiment: z.enum(["positive", "negative", "neutral"]),
  score: z.number().min(0).max(1),
  keywords: z.array(z.string()),
});

// 旧管线第一步：parser 自带 format instructions
const parser = StructuredOutputParser.fromZodSchema(schema);

const prompt = ChatPromptTemplate.fromMessages([
  ["system", "Extract structured info. {format_instructions}"],
  ["human", "{text}"],
]);

const chain = prompt
  .pipe(model)
  .pipe(parser);

const result = await chain.invoke({
  text: "电池续航惊人，充电也快，就是有点贵。",
  format_instructions: parser.getFormatInstructions(),
});
// result: { sentiment: "positive", score: 0.9, keywords: [...] }
```

三个机制值得注意：`getFormatInstructions()` 生成一段「请按 JSON 输出」的文本拼进 prompt——**协议靠 prompt 约定**，与 L113 的 ReAct 文本协议同源同弱；解析失败抛 OutputParserException，L97 讲过这条错误哲学（抛错可回喂 vs 返回 undefined）；parser 是 Runnable，所以能直接 `.pipe()` 进链。这套管线在 1.x 依然能跑（改 import 到 `@langchain/core/output_parsers`），但它的脆弱性也没变——模型少个逗号就抛异常。

两个补充机制让旧管线画像完整。其一，parser 的 Runnable 身份不是「恰好兼容」而是类型契约：core 的 BaseLLMOutputParser 直接 `extends Runnable<string | BaseMessage, T>`（output_parsers/base.ts:15-16），解析器天生可入链、可 batch、可流式，这是旧轨道在 1.x 继续服役的结构性理由。其二，旧族还有一个变体 JsonMarkdownStructuredOutputParser（classic output_parsers/structured.ts:129 ↔ core structured.ts:158 同签名下沉），它把 format instructions 的生成换成「markdown JSON 围栏」约定以降低模型格式漂移率（core 的 getFormatInstructions 见 structured.ts:165）——如果旧代码用的是这个变体，迁移时同样改 import 即可，不必在换代清单里把它当成另一套 API 处理。

### 三、新轨道实操：responseFormat 接入与 structuredResponse 读取

同一需求在新轨道下的写法。responseFormat 接受 Zod schema 时走 Overload 1（agents/index.ts:175-197，参数类型 `InteropZodType<StructuredResponseFormat>`），运行时经 transformResponseFormat（responses.ts:322）归一化成策略对象：

```ts
import { createAgent } from "langchain";
import { z } from "zod";

const schema = z.object({
  sentiment: z.enum(["positive", "negative", "neutral"]),
  score: z.number().min(0).max(1),
  keywords: z.array(z.string()),
});

const agent = createAgent({
  model: "openai:gpt-4o",
  responseFormat: schema,        // ← Zod 直接给，形状由重载 1 推断
  prompt: "Extract structured info from the user text.",
});

const result = await agent.invoke({
  messages: [{ role: "user", content: "电池续航惊人，充电也快，就是有点贵。" }],
});

const extracted = result.structuredResponse;
// extracted.sentiment === "positive"（类型级保证，无需运行时解析）
```

差异一目了然：format_instructions 不用手拼——schema 编译由框架完成；没有解析异常要兜——收尾节点在图内完成解析；类型从泛型链路推导——TS 直接知道 `extracted.keywords` 是 string[]。旧管线的三个手工步骤全部被吸收进 agent 图。

### 四、双策略实操与自动降级：toolStrategy / providerStrategy

Zod 直传时框架帮你选了默认策略；要显式控制就用两个工厂函数——`toolStrategy`（responses.ts:478 起，多个重载）与 `providerStrategy`（responses.ts:615 起）。先看两者的类结构差异（节选）：

```ts
export class ToolStrategy<_T = unknown> {
  constructor(
    public readonly schema: Record<string, unknown>,
    public readonly tool: { type: "function"; function: FunctionDefinition },
    public readonly options?: ToolStrategyOptions
  ) {}
  // fromSchema 自动生成工具名：
  function getFunctionName(name?: string) {
    return name ?? `extract-${++bindingIdentifier}`;
  }
}

export class ProviderStrategy<T = unknown> {
  public readonly schema: Record<string, unknown>;
  public readonly strict: boolean;   // 默认取 PROVIDER_STRATEGY_DEFAULT_STRICT
}
```

*— langchain/src/agents/responses.ts:54-110 / :164-200（commit 7704471，节选合并）*

ToolStrategy 的构造体暴露了它的本质：一个 `{ type: "function", function: FunctionDefinition }` 的工具定义，工具名自动生成 `extract-N`——**把 schema 伪装成隐藏工具，靠模型调用这个工具来交付结构**；ProviderStrategy 则把 schema 直传给模型 API 的原生结构化输出。接进 agent 并构建自动降级逻辑：

```ts
import { createAgent, providerStrategy, toolStrategy } from "langchain";

function pickStrategy(supportsNative: boolean) {
  return supportsNative
    ? providerStrategy(schema, /* strict */ true)
    : toolStrategy(schema);      // 伪装成 extract-N 工具
}

const supportsNative = detectJsonSchemaSupport("openai:gpt-4o"); // 能力探测（L97 的能力协商面）

const agent = createAgent({
  model: "openai:gpt-4o",
  responseFormat: pickStrategy(supportsNative),
});
```

选型规则一句话：**能力够用选 providerStrategy（协议由 API 保证，最稳），能力不足或跨多家提供商兜底选 toolStrategy（任何支持 tool calling 的模型都能走）**。两种策略可以在同一个应用里并存——比如主力模型走 providerStrategy、备用模型走 toolStrategy，这正是双策略设计存在的理由。

### 五、验收对照：新旧输出形状断言

迁移收尾要验证行为等价。写一组断言跑同一输入：

```ts
import { expect } from "vitest";

describe("结构化输出迁移验收", () => {
  it("旧管线：解析结果符合 schema", async () => {
    const legacy = await legacyChain.invoke({ text, format_instructions: parser.getFormatInstructions() });
    expect(schema.safeParse(legacy).success).toBe(true);
  });

  it("新轨道：structuredResponse 字段齐备且类型正确", async () => {
    const { structuredResponse } = await agent.invoke({ messages: [{ role: "user", content: text }] });
    expect(["positive", "negative", "neutral"]).toContain(structuredResponse.sentiment);
    expect(structuredResponse.score).toBeGreaterThanOrEqual(0);
    expect(structuredResponse.score).toBeLessThanOrEqual(1);
    expect(Array.isArray(structuredResponse.keywords)).toBe(true);
  });

  it("降级路径：toolStrategy 在无原生 json_schema 的模型上也能产出", async () => {
    const fallbackAgent = createAgent({ model, responseFormat: toolStrategy(schema) });
    const { structuredResponse } = await fallbackAgent.invoke({ messages: [{ role: "user", content: text }] });
    expect(schema.safeParse(structuredResponse).success).toBe(true);
  });
});
```

三条断言对应三条验收线：旧管线语义、新轨道类型化结果、降级路径可用性。跑通它们，结构化输出的换代就闭环了。这里埋一个钩子：agent 返回对象里的字段名为什么是 `structuredResponse`？这是新包 responses 协议的字段约定，L96 讲过它的图内收尾节点来源；迁移中如果发现旧代码把解析结果塞进了自定义 outputKey（旧 LLMChain 的 outputKey = \"text\" 之类），那部分逻辑要按 messages 状态模型重写（L104），不能照搬键名。

### 六、归一化管线走读与三类误用案例

先补一层机制走读，理解「Zod 直传」到底发生了什么。responseFormat 参数的运行时类型（responses.ts:294-306）是一个五路联合：InteropZodType / SerializableSchema / TypedToolStrategy / ToolStrategy / ProviderStrategy——重载面负责把五路输入映射到精确返回类型，而运行时统一交给 transformResponseFormat（responses.ts:322）编译成策略对象。`toolStrategy` 与 `providerStrategy` 工厂本身也各有多个重载（toolStrategy 见 responses.ts:478-555，覆盖单个 Zod、Zod 数组、JSON Schema 及数组；providerStrategy 见 responses.ts:615-628，覆盖 Zod 与 JSON Schema）。把这条链记下来：**输入形态 → 工厂/重载 → transformResponseFormat → 策略实例 → 图内收尾节点解析**。迁移调试时若 responseFormat 行为不符预期，从 transformResponseFormat 的输出开始逐环检查，比直接猜 Zod 语法快得多。

三个高频误用，全部有源码依据。**误用一：无 responseFormat 时去读 structuredResponse。** responses.ts:26 的类型注释写明：*When this type is used, the structuredResponse property should not be present in the result*——没配 responseFormat 的 agent 返回对象里根本没有这个属性，读它永远是 undefined。迁移旧代码时如果发现「agent 没返回结构化结果」，先确认 responseFormat 是否真的传了，而不是去调试消息流。

**误用二：假设 strict 的默认行为全提供商一致。** ProviderStrategy 的 strict 默认值来自常量 PROVIDER_STRATEGY_DEFAULT_STRICT（responses.ts:33），且 :35-40 的注释专门讨论了 OpenAI parse() 方法在 strict 模式下的行为差异——strict 是「提供商相关的能力开关」，不是跨提供商的统一承诺。旧 OutputParser 管线从不涉及 strict，迁移时要为每个目标提供商重新验证 strict 的实际效果，不能沿用「旧管线在 A 提供商能跑所以 B 也行」的直觉。

**误用三：在 agent 外面再手工串一层解析器。** StructuredOutputParser 在 core 同名可用（structured.ts:34，getFormatInstructions 实现在 :87），于是有人会写出「createAgent + responseFormat，再对结果跑一遍 parser」的双重解析——两条轨道的解析点不同（parser 在链上事后解析文本，responseFormat 在图内收尾节点解析），双重解析轻则浪费一次校验，重则 schema 不一致时互相掩盖错误。判别原则：**有 agent 就用 responseFormat，无 agent（纯 Runnable 链）才用解析器轨道**，两者泾渭分明。

最后给一个「旧轨道保留价值」的收尾判断，迁移评审时按三条线查：纯 Runnable 链（prompt.pipe(model).pipe(parser)）且无 agent 循环 → 旧轨道是正解，不必为换代而换代；需要流式解析中间产物 → 解析器族有专门的流式基类支撑（core output_parsers/transform.ts:20 的 BaseTransformOutputParser 与 :69 的 BaseCumulativeTransformOutputParser，后者在 :119 用 `accGen.concat(chunkGen)` 累积合并 chunk），responseFormat 没有等价的流式解析面；需要把解析错误回喂重试 → 旧轨道的 OutputParserException + 链外 catch 是既有路径，新轨道对应物是 toolStrategy 的工具调用失败处理。三条线都指向旧轨道时，迁移清单上这一项就写「保留并改 import」——换代清单不是清零清单。

### 本课小结

- StructuredOutputParser 族**下沉 core 继续可用**（classic:30 ↔ core:34 同签名），Runnable 链场景无需迁移；agent 语境才换 responseFormat。
- 旧管线的 format_instructions 手拼、OutputParserException 兜底、泛型推导三件事，在 responseFormat 轨道全部被框架吸收。
- ToolStrategy（responses.ts:54）= schema 伪装成 extract-N 隐藏工具；ProviderStrategy（responses.ts:164）= schema 直传 API + strict 开关；14 个重载（agents/index.ts:175 起）只为把输入形态精确映射到返回类型。
- 验收断言三件套：旧语义、新类型、降级路径。下一课处理更轻的搬家族：Prompt 与 OutputParser 里那些「只需改 import」的原样同名类。
