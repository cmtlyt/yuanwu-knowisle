### 不存全量的两种哲学：重放 vs 遗忘

Channel 系统的收官课。前面八种通道都在 checkpoint 里存「当前值」，本课的两种通道反其道而行：**DeltaChannel 选择不存全量——只存哨兵，读取时沿祖先链重放写入重建状态；UntrackedValueChannel 选择不追踪——checkpoint 里永远没有它的影子**。前者是存储优化的极致（Beta 阶段），后者是对「运行时状态不该被持久化」的正面承认。顺带把 checkpoint 的三字典结构 v:4 一次讲透。

### DeltaChannel：checkpoint 里缺席的通道

*— channels/delta.ts:84-122, 217-219（有裁剪，commit fa426b2）*

注意三泛型的最后一个：CheckpointType 是 `undefined`——这与 UntrackedValueChannel 相同的签名，但语义完全不同（下文对照）。checkpoint() 返回 undefined 后，createCheckpoint 的循环里 `if (isDeltaChannel(channel)) continue`——**通道从 channel_values 字典里消失**（channels/base.ts:349-352）。那状态在哪？在每个超步的 checkpoint_writes 里（任务写入本来就逐条持久化），重建时 channelsFromCheckpoint 批量调 saver 的 `getDeltaChannelHistory` 拿到祖先写入序列，逐通道 replayWrites（channels/base.ts:559-576）。

### 批量不变式：重放正确的唯一前提

```ts
// reducer(reducer(state, xs), ys) === reducer(state, xs.concat(ys))
export type DeltaReducer<ValueType, UpdateType = unknown> = (
  state: ValueType,
  writes: UpdateType[]
) => ValueType;
```

*— channels/delta.ts:26-37（commit fa426b2）*

重放的批次划分与产生时的批次划分几乎必然不同（恢复点不同、合并策略不同），所以 reducer 必须对批次切分不敏感——这就是批量不变式（结合律）的全部动机。`messagesDeltaReducer` 是官方示范：单遍线性扫描完成去重 + tombstone 置 null，并用 `Symbol.for` 品牌标记让 ESM/CJS 双副本加载时也能被识别（graph/messages_reducer.ts:269-284）。快照节奏是两条线：**per-channel 更新计数到 snapshotFrequency（默认 100）或全局超步数到 DELTA_MAX_SUPERSTEPS_SINCE_SNAPSHOT（默认 5000）**，任一触发就写入完整 DeltaSnapshot，给不再收到写入的通道限制重放深度（channels/delta.ts:59-64）。

### replayWrites：最后一个 Overwrite 是重置点

```ts
public replayWrites(writes: CheckpointPendingWrite[]): void {
  const values = writes.map((w) => w[2]);
  if (values.length === 0) return;
  let base = this.value as ValueType;
  let start = 0;
  for (let i = 0; i < values.length; i += 1) {
    const [isOverwrite, overwriteValue] = _getOverwriteValue<ValueType>(values[i]);
    if (isOverwrite) {
      base = overwriteValue !== undefined && overwriteValue !== null
        ? overwriteValue : this.initialValueFactory();
      start = i + 1;
    }
  }
  const remaining = values.slice(start) as UpdateType[];
  this.value = remaining.length > 0 ? this.reducer(base, remaining) : base;
}
```

*— channels/delta.ts:146-165（commit fa426b2）*

祖先链里最后一个 Overwrite 之前的所有写入都不必重放——它就是新的基准。运行时的 update 同样尊重 Overwrite 的霸权：一旦出现，**整步的兄弟写入（无论先后）全部丢弃**，直接以 Overwrite 值（或初值）为准（channels/delta.ts:184-193），与 BinaryOperatorAggregate 的单 Overwrite 规则对齐。

*— channels/untracked_value.ts:21-87（有裁剪，commit fa426b2）*

`MISSING = Symbol.for("langgraph.channel.missing")` 哨兵代替「空数组包装」表达未写入。guard 默认 true（与 LastValue 同样的并发单写约束），guard=false 时静默取最后一个。设计意图写在类文档里：**DB 连接、临时缓存、运行时配置这类状态存进 checkpoint 反而是 bug**——恢复出的旧连接早已失效。注意与 DeltaChannel 的本质区别：Delta 的 undefined 是「值在别处，可重建」，Untracked 的 undefined 是「值没有持久形态，恢复即空」。

### checkpoint 结构 v:4 与版本时钟

```ts
return {
  v: 4,
  id: options?.id ?? uuid6(step),
  ts: new Date().toISOString(),
  channel_values: values,
  channel_versions: channelVersions,
  versions_seen: markBumpsSeen(checkpoint.versions_seen, bumped, options?.triggerToNodes),
```

*— channels/base.ts:366-378（有裁剪，commit fa426b2）*

三字典：channel_values（按通道快照值，Delta 通道缺席）、channel_versions（版本时钟，写一次前进一版）、versions_seen（每个节点上次读到的版本，interrupt 与增量恢复的判定依据）。`uuid6(step)` 让 id 按步数单调递增，字符串比较即时间排序。还有一个精妙的坑被专门修补：快照触发的版本 bump 不是写入，若不同步推进 versions_seen，会误触发 interruptBefore 和订阅者——`markBumpsSeen` 用 SNAPSHOT_BUMPS 键记录「真实读到哪版」，`versionsSeenWithoutBumps` 读取时把 bump 撤回（channels/base.ts:391-456）。这套版本时钟将在 L74（isResuming）与 L75（tick）成为主角。

### 易混淆点辨析：channel_values 里「缺席」有三种含义

createCheckpoint 的循环体其实有四个分支，对应「通道在快照里」的三种不同缺席（channels/base.ts:326-362）。第一种：普通通道 `checkpoint()` 抛 EmptyChannelError 被捕获后 no-op——通道为空，channel_values 里缺席，恢复时等价于 undefined，这是「真空」。第二种：`isDeltaChannel(channel)` 显式 `continue`，源码注释写得分明：`Omitted from channel_values; reconstructed from ancestor writes`（base.ts:344-350）——缺席但**可重建**，值活在祖先写入链里。第三种：通道在 `channelsToSnapshot` 白名单里时写 `new DeltaSnapshot(channel.get())` blob，且若该通道版本自上次存储后未移动还要专门 bump 版本（base.ts:326-342）——这是快照步，Delta 通道此时反而「在场」。三种缺席外观一样（key 不在字典里），语义分别是「空」「在别处」「这是快照」，恢复路径完全不同：空 → fromCheckpoint(undefined)；在别处 → getDeltaChannelHistory 回放；快照 → isDeltaSnapshot 识别后直取 `.value`。读懂这三种缺席，就读懂了为什么 channelsFromCheckpoint 要先探测形态再决定恢复策略（base.ts:559-576）。

UntrackedValueChannel 提供了第四种风味，但在通道内部而非快照层面：它用 `MISSING = Symbol.for("langgraph.channel.missing")` 哨兵表达「未写入」（untracked_value.ts:5、37），而不是 LastValue 那样的空数组包装——反正它 checkpoint() 永远返回 undefined，快照层面根本不会出现它的 key。还有一个小边界顺带记下：构造 DeltaChannel 时 `snapshotFrequency` 必须是正整数，传 0 或非整数直接抛 `snapshotFrequency must be a positive integer`（channels/delta.ts:112-115）——快照节奏是恢复正确性的一部分，不接受无效配置。

### 本课小结

- DeltaChannel 的 checkpoint() 返回 undefined 是「缺席」而非「空」：重建靠 getDeltaChannelHistory 祖先重放，reducer 必须满足批量不变式。
- 快照双节奏：snapshotFrequency 默认 100 次更新，或全局 5000 超步兜底；最后一个 Overwrite 是重放的重置点。
- UntrackedValueChannel 的 undefined 是「永不持久化」：连接/缓存类状态恢复即重置，guard=false 可放宽并发写。
- checkpoint v:4 = 三字典 + uuid6 单调 id + markBumpsSeen 修补快照 bump 的误触发。
- channel_values 里的缺席有三种语义：空（EmptyChannelError 吞掉）、在别处（Delta 显式 continue）、快照（DeltaSnapshot blob + 可能 bump），恢复策略各不相同。
