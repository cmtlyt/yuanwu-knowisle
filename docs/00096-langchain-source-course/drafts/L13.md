### 调用闭环的另一半

L12 结尾留了钩子：AIMessage.tool_calls[].id 是调用链路键。本课的 ToolMessage 就是链路的另一半——模型发起调用，工具产生结果，**ToolMessage 用三个字段把「结果」装回消息世界**：tool_call_id 负责关联，content/artifact 负责装载，status 负责宣告成败。除了三字段，本课还讲一个容易错过的设计：ToolMessage 自己实现了 DirectToolOutput 标记，让工具可以「直接返回消息」。**核心结论：ToolMessage 的每个字段都在回答一个协议问题——这个结果属于哪次调用、模型能看到多少、执行成没成功**。

### 三字段定义：必填的关联键与可选的双通道

```ts
export interface ToolMessageFields<
  TStructure extends MessageStructure = MessageStructure,
> extends BaseMessageFields<TStructure, "tool"> {
  /**
   * Artifact of the Tool execution which is not meant to be sent to the model.
   *
   * Should only be specified if it is different from the message content, e.g. if only
   * a subset of the full tool output is being passed as message content but the full
   * output is needed in other parts of the code.
   */
  artifact?: any;
  tool_call_id: string;
  status?: "success" | "error";
  metadata?: Record<string, unknown>;
}
```

*— langchain-core/src/messages/tool.ts:13-28（commit 7704471）*

字段类型本身就写满了协议。**tool_call_id: string 没有 ? 修饰**——类型层面强制关联：每条工具结果必须声明它属于哪次调用，agent 循环据此把结果路由回对话流（历史对话里模型看见的是「我调用了 X，结果是……」的配对序列）。**artifact?: any 的注释是设计文档**：双通道的分工在注释里说得直白——content 是给模型的（会被送进上下文），artifact 是给程序的（不进上下文）；且只在两者不同时才需要 artifact，content 放子集、artifact 放全量是最典型的用法。这个设计直接决定工程实践：大文件、数据集、二进制产物走 artifact，模型的上下文里只留摘要或错误说明。status 是可选的三态之一（success/error/undefined），metadata 补一个自由字典。

类本体把 interface 的字段逐一落地（tool.ts:53-118），并多了一个类级成员：

### DirectToolOutput：让工具直接返回消息

```ts
export interface DirectToolOutput {
  readonly lc_direct_tool_output: true;
}

export function isDirectToolOutput(x: unknown): x is DirectToolOutput {
  return (
    x != null &&
    typeof x === "object" &&
    "lc_direct_tool_output" in x &&
    x.lc_direct_tool_output === true
  );
}
```

*— langchain-core/src/messages/tool.ts:37-48（commit 7704471）*

接口注释交代了机制全貌：自定义工具被 ToolCall 调用后，如果返回值不是 DirectToolOutput 实例，输出会被自动 coerce 成字符串再包装进 ToolMessage；反之则原样通行。ToolMessage 类自己实现这个接口（lc_direct_tool_output = true），形成一条**穿透路径**：工具函数内部直接构造好 ToolMessage（带上 status、artifact、metadata），返回后不走「字符串化再包一层」的默认流程，产物直接成为消息。判型函数用结构检查（in + ===true）而非 instanceof——这个标记是跨包安全的鸭子类型，与 L05 的 symbol 思路同源但更轻量。L23 讲 ToolRuntime 注入时，writer 通道是这条路径的进阶版，本课先记住标记语义。

### 双签名构造：类型与历史习惯的和解

```ts
  constructor(
    fields: $InferMessageContent<TStructure, "tool"> | ToolMessageFields,
    tool_call_id: string,
    name?: string
  );

  constructor(fields: ToolMessageFields<TStructure>);

  constructor(
    fields:
      | $InferMessageContent<TStructure, "tool"> | ToolMessageFields<TStructure>,
    tool_call_id?: string,
    name?: string
  ) {
    const toolMessageFields: ToolMessageFields<TStructure> =
      typeof fields === "string" || Array.isArray(fields)
        ? ({
            content: fields,
            name,
            tool_call_id: tool_call_id!,
          } as ToolMessageFields<TStructure>)
        : fields;
    super(toolMessageFields);
    this.tool_call_id = toolMessageFields.tool_call_id;
    this.artifact = toolMessageFields.artifact;
    this.status = toolMessageFields.status;
    this.metadata = toolMessageFields.metadata;
  }
```

*— langchain-core/src/messages/tool.ts:90-118（commit 7704471）*

第一签名 `(fields, tool_call_id, name)` 是历史形态的保留：早期 API 是 `new ToolMessage(content, toolCallId, name)`，第二签名 `({content, tool_call_id, ...})` 是 fields 形态的规范化。实现里用 `tool_call_id!` 非空断言兜住旧签名——若调用方两个签名都没给全，这里不做运行时校验，错误会推迟到消费侧。教学含义：**新代码一律用 fields 形态**，双签名是兼容层而非推荐面；type 判型（tool.ts:125-143）与 AI 消息同构，symbol + type 两层检查，此处不再重复。

### concat：status 的保守合并与 artifact 的通用合并

```ts
  concat(chunk: ToolMessageChunk<TStructure>) {
    const Cls = this.constructor as Constructor<this>;
    return new Cls({
      content: mergeContent(this.content, chunk.content),
      additional_kwargs: _mergeDicts(
        this.additional_kwargs,
        chunk.additional_kwargs
      ),
      response_metadata: _mergeDicts(
        this.response_metadata,
        chunk.response_metadata
      ),
      artifact: _mergeObj(this.artifact, chunk.artifact),
      tool_call_id: this.tool_call_id,
      id: this.id ?? chunk.id,
      status: _mergeStatus(this.status, chunk.status),
    });
  }
```

*— langchain-core/src/messages/tool.ts:192-209（commit 7704471）*

与 L11 的 chunk 套路相比多了两行专属逻辑。**status 走 _mergeStatus**（base.ts:172-180）：`if (left === "error" || right === "error") return "error"; return "success"`——错误一旦出现就在合并链里永久保留，这是保守主义合并：聚合多个增量时宁可误报失败也不漏报。**artifact 走 _mergeObj**（base.ts:669-700）：类型相同才合并——双字符串拼接、双数组走 _mergeLists、双对象走 _mergeDicts、类型不匹配抛错。对比 status 的宽容（任何输入都出结果），_mergeObj 对类型冲突宁可抛错也不猜测，两套函数的容错取向截然不同：status 是「结果语义」，错就是错；artifact 是「数据结构」，乱就是 bug。tool_call_id 不参与合并直接取 this——同一条工具结果的增量切片必然共享同一 id。

### 关联链全景：一个 id 的三站旅程

tool_call_id 只在 ToolMessage 上出现，但它串起的链路横跨三课，值得把全景画出来。**第一站在模型输出侧**：AIMessage.tool_calls[] 的每个元素带 id（可缺省，L12 的结构表里它标着「可选完整标识」），agent 循环据此逐个发起工具执行。**第二站在框架注入侧**：StructuredTool.invoke 检测到输入是 ToolCall 时，把整个 toolCall 挂进 enrichedConfig.toolCall（libs/langchain-core/src/tools/index.ts:175-209 附近的 invoke 逻辑）——工具函数第二参数 runtime 里读到的 toolCallId/toolCall 就是从 config 这条暗道进来的（E17 的 ToolRuntime 契约：state/toolCallId/toolCall/config/context/store/writer）。**第三站在结果回填侧**：工具执行完，框架把返回值包装成 ToolMessage 时带上同一个 tool_call_id，消息历史里于是形成「AIMessage(tool_calls) → ToolMessage(tool_call_id)」的配对序列——provider（OpenAI/Anthropic）要求 tool 结果消息必须携带发起调用的 id，这个字段不是 LangChain 的发明，而是 provider API 的硬约束在消息模型上的投影。链路任何一环断掉（手工构造消息历史时漏 id、或重放时 id 对不上）都会在 provider 侧报 400 级错误——这就是 pitfalls 里「tool_call_id 必填」的真实代价。顺带把 metadata 字段说清：ToolMessageFields 里的 `metadata?: Record<string, unknown>`（tool.ts:27）是工具结果的自定义元数据（执行耗时、来源版本之类），它进消息但不进模型上下文的语义约束与 artifact 类似——**artifact 藏全量、metadata 藏注脚、content 给模型**，三层各司其职。

### 本课小结

- 三字段协议：tool_call_id（必填关联键，与 AIMessage.tool_calls[].id 配对）、artifact（不进模型上下文的全量产物通道）、status（错误即数据，非控制流）。
- artifact 的注释即设计文档：仅当与 content 不同时才指定，content 子集 + artifact 全量是典型分工。
- DirectToolOutput 标记让工具直接返回 ToolMessage，绕过字符串化包装；ToolMessage 自己也实现了该标记。
- concat 里 status 用 error 优先的保守合并，artifact 用类型敏感的 _mergeObj，两套容错取向与字段语义一一对应。
