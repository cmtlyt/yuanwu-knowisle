### 读写契约：五个抽象方法、一个排序键、一个双态 serde

上一课解决了「checkpoint 里存什么」；本课解决「谁来存、怎么存才可重放」。核心结论：**BaseCheckpointSaver 把持久化压缩成五个方法，而正确性的全部重量压在一个排序键上——存储端返回的写入顺序必须与 live 执行顺序一致，否则顺序敏感的 reducer 会重建出不同的值**。framework 课型，langgraphjs（commit fa426b2）逐段走读，最后手写一个自定义 checkpointer 验证契约。

### 走读：BaseCheckpointSaver 五抽象

```ts
export abstract class BaseCheckpointSaver<V extends string | number = number> {
  serde: SerializerProtocol = new JsonPlusSerializer();
  constructor(serde?: SerializerProtocol) { this.serde = serde || this.serde; }

  toJSON(): string { return `[${this.constructor.name}` + `]`; }   // 防 stringify 深入 pg Pool

  async get(config: RunnableConfig): Promise<Checkpoint | undefined> {
    const value = await this.getTuple(config);
    return value ? value.checkpoint : undefined;
  }
  abstract getTuple(config: RunnableConfig): Promise<CheckpointTuple | undefined>;
  abstract list(config: RunnableConfig, options?: CheckpointListOptions): AsyncGenerator<CheckpointTuple>;
  abstract put(config, checkpoint: Checkpoint, metadata: CheckpointMetadata, newVersions: ChannelVersions): Promise<RunnableConfig>;
  abstract putWrites(config, writes: PendingWrite[], taskId: string, taskPath?: string): Promise<void>;
  abstract deleteThread(threadId: string): Promise<void>;
}
```

五个抽象方法的职责矩阵：`getTuple` 单读（get 是它的便捷壳）；`list` 是 **AsyncGenerator**——流式列举整个线程的历史检查点，后端实现时注意这是惰性接口，别一次性拉全量；`put` 写入完整检查点并返回**新 config**（调用方拿这个 config 继续寻址）；`putWrites` 存超步内的中间写入（interrupt 恢复与 DeltaChannel 重建靠它）；`deleteThread` 清线程（GDPR/多租户清理的落点）。serde 字段默认实例化 JsonPlusSerializer 且构造器可注入替换——**自定义存储器可以换加密序列化**，这是安全合规场景的官方扩展点。

### 排序键：可重放性的全部秘密

```ts
/** Sort key for the writes of one superstep: `(task_path, task_id, idx)`. */
export type WritesSortKey = readonly [string, string, number];

export function writesSortKey(taskPath: string, taskId = "", idx = 0): WritesSortKey {
  return [taskPath, taskId, idx];
}

export function compareWritesSortKeys(a: WritesSortKey, b: WritesSortKey): number {
  if (a[0] !== b[0]) return compareStringsByCodePoint(a[0], b[0]);
  if (a[1] !== b[1]) return compareStringsByCodePoint(a[1], b[1]);
  return a[2] < b[2] ? -1 : a[2] > b[2] ? 1 : 0;
}
```

*— langgraphjs/libs/checkpoint/src/base.ts:113-154（commit fa426b2）*

putWrites 的 JSDoc（base.ts:216-227）把问题说得很直白：live 执行按 (taskPath, taskId, idx) 序应用超步写入，**重放若按其它顺序，顺序敏感（但批内序不变）的 reducer 会重建出不同的值**。所以契约规定：实现者应尽量持久化 taskPath，且 getTuple/list 返回 pendingWrites 必须按 writesSortKey 排序。无路径的旧数据用空串排序——空串按 code point 排在任何真实 taskPath 之前，恰好对齐「live 执行中输入也是最先应用的」这一事实。

`compareWritesSortKeys` 的注释还藏着一个跨语言细节：字符串比较按 **Unicode code point**（对齐 Python str 序）而不是 UTF-16 code unit 序——增补平面字符（如 emoji）在两种序里位置不同。注释明确警告：不要用 `<`、`localeCompare` 或默认 `Array.prototype.sort` 直接比较 key 元组。分布式 checkpointer（pg/redis）实现时这是最容易翻车的点。MemorySaver 侧的 `_orderedWrites`（memory.ts:173-199）就是排序的消费方示范：从存储键 `${taskId},${idx}` 解析回 taskId/idx，与记录里的 taskPath 组装排序键后排序。

### JsonPlusSerializer：双态 serde 协议

```ts
export class JsonPlusSerializer implements SerializerProtocol {
  protected _dumps(obj: any): Uint8Array {
    return new TextEncoder().encode(
      stringify(obj, (_, value) => _default(value)));
  }
  async dumpsTyped(obj: any): Promise<[string, Uint8Array]> {
    if (obj instanceof Uint8Array) return ["bytes", obj];
    else return ["json", this._dumps(obj)];
  }
  async loadsTyped(type: string, data: Uint8Array | string): Promise<any> {
    if (type === "bytes") return typeof data === "string" ? new TextEncoder().encode(data) : data;
    else if (type === "json") return this._loads(typeof data === "string" ? data : new TextDecoder().decode(data));
    else throw new Error(`Unknown serialization type: ${type}`);
  }
}
```

*— langgraphjs/libs/checkpoint/src/serde/jsonplus.ts:227-261（commit fa426b2）*

"Typed" 协议的名字来自返回二元组 `[类型标签, 二进制]`：**bytes 直通**（Uint8Array 原样进出，零转换开销——通道里的大二进制负载不会被 JSON 化）与 **json + reviver**（其余一切）。`_default` replacer 处理 JSON 不友好类型（jsonplus.ts:204-225）：Set/Map 记构造参数重建、RegExp 存 source/flags、Error 存 message、Send 对象特判保留 node/args/timeout。**任意自定义 class 不在白名单内**——reviver 还原不了类型，这是「checkpoint 里别放任意对象」的技术根源（L88 埋的伏笔在此兑现）。`SerializerProtocol` 接口只有 dumpsTyped/loadsTyped 两个方法（serde/base.ts:3-5），两态之外想加加密/压缩，继承替换即可——serde 字段是注入点。

### BaseStore：与 checkpoint 平行的另一个持久化面

设计模式一眼见底：**唯一抽象方法是 batch，get/search/put 全是 batch 的语法糖**——后端只需实现一个方法，事务性批量写天然获得。两个值得注意的能力：namespace 是分层路径（`["users", userId, "memories"]`），`validateNamespace` 做路径合法性校验；search 的 options 带 `query`——**语义检索直接内建在 store 接口里**（IndexConfig 声明索引字段，SearchItem 带相似度分）。这与 checkpoint 的分工：**checkpoint 存 thread 级会话状态（有版本时钟、可 resume）；Store 存跨线程的长期记忆（用户画像、事实沉淀，可语义检索）**。对话内记忆给 checkpoint，跨会话记忆给 Store——一条边界口诀。

### MemorySaver 内部：复合键、写入排序与三重防污染

官方内存实现把上面两条契约的「消费端」都演了一遍，值得单独看一眼。存储键不是手拼分隔符，而是 `JSON.stringify([threadId, checkpointNamespace, checkpointId])`（memory.ts:93-101）——JSON 数组序列化天然无歧义，解析侧 `_parseKey` 直接 `JSON.parse` 回三元组，避免了「threadId 里恰好含分隔符」这类经典事故。

防污染是这一课最值得搬进自己工程的三层防御。`assertSafeStorageKey`（memory.ts:62-91）拒绝三类值：非字符串（错误信息里带上实际类型）、空字符串（checkpoint_ns 除外）、以及 `POLLUTION_KEYS = { __proto__, constructor, prototype }` 三个魔法键（memory.ts:30）——用它们当 thread_id 会直接抛错。注释把设计意图说得清楚：底层存储对象用 `Object.create(null)` 无原型构造（memory.ts:106-117），即使恶意键绕过校验也够不到 Object.prototype；**但读路径 getTuple 仍然重新校验一遍**（memory.ts:225-235）——「写路径查过不够，读路径不能从原型链上取回数据」，纵深防御的双保险。

`_orderedWrites`（memory.ts:173-199）是排序契约的消费端示范：先对每条写入记录**一次性**算出排序键（`lastIndexOf(",")` 从存储键 `${taskId},${idx}` 解析回 taskId/idx，与记录第四元素 taskPath 组装），缓存后再 sort——注释强调「Compute each record's key once, then sort on the cached keys」，避免排序比较器里重复解析。getTuple 返回 pendingWrites 前正是走这条 `_orderedWrites → _deserializeOrderedWrites` 管线，把上一节的「按 writesSortKey 有序返回」从承诺变成代码。

### 手写对照：一个 40 行的自定义 checkpointer

```ts
import { BaseCheckpointSaver, Checkpoint, CheckpointTuple, CheckpointMetadata, ChannelVersions } from "@langchain/langgraph-checkpoint";
import type { RunnableConfig } from "@langchain/core/runnables";

class MapCheckpointer extends BaseCheckpointSaver {
  // thread_id -> (ns, checkpoint_id) -> tuple
  private store = new Map<string, Map<string, CheckpointTuple>>();
  private writes = new Map<string, { key: [string, string, number]; write: any }[]>();

  async getTuple(config: RunnableConfig): Promise<CheckpointTuple | undefined> {
    const threadId = config.configurable?.thread_id;
    const cpId = config.configurable?.checkpoint_id;
    const thread = this.store.get(threadId ?? "");
    if (!thread) return undefined;
    // 未指定 id：取「最新」——真实实现需按 uuid6 时间序取最大
    return thread.get(cpId ?? this.latestId(threadId));
  }

  async *list(config: RunnableConfig, options?): AsyncGenerator<CheckpointTuple> {
    // 沿 parentConfig 从最新回溯，逐个 yield
    let tuple = await this.getTuple(config);
    while (tuple) { yield tuple; tuple = tuple.parentConfig ? await this.getTuple(tuple.parentConfig) : undefined; }
  }

  async put(config, checkpoint: Checkpoint, metadata: CheckpointMetadata, newVersions: ChannelVersions): Promise<RunnableConfig> {
    const threadId = config.configurable?.thread_id;
    const next = { config, checkpoint, metadata, parentConfig: config };
    // 写入序列化后的 checkpoint + metadata（这里省略 serde 调用，真实实现须 dumpsTyped）
    const thread = this.store.get(threadId) ?? new Map();
    thread.set(checkpoint.id, next);
    this.store.set(threadId, thread);
    return { ...config, configurable: { ...config.configurable, checkpoint_id: checkpoint.id } };
  }

  async putWrites(config, writes: PendingWrite[], taskId: string, taskPath?: string): Promise<void> {
    const threadId = config.configurable?.thread_id;
    const cpId = config.configurable?.checkpoint_id ?? "";
    const list = this.writes.get(`${threadId}:${cpId}`) ?? [];
    writes.forEach((w, idx) =>
      list.push({ key: writesSortKey(taskPath ?? "", taskId, idx), write: { taskId, idx, value: w } })
    );
    // 关键：读取时按 compareWritesSortKeys 排序返回——契约就在这一行
    list.sort((a, b) => compareWritesSortKeys(a.key, b.key));
    this.writes.set(`${threadId}:${cpId}`, list);
  }

  async deleteThread(threadId: string): Promise<void> {
    this.store.delete(threadId);
  }
}
```

验收要点三条：`put` 必须返回带新 checkpoint_id 的 config（寻址契约）；`getTuple` 无 id 时必须取时间序最新（uuid6 保证 id 可比）；`putWrites` 后的 pendingWrites 必须按 writesSortKey 有序返回（重放契约）。内存版三行搞定，换 pg/redis 时难点全部集中在排序与序列化两处——**契约的复杂度不在接口数量，而在这两个正确性陷阱**。

### 本课小结

- BaseCheckpointSaver 五抽象：getTuple/list/put/putWrites/deleteThread；serde 可注入替换（加密序列化入口）。
- putWrites 排序契约：pendingWrites 按 (taskPath, taskId, idx) 返回，空路径排最前对齐输入应用序；code point 比较对齐 Python str 序。
- JsonPlusSerializer 双态协议：bytes 直通 + json/reviver 白名单（Set/Map/RegExp/Error/Send）；任意 class 不保真。
- BaseStore 与 checkpoint 分工：唯一抽象 batch、命名空间分层、内建语义检索——跨线程长期记忆，与会话状态互不替代。
- 模块七记忆与缓存三课到此收束；下一课转向可观测：Tracer 家族与 langsmith 硬依赖——trace 数据模型是谁定义的。
