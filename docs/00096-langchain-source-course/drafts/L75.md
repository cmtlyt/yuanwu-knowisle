### 定锚：把超步的「骨架」与「肌肉」分开

L74 解决了「是不是 resume」，本课回答「resume 之后每一超步到底发生了什么」。**tick() 是 PregelLoop 的心脏，但它不是执行器**——它做的是 BSP（Bulk Synchronous Parallel）模型的同步阶段：收集上一批任务的写入、应用到通道、存 checkpoint、准备下一批任务；而任务的并发执行在 `PregelRunner.tick`（L77）里，二者交替调用推进整张图。把这条「收写 → applyWrites → checkpoint → 准备 → 派发」的流水线逐段读通，后面 L76 的写排序、L79 的 durability 三档才有了挂靠点。

### 第一段：三种入口状态分流

```ts
async tick(params: { inputKeys?: string | string[] }): Promise<boolean> {
  if (this.status !== "pending") {
    throw new Error(
      `Cannot tick when status is no longer "pending". Current status: "${this.status}"`
    );
  }
  if (![INPUT_DONE, INPUT_RESUMING].includes(this.input)) {
    await this._first(inputKeys);
  } else if (this.toInterrupt.length > 0) {
    this.status = "interrupt_before";
    throw new GraphInterrupt();
  } else if (
    Object.values(this.tasks).every((task) => task.writes.length > 0)
  ) {
    // finish superstep
    ...
  } else {
    return false;
  }
```

*— pregel/loop.ts:1194-1309（commit fa426b2）*

入口分三路：**真实输入**（非哨兵）先走 `_first`——首超步加载 checkpoint、处理 Command、决定 skipDoneTasks；**INPUT_RESUMING/INPUT_DONE 哨兵**则跳过输入处理直接进收尾。第二路的 `this.toInterrupt` 是上一轮就挂起的待中断任务清单——resume 后如果这些任务仍触发断点，立即抛 `GraphInterrupt`。第三路是本课最关键的分支：**所有任务都已有 writes**——resume 场景下任务在上一个进程里就跑完了，此时把存量 writes 交给 `_applyWrites` 正常收尾，而不是重新执行。最后 `status !== "pending"` 的守卫说明 tick 不可重入并发：一个 loop 一次只推进一个超步。

这一段的顺序是硬约束，注释给了理由：values 事件可以携带 checkpoint envelope（供 streamEvents v3 的分支/时间旅行 UI 使用），**envelope 必须指向捕获本超步最终状态的快照**，所以 `_putCheckpoint` 必须先行。sync 档再进一步：等全部持久化 promise 落定才发 values——这是「values 到达 ⇒ checkpoint 已在存储里」这条不变式的唯一保证点（三档语义的完整展开见 L79）。Overwrite 强制快照则是 DeltaChannel 的正确性细节：live 的 `update` 已经丢弃了被覆盖的兄弟值，稀疏重放必须从覆盖后的值起步，相关计数器机制在 L79 展开。

三个闸门的次序有讲究。**interruptBefore 在派发前**：断点命中就以 `throw GraphInterrupt` 停止——异常即控制流，上层把 interrupts 持久化为 INTERRUPT 写。**drain 紧随其后**：注释特意说明 drain 要排在断点之后——「resume 的运行要能通过下一超步的断点，drain 挡在断点前面就会跳过它」。**cached writes 的流送最后**：如果运行停在断点或 drain，这些写入在 resume 时会再次流出，提前流送会造成重复事件。递归重入（`return this.tick(...)`）是 resume 场景的平滑路径：准备好的任务若全部已有存量 writes，不经过 runner 直接进入下一个收尾循环。返回 `true` 才把控制权交给 runner——至此一次 tick 结束，BSP 的「同步段」完成，「并行段」开始。

### 第五段：把两个 tick 缝起来的外层驱动

前四段都在 loop 内部，但「tick 与 runner 交替」这件事本身发生在编译图的主循环里：

```ts
private async _runLoop(params: { loop: PregelLoop; runner: PregelRunner; ... }) {
  let tickError;
  try {
    while (await loop.tick({ inputKeys: this.inputChannels as string | string[] })) {
      for (const { task } of await loop._matchCachedWrites()) {
        loop.putWrites(task.id, task.writes, true);
      }
      await runner.tick({
        timeout: this.stepTimeout,
        retryPolicy: this.retryPolicy,
        onStepWrite: (step, writes) => { ... },
        maxConcurrency: config.maxConcurrency,
        signal: config.signal,
      });
    }
    if (loop.status === "draining") { ... throw new GraphDrained(...); }
    if (loop.status === "out_of_steps") {
      throw new GraphRecursionError(
        [`Recursion limit of ${config.recursionLimit} reached`,
         "without hitting a stop condition. You can increase the",
         `limit by setting the "recursionLimit" config key.`].join(" "),
        { lc_error_code: "GRAPH_RECURSION_LIMIT" });
    }
  } catch (e) {
    tickError = e as Error;
    const suppress = await loop.finishAndHandleError(tickError);
    if (!suppress) throw e;
  } finally {
    if (tickError === undefined) await loop.finishAndHandleError();
  }
}
```

*— pregel/index.ts:2865-2924（commit fa426b2）*

这段代码回答了三个此前悬而未决的问题。**一，交替驱动的调用点**：`while (await loop.tick(...))` 的返回值就是 tick 的布尔语义——true 表示「已准备好待执行任务，请 runner 接手」，false 表示「图结束/中断/步数耗尽」，循环体里才调用 `runner.tick`。runner 不可能自己调 loop（L77 的注释契约），衔接处就在这里。**二，cached writes 的兜底回填**：每次 loop.tick 返回后先 `_matchCachedWrites` 并把领回的写入 `putWrites(..., true)` 持久化——这是 L77 里 `_outputCachedWrites` 流送之外的存储侧动作。**三，终态翻译表**：tick 里设置的 status 并不直接抛错，而是由外层翻译——draining 翻成 `GraphDrained`、out_of_steps 翻成带 `GRAPH_RECURSION_LIMIT` 错误码的 `GraphRecursionError`。所以「recursionLimit 到底抛什么」的答案不选 GraphInterrupt 也不选 AggregateError，而选 GraphRecursionError——考题里常见的干扰项正源于没把 status 与异常类型分开记。catch 分支里 `finishAndHandleError(tickError)` 的 suppress 返回值决定了错误是否继续上抛（error handler 路由成功时可以吞掉，L79 的 exit 档落盘也发生在这条路径里）；finally 分支只在正常结束时补一次无参收尾调用。

### 本课小结

- tick 与 runner 分工：**tick 管收写/checkpoint/派发决策，runner 管并发执行**；二者交替构成 BSP 超步。
- 收尾顺序是硬约束：_applyWrites → （Overwrite 强制快照）→ values 产出 → _putCheckpoint →（sync 档 await）→ 发 values → interruptAfter 检查。
- interruptBefore 在派发前、interruptAfter 在写入应用后，都以 `throw GraphInterrupt` 中断；drain 排在断点之后，cached writes 流送排在两者之后。
- recursionLimit 默认 25 是额外超步数；checkpoints/tasks 流按订阅才产出。
- 下一课进入 tick 收尾调用的核心函数 `_applyWrites`：任务路径排序为什么等于可重放。
