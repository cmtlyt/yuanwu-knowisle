### 本课坐标：从「是什么」进阶到「谁依赖谁」

L01 给出了三包地图；本课取证第二层：**依赖方向**。方法只有一个——读 package.json 的三个字段：`dependencies`（运行时硬依赖，npm 会安装）、`peerDependencies`（要求宿主提供的依赖）、`devDependencies`（仅开发期使用）。读完你会得到一条铁律：**core 是零内部依赖底座，所有家族依赖都是单向指向 core 的**。这条铁律解释了后面课程里大量机制（为什么跨包判型要用 Symbol.for、为什么消息类型可以在 provider 包与主包之间互通）。

### core：七个外部依赖，零个家族依赖

```json
"dependencies": {
  "@cfworker/json-schema": "^4.1.4",
  "@standard-schema/spec": "^1.1.0",
  "js-tiktoken": "^1.0.12",
  "langsmith": ">=0.11.0 <1.0.0",
  "mustache": "^4.2.0",
  "p-queue": "^6.6.2",
  "zod": "^4.6.6"
}
```

*— libs/langchain-core/package.json:26-33（commit 7704471）*

这七行是 L04 的完整预告（每个依赖管什么，下一课逐个拆），本课只看结构特征：**没有任何 @langchain/* 或 langchain 字样的包名**。core 对外只依赖通用库：JSON Schema 校验器、标准 schema 规范、tokenizer、可观测平台客户端、模板引擎、并发队列、schema 库。

零内部依赖不是「功能少」的结果，而是架构前提：主包、classic、所有 provider 包（@langchain/openai、@langchain/anthropic 等，在 monorepo 的 `providers/` 目录）都依赖 core。如果 core 反过来依赖其中任何一个，依赖图立刻成环。**单向无环是 monorepo 里让三份 ESM/CJS 构建、多个 npm 版本共存时类型仍然互通的唯一解**——L05 会展示这个前提失效时的补丁。

### 主包：心脏换成了 langgraph

```json
"peerDependencies": {
  "@langchain/core": "workspace:^"
},
"dependencies": {
  "@langchain/langgraph": "^1.6.1",
  "@langchain/langgraph-checkpoint": "^1.1.5",
  "langsmith": ">=0.11.0 <1.0.0",
  "zod": "^4.6.6"
}
```

*— libs/langchain/package.json:73-80（commit 7704471）*

两张依赖表读出三个结论。**第一**，core 走 peerDependencies：主包要求宿主提供 core，而不是自带一份——全应用只有一份 core 实例，消息类与 Runnable 类型天然互通。**第二**，dependencies 里最重要的一行是 `@langchain/langgraph`：1.x 主包把编排内核作为硬依赖装进心脏，agent 就是编译后的 LangGraph 图（模块四逐行验证）。对比 0.x——主包的「编排」是自己写的 Chain 执行器——这是一次换心手术。**第三**，`zod` 出现在主包自己的 dependencies 里：agent 的 state/context schema 与 responseFormat 都直接消费 zod 对象，主包不经过 core 转手。

### classic：回望 0.x 的依赖表

```json
"peerDependencies": {
  "@langchain/core": "workspace:^",
  "cheerio": "*",
  "peggy": "^5.1.1",
  "typeorm": "*"
},
"dependencies": {
  "@langchain/openai": "workspace:*",
  "@langchain/textsplitters": "workspace:*",
  "handlebars": "^4.7.10",
  "js-yaml": "^5.5.0",
  "jsonpointer": "^5.0.1",
  "openapi-types": "^12.1.3",
  "yaml": "^2.9.1",
  "zod": "^4.6.6"
}
```

*— libs/langchain-classic/package.json:199-225（commit 7704471）*

最扎眼的一行是 **`"@langchain/openai": "workspace:*"` 出现在 dependencies 而不是 peerDependencies**。原因在 classic 的 exports 清单里：`./agents/format_scratchpad/openai_functions`、`./chains/openai_functions`、`./document_transformers/openai_functions` 这些旧子路径解析 OpenAI 专有的 function-call 结构，需要 openai-types 与 ChatOpenAI 的具体实现。这是 0.x 遗产的两个老问题被原样打包：**模型家族 API 硬编码进库本体**、**optional 依赖用 peerDependenciesMeta 表达**（cheerio/peggy/typeorm 都是 optional）。对照主包的依赖表，你会发现新架构里 provider 全部被推到运行时字符串（`"openai:gpt-4o"`）加动态 import 的位置（L09 详述）——依赖方向本身就是一次架构进化。

### 三种依赖表达机制在同一个文件里的同框

classic 的依赖表恰好是 npm 依赖表达机制的完整教材，值得把四个字段的行号逐个对齐（libs/langchain-classic/package.json:199-228，commit 7704471）：`peerDependencies`（L199-204）声明 core/cheerio/peggy/typeorm；紧随其后的 `peerDependenciesMeta`（L205-215）把后三者标记为 `"optional": true`；`dependencies`（L216-225）装着 @langchain/openai 等硬依赖；最容易被忽略的 `optionalDependencies`（L226-228）里还有一个 langsmith。四种表达方式的语义差异是：dependencies 是「没有就装」，peerDependencies 是「宿主必须给」，optional peerDep 是「宿主给就用、不给也不报错」，optionalDependencies 是「装了失败也不阻塞安装」。classic 用齐四种，因为它承接的 0.x 时代功能面对的宿主环境千差万别——cheerio 服务文档加载器（可能没人用）、peggy 服务语法解析、typeorm 服务 SQL 链，把任何一个写成硬依赖都会强迫所有用户安装用不上的东西。对照主包：dependencies 四项、peerDependencies 一项、没有 optional 系列——**依赖表达机制的收敛本身就是架构收敛的一部分**，1.x 的功能面不再需要「可选全家桶」这种表达力。

### 依赖方向总图与一个外部内核

```text
                 ┌────────────────────────┐
  应用代码 ──────▶  langchain@1.6.6        │──▶ @langchain/langgraph  (langgraphjs 仓)
                 │   (peer)               │──▶ @langchain/langgraph-checkpoint
                 └──────┬─────────────────┘
                        │ peer
                        ▼
  providers/* ────▶ @langchain/core@1.4.1 ──▶ 7 个外部库（langsmith/zod/…）
                        ▲ peer
  @langchain/classic ───┘ (+ deps: @langchain/openai, handlebars, …)
```

一个容易混淆的点必须钉死：`@langchain/langgraph` **不在 langchainjs 仓库里**，它来自独立仓库 langgraph-ai/langgraphjs（commit 锚 fa426b2），那边 `libs/langgraph/package.json` 的 version 是 1.0.47，`libs/langgraph-core` 才是 Pregel 内核所在。主包依赖 langgraph 而不是反过来——所以你在主包源码里能读到 agent 如何「用」图，但图的 tick/Channel 实现要去另一个仓库读（模块六的任务）。

### 为什么这个方向决定了 API 形态

依赖方向不只是包管理细节，它直接塑造了你写的代码。三组现象同源：

**现象一：消息类跨包通用。** provider 包（如 @langchain/openai）能返回主包与 core 都认识的 AIMessage，因为三者共享同一份 core 实例（peerDep 强制单实例）。

**现象二：主包不重复实现原语。** L03 会看到主包 index.ts 直接 `export { BaseMessage } from "@langchain/core/messages"`——转发而非复制，core 的类型签名就是主包的对外契约。

**现象三：classic 只能靠 peerDep 接 core。** 旧 API 的序列化格式（StoredMessage、lc_kwargs）兼容 core 的 Serializable 体系，但 core 不会为旧格式回头加任何东西——单向依赖意味着 core 永远不感知 classic 的存在。

### 本课小结

- core 的 dependencies 只有 7 个外部库（L26-33），零个家族成员——这是全家族单向依赖图的底座前提。
- 主包对 core 用 peerDependencies（单实例保证），对 @langchain/langgraph 用 dependencies（换心）；zod 是主包自己的硬依赖。
- classic 依赖表回望 0.x：@langchain/openai 写成硬 dependencies，cheerio/peggy/typeorm 走 optional peerDep。
- @langchain/langgraph 来自独立仓库 langgraphjs（锚 fa426b2），方向是主包依赖它。
