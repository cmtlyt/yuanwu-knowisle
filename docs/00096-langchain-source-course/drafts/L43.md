### 开篇：同一个图，两条流出口

L42 走完 invoke，本课走流式。agent 层有两条流式通道：**stream() 输出状态更新**（LangGraph 的 chunk 协议），**streamEvents() 输出事件级流**（legacy StreamEvent 或 v3 AgentRunStream）。两条通道共享同一张编译图（L41）与同一套预处理（配置合并 + 中间件状态初始化），差异只在出口协议。本课先走读两条通道的源码，然后跑两组实验：实验一用 streamMode 两种模式消费状态更新流；实验二写出 v3 AgentRunStream 的完整消费循环。深度八种流模式的协议细节划界给 L78（模块六），本课只碰 agent 层能直接观察到的部分。

### 通道一：stream()——状态更新的薄封装

stream 的实现与 invoke 同构：

```ts
async stream<
  TStreamMode extends StreamMode | StreamMode[] | undefined,
  TSubgraphs extends boolean,
  TEncoding extends "text/event-stream" | undefined,
>(
  state: InvokeStateParameter<Types>,
  config?: StreamConfiguration<..., TStreamMode, TSubgraphs, TEncoding>
) {
  const mergedConfig = this.#getGraphConfig(config);
  const initializedState = await this.#initializeMiddlewareStates(
    state,
    mergedConfig as RunnableConfig
  );
  return this.#graph.stream(initializedState, mergedConfig) as Promise<
    IterableReadableStream<
      StreamOutputMap<
        TStreamMode, TSubgraphs,
        MergedAgentState<Types>, MergedAgentState<Types>,
        string, unknown, unknown, TEncoding
      >
    >
  >;
}
```

*— libs/langchain/src/agents/ReactAgent.ts:1289-1326（commit 7704471）*

三处与 invoke 的不同值得注意。其一，方法头部有**三个流相关泛型**（TStreamMode/TSubgraphs/TEncoding），返回类型的 StreamOutputMap 由它们参数化——你在 config.streamMode 里写 `"values"`，chunk 类型就随之变窄，这是「泛型随配置联变」的类型层技巧。其二，config 类型是 StreamConfiguration（runtime.ts:159-195）：在 InvokeConfiguration 的约束之外追加 `encoding`/`streamMode` 两个键——这两个键的定义体只有一行 `type CreateAgentPregelStreamOptions = "encoding" | "streamMode"`（runtime.ts:127），也就是说 agent 层对流配置的开放面收窄到极致，LangGraph 更细的流选项（如自定义模式）不在这份白名单里。其三，返回值是 Promise<IterableReadableStream<...>>——先 await 拿流、再 for await 消费，两段式是 Pregel 的接口惯例。

StreamConfiguration 的 context 约束与 InvokeConfiguration 是同构的三分支，但值得单独看一眼，因为它决定了 stream 的第二个参数怎么写。源码结构是：contextSchema 是 InteropZodDefault 时返回 `Partial<Pick<PregelOptions, ...>> & { context?: Partial<ContextSchema> }`；IsAllOptional 为真时同样放宽；否则 fallback 分支里 `& WithMaybeContext<ContextSchema>` 让 context 回到「按 schema 可选性决定必填」的轨道（runtime.ts:163-195）。实践含义：**stream 与 invoke 对 context 的类型约束完全一致**——你在 L42 学到的「contextSchema 含 default 则 context 可省」规则原样适用于流式调用，不需要为流式单独记一套。

还有一个两段式消费的工程细节：`await agent.stream(...)` 返回 Promise，await 之后拿到的才是 `IterableReadableStream`。这意味着**图的执行不是在 await 时开始的，而是在你第一次 for await 拉取时**——如果你拿到了流却不消费（比如条件分支里忘了迭代），节点不会执行；反过来，两段式的价值在于你可以在拿到流之后、开始消费之前做准备工作（建文件、开连接），而消费一旦开始就按 Pregel 的节奏逐节点推进。L29 讲过的「流首块缓冲」在图层同样成立：错误能在首块缓冲里被提前抛出，而不是等到迭代深处才炸。

### 实验一：updates 与 values 两种 chunk 的形状对比

用 L42 的假模型 agent 跑两种模式（`createAgent`/`tool`/`FakeToolCallingModel` 的定义同 L42 实验一，此处复用）：

```ts
// 模式一：updates —— 每个节点完成时吐「该节点写入的增量」
const streamUpdates = await agent.stream(
  { messages: [{ role: "user", content: "What's the weather in Paris?" }] },
  { streamMode: "updates" }
);

for await (const chunk of streamUpdates) {
  console.log(Object.keys(chunk), "->", Object.keys(chunk).map((k) =>
    Object.keys((chunk as Record<string, any>)[k] ?? {})
  ));
  // 依次输出类似：
  // ["model_request"] -> ["messages"]   （AIMessage + tool_calls）
  // ["tools"]         -> ["messages"]   （ToolMessage）
  // ["model_request"] -> ["messages"]   （收尾 AIMessage）
}

// 模式二：values —— 每步之后吐「全量状态快照」
const streamValues = await agent.stream(
  { messages: [{ role: "user", content: "What's the weather in Paris?" }] },
  { streamMode: "values" }
);

for await (const snapshot of streamValues) {
  console.log("messages so far:", (snapshot as any).messages.length);
  // 1 -> 2 -> 3 -> 4，逐步增长
}
```

观察结论：**updates 的 chunk 是「节点名 → 写入增量」的映射，values 的 chunk 是全量快照**。两者底层是同一张图在跑，只是出口协议不同；`streamMode` 还可以传数组（如 `["updates", "values"]`），chunk 形状按 LangGraph 的 `[namespace, mode, payload]` 协议组织（协议细节归 L78）。subgraphs 打开时，chunk 会带子图命名空间，v3 之外的消费代码要自己处理路由。

两个流模式的选型也值得给出操作建议。updates 模式的 chunk 天然带节点署名（键就是节点名），适合「执行进度面板」：把 `Object.keys(chunk)` 直接映射到 UI 上的步骤条（模型请求中 → 工具执行中 → 收尾），不需要自己维护游标。values 模式每步给全量快照，适合「断点续渲」：消费者重启或中途接入时，拿最新一个 chunk 就是完整状态，不依赖此前所有 chunk 的累积——代价是重复传输（第 N 步的快照含全部历史）。还有一个内存层面的提醒：values 的快照会引用消息对象，消费端若长期持有 chunk 引用而不深拷贝，快照里的数组在图继续写入时可能被 reducer 语义影响；做重放或审计时，先把需要的字段序列化再存。这两种模式与 checkpointer 的 values 流（L79 的 durability 话题）名字相近但层级不同——本课的是出口协议，L79 的是持久化时机，注意别混淆。

### 通道二：streamEvents 的双版本分派

streamEvents 有三个重载签名，实现体的分派逻辑只有一问：**version 是不是显式的 "v3"**？

```ts
streamEvents(
  state: InvokeStateParameter<Types>,
  config?:
    | (InvokeConfiguration<...> & {
        version: "v3";
        transformers?: ReadonlyArray<() => StreamTransformer<any>>;
      })
    | (StreamConfiguration<..., StreamMode | StreamMode[] | undefined, boolean, "text/event-stream" | undefined>
        & { version?: "v1" | "v2" }),
  streamOptions?: Parameters<Runnable["streamEvents"]>[2]
):
  | Promise<AgentRunStream<MergedAgentState<Types>, Types["Tools"], ...>>
  | IterableReadableStream<StreamEvent> {
  if (config?.version !== "v3" || streamOptions != null) {
    const mergedConfig = this.#getGraphConfig(config);
    const version =
      config?.version === "v1" || config?.version === "v2"
        ? config.version
        : "v2";
    return this.#graph.streamEvents(
      state,
      { ...(mergedConfig as ...), version },
      streamOptions
    );
  }
  // ... v3 分支（async IIFE，见下）
}
```

*— libs/langchain/src/agents/ReactAgent.ts:1448-1506（commit 7704471，节选）*

legacy 分支的三件事：合并配置、把 version 归一为 `"v2"`（不传或传 v1/v2 之外的值都落 v2）、转发 `#graph.streamEvents(state, config, streamOptions)`——注意 `streamOptions` 是 Runnable.streamEvents 的第三参数，一旦非空就**强制走 legacy**，即使 version 写了 "v3"（这是有意设计：streamOptions 属于 legacy 协议的输入面）。源码注释写明 legacy 的定位：为 LangGraph Platform 集成保留的内部事件流，不建议新用户代码使用。

对照 v3 分支还能看出一个易漏的不对称：**legacy 分支把原始 `state` 直接传给 `#graph.streamEvents`，跳过了中间件状态初始化**；而 v3 分支里 `initializedState = await this.#initializeMiddlewareStates(state, ...)`（ReactAgent.ts:1524-1528）走的是与 invoke 相同的完整归一。后果很具体：一个带必填 stateSchema 中间件的 agent，invoke 与 streamEvents v3 都会在缺字段时报「Middleware X has required state fields...」，而 legacy 路径会把缺省状态原样带进图——schema 校验被跳过，缺省行为取决于图内节点的容错。这与 legacy「内部集成路径」的定位一致：它的调用方（Platform）自己负责状态完备性。教学结论：**做状态完整性实验必须用 invoke 或 v3，legacy 的行为不可作为状态语义的参照**。

### v3 分支：AgentRunStream 与调用期 transformers

显式 `version: "v3"` 时进入 v3 分支：

```ts
return (async () => {
  type FullState = MergedAgentState<Types>;
  const {
    transformers: callSiteTransformers,
    version: _version,
    ...restConfig
  } = agentConfig ?? {};
  const mergedConfig = this.#getGraphConfig(restConfig);
  const initializedState = await this.#initializeMiddlewareStates(
    state,
    mergedConfig as RunnableConfig
  );

  return (await this.#graph.streamEvents(initializedState, {
    ...(mergedConfig as Record<string, any>),
    version: "v3",
    transformers: callSiteTransformers,
  })) as unknown as AgentRunStream<FullState, Types["Tools"], ...>;
})();
```

*— libs/langchain/src/agents/ReactAgent.ts:1508-1543（commit 7704471，节选）*

两个工程细节。其一，config 解构把 `transformers` 抽出来单独透传——这是**调用期 transformers**（run after 编译期内置与中间件转换器，JSDoc 原话），与 L41 编译期固化的 compileTransformers 是「先固化、后追加」的关系，共同决定 v3 投影的 extensions 形状。其二，整个分支包在 async IIFE 里，因为 #initializeMiddlewareStates 是异步的——返回值是 Promise<AgentRunStream>，await 一次拿 run 对象再逐投影消费。

### 实验二：v3 AgentRunStream 的完整消费循环

```ts
const run = await agent.streamEvents(
  { messages: [{ role: "user", content: "What's the weather in Paris?" }] },
  { version: "v3" }
);

// 1. token 级消费 AI 消息文本
for await (const msg of run.messages) {
  for await (const token of msg.text) {
    process.stdout.write(token);
  }
  process.stdout.write("\n---\n");
}

// 2. 工具调用生命周期
for await (const call of run.toolCalls) {
  console.log("tool:", call.name, "input:", call.input);
  console.log("status:", (await call.output) !== undefined ? "done" : "pending");
}

// 3. 最终状态（promise-like）
const final = await run.output;
console.log(final.messages.length);
```

三个消费面按需选用：`run.messages` 适合前端逐 token 渲染；`run.toolCalls` 适合做工具执行面板（input/output/status 三个投影覆盖生命周期）；`run.output` 收尾取全量状态，等价于 invoke 的返回。注意 JSDoc 的定位声明：**v3 是实验性 API，未来大版本会成为默认**——生产代码若求稳，可以用 legacy 但要接受更原始的 StreamEvent 处理；若求新，用 v3 并把投影名（messages/toolCalls/output）写进自己的抽象层，方便后续切换。

再展开 run.output 与 invoke 返回的等价性验证：run.output resolve 出来的就是 `MergedAgentState<Types>`——含 messages 全序列与中间件状态字段，签名上是 `Promise<AgentRunStream<...>>` 的 promise-like 成员（ReactAgent.ts:1481-1487）。实验里把 `final` 与 L42 的 invoke 返回逐键比对（同输入、同假模型剧本），messages 长度与每条消息的类型应当完全一致——这正好验证了「两条通道共享同一张图」的口径：**流的出口协议再花哨，底层状态机只有一个**。若中间件在 beforeAgent/afterAgent 里写了状态（如 L42 的 counter 加 rounds），run.output 里同样能看到终值，因为投影是从图状态派生的，不是独立通道。

消费循环的异常处理也有一条纪律值得写进你的抽象层：run.messages / run.toolCalls 是异步迭代器，消费者中途 break 或抛错时，图的执行并不会自动取消——要真正终止需要给 config 传 signal（AbortSignal，InvokeConfiguration 白名单键之一）。前端「用户点了停止按钮」的实现路径因此是：保存 invoke 时创建的 AbortController，在停止回调里 `controller.abort()`，而不是粗暴地跳出 for await 循环。这个组合（v3 流 + signal）在类型层完全合法——signal 本来就在 InvokeConfiguration 的白名单里。

### 本课小结

- **两条通道一句话**：stream() = 状态更新 chunk（StreamOutputMap，泛型随 streamMode 联变）；streamEvents() = 事件级流（legacy StreamEvent / v3 AgentRunStream），两者共享配置合并与中间件状态初始化两道预处理。
- **分派逻辑一问定乾坤**：`config?.version !== "v3" || streamOptions != null` → legacy（version 缺省 "v2"）；否则 v3 分支（async IIFE + 调用期 transformers 透传）。
- **updates vs values 实操**：updates 吐「节点名 → 增量」，values 吐全量快照；同一图、不同出口协议。
- **v3 七消费面**：messages/toolCalls/middleware/values/output/subgraphs/extensions；实验二覆盖前三个与 output。
- 下一课看图级 API 透传：getState/getStateHistory/getSubgraphs 等内部方法如何把 LangGraph Platform 需要的运行时面完整暴露出去。
