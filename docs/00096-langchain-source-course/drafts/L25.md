上一课的 PromptTemplate 只能产出一张字符串——对聊天模型来说还不够：对话的输入是**消息列表**，system/user/assistant 各有各的模板。本课的主角 `ChatPromptTemplate` 解决的就是「消息级模板」，而它的地基 `BasePromptTemplate` 还藏着一个架构级事实：**Prompt 本身是 Runnable**。这两件事合起来回答了 LCEL 的一个常见疑问：为什么 `prompt.pipe(model)` 可以一行写出来、不需要任何适配器。证据来自 `prompts/base.ts` 与 `prompts/chat.ts`（commit 7704471）。

### Prompt 即 Runnable

先看身份声明与 invoke 实现：

```ts
export abstract class BasePromptTemplate<
  RunInput extends InputValues = any,
  RunOutput extends BasePromptValueInterface = BasePromptValueInterface,
  PartialVariableName extends string = any,
> extends Runnable<RunInput, RunOutput>
  implements BasePromptTemplateInput
{
  lc_serializable = true;
  lc_namespace = ["langchain_core", "prompts", this._getPromptType()];

  inputVariables: Array<Extract<keyof RunInput, string>>;
  outputParser?: BaseOutputParser;
  partialVariables: PartialValues<PartialVariableName>;

  async invoke(input: RunInput, options?: BaseCallbackConfig): Promise<RunOutput> {
    const metadata = { ...this.metadata, ...options?.metadata };
    const tags = [...(this.tags ?? []), ...(options?.tags ?? [])];
    return this._callWithConfig(
      (input: RunInput) => this.formatPromptValue(input),
      input,
      { ...options, tags, metadata, runType: "prompt" }
    );
  }
}
```

三个观察点。**其一**，继承 Runnable 意味着 prompt 免费获得 L27 即将展开的四大支柱（invoke/batch/stream/transform）与全部组合子——pipe/batch/withRetry 都对 prompt 生效，没有为 prompt 单开的特殊通道。**其二**，invoke 把实际工作委托给 `formatPromptValue`，产出 `PromptValue` 中间表示（字符串版与聊天版两种），这正是 L16 里 `generatePrompt([promptValue])` 消费的类型——**模板端与模型端在 PromptValue 上会师**，中间表示链由此闭合。**其三**，`runType: "prompt"` 让 prompt 在回调执行树（L36）里与 model/chain/tool 并列为一等节点类型，`lc_serializable = true` 则声明它可以被序列化持久化。类上还有个 `outputParser?` 字段——历史上 prompt 可以绑定解析器（few_shot 场景），这是解析器世界（L26）与本课的一根旧接口线。

### fromMessages 的三步归一

`ChatPromptTemplate` 持有 `promptMessages: Array<BaseMessagePromptTemplate | BaseMessage>`（chat.ts:943），`fromMessages` 是它的标准入口，实现是一串 reduce：

```ts
static fromMessages<RunInput, Extra>(
  promptMessages: (ChatPromptTemplate<InputValues, string> | BaseMessagePromptTemplateLike)[],
  extra?: ...
): ChatPromptTemplate<RunInput> {
  const flattenedMessages = promptMessages.reduce(
    (acc, promptMessage) =>
      acc.concat(
        promptMessage instanceof ChatPromptTemplate
          ? promptMessage.promptMessages
          : [_coerceMessagePromptTemplateLike<...>(promptMessage, extra)]
      ),
    []
  );
  const flattenedPartialVariables = promptMessages.reduce(
    (acc, promptMessage) =>
      promptMessage instanceof ChatPromptTemplate
        ? Object.assign(acc, promptMessage.partialVariables)
        : acc,
    Object.create(null) as PartialValues
  );
  const inputVariables = new Set<string>();
  for (const promptMessage of flattenedMessages) {
    if (promptMessage instanceof BaseMessage) continue;
    for (const inputVariable of promptMessage.inputVariables) {
      if (inputVariable in flattenedPartialVariables) {
        continue;
      }
      inputVariables.add(inputVariable);
    }
  }
  return new this<RunInput>({
    ...extra,
    inputVariables: [...inputVariables] as ...,
    promptMessages: flattenedMessages,
    partialVariables: flattenedPartialVariables,
    templateFormat: extra?.templateFormat,
  });
}
```

*— langchain-core/src/prompts/chat.ts:1190-1249 裁剪（commit 7704471）*

三步对应三个 reduce/循环。**第一步展平**：入参接受四种形态——消息模板、裸 BaseMessage、元组（交给 coerce）、甚至嵌套的 ChatPromptTemplate；嵌套实例不包装而是拆开取 `promptMessages`，组合式用法由此成立。**第二步合并 partial**：嵌套模板的 partialVariables 被 Object.assign 汇聚到顶层。**第三步推导变量清单**：两个 continue 是关键——BaseMessage 实例没有变量，partial 已覆盖的变量调用方无需再传；清单语义因此是「format 时还缺什么」。注意返回 `new this<RunInput>(...)`——用 new this 而非 new ChatPromptTemplate，子类化 fromMessages 也能返回正确的类型。

### coerce：元组语法糖

元组形态的转换是 fromMessages 的易用性来源：

```ts
function _coerceMessagePromptTemplateLike<...>(
  messagePromptTemplateLike: BaseMessagePromptTemplateLike,
  extra?: Extra
): BaseMessagePromptTemplate | BaseMessage {
  if (
    _isBaseMessagePromptTemplate(messagePromptTemplateLike) ||
    isBaseMessage(messagePromptTemplateLike)
  ) {
    return messagePromptTemplateLike;
  }
  if (
    Array.isArray(messagePromptTemplateLike) &&
    messagePromptTemplateLike[0] === "placeholder"
  ) {
    const messageContent = messagePromptTemplateLike[1];
    if (
      extra?.templateFormat === "mustache" &&
      typeof messageContent === "string" &&
      messageContent.slice(0, 2) === "{{" &&
      messageContent.slice(-2) === "}}"
    ) {
      const variableName = messageContent.slice(2, -2);
      return new MessagesPlaceholder({ variableName, optional: true });
    } else if (
      typeof messageContent === "string" &&
      messageContent[0] === "{" &&
      messageContent[messageContent.length - 1] === "}"
    ) {
      const variableName = messageContent.slice(1, -1);
      return new MessagesPlaceholder({ variableName, optional: true });
    }
    // ...
  }
  // 元组 [role, template] → 对应 role 的 MessagePromptTemplate
}
```

*— langchain-core/src/prompts/chat.ts:805-845 裁剪（commit 7704471）*

这段代码的顺序就是它的优先级表：**已有模板或消息实例 → 原样返回；placeholder 元组 → MessagesPlaceholder（mustache 与 f-string 两种花括号形态都识别，且一律 optional: true）；普通 [role, template] 元组 → 按 role 映射到 HumanMessagePromptTemplate 等类**。最常见的 `["user", "{question}"]` 走最后一条分支。两个值得警惕的细节：coerce 出来的 MessagesPlaceholder 固定 optional——缺变量静默为空列表，想要强校验必须显式构造类；mustache 分支要求 `extra.templateFormat === "mustache"` 才生效，否则 `{{history}}` 会被当成字面量文本处理。

### formatMessages 与 stop 保留字

format 侧的调用链是 `formatMessages(values)` → 逐条 `promptMessage.formatMessages(剩余变量)` → 拼成 `BaseMessage[]`，再由 `formatPromptValue` 包成 ChatPromptValue。变量在消息间的分配依赖每条消息模板自带的 inputVariables（L24 运行时提取的成果在这里被复用）。构造期的防御只剩一条：BasePromptTemplate 构造函数里 `if (inputVariables.includes("stop")) throw`——stop 是模型调用选项的保留字，同名输入变量会在 config 传播时与停止序列选项冲突，于是在最早的时刻拒绝。最后看一个组合全貌：`ChatPromptTemplate.fromTemplate("Say {foo}")` 的实现是先造 PromptTemplate、包进 HumanMessagePromptTemplate、再 fromMessages——**字符串世界的 L24 与消息世界的本课，由这一行胶水衔接**；而 pipe 进模型后的输出解析，就是下一课 FewShot 与 OutputParser 的领地。

### MessagesPlaceholder：optional 的两面与 formatMessages 的分配律

coerce 出来的占位符类本身值得单独读一遍。`MessagesPlaceholder` 支持裸字符串构造（`new MessagesPlaceholder("history")` 与 fields 形态等价），`optional ?? false` 是字段默认值——**注意类构造与 coerce 语义相反：显式建类默认强制存在**（prompts/chat.ts:101-127）。formatMessages 的分支把 optional 的两面钉死：

```ts
async formatMessages(values): Promise<BaseMessage[]> {
  const input = values[this.variableName];
  if (this.optional && !input) {
    return [];

      `Field "${this.variableName}" in prompt uses a MessagesPlaceholder, which expects an array of BaseMessages as an input value. Received: undefined`
    );
    error.name = "InputFormatError";
    throw error;
  }
  ...
}
```

非 optional 且缺变量时抛出的错误被命名为 `InputFormatError`——一个可判型的错误名，供上层按类型捕获。值存在时逐元素过 `coerceMessageLikeToMessage`（chat.ts:155-160），所以 placeholder 既能接 BaseMessage[] 也能接 message-like 宽容形态。分配侧还有一条隐藏规则藏在 `ChatPromptTemplate.formatMessages` 里：mustache 格式下每条消息模板拿到的是 `{...allValues}` **全量变量**；f-string 格式则按消息自带的 inputVariables 逐条精确配给，缺值时经 `addLangChainErrorFields` 打上 `INVALID_PROMPT_INPUT` 错误码抛出——但 optional 的 placeholder 被显式豁免于缺值检查（chat.ts:1074-1088）。两种模板引擎连「变量分配」的语义都不同：f-string 是精确配给，mustache 是全局可见。这是双格式差异在消息层的延续，也是 mustache 模板里引用未声明变量不报错的原因——同一份 values，两个引擎读到的是两份视图。占位符与外层清单的衔接还有一处闭环可看：`get inputVariables()` 返回 `[this.variableName]`（chat.ts:129-131）——placeholder 把自己的变量名上报给 fromMessages 的清单推导（本课三步归一的第三步正是读这个 getter），所以 coerce 出来的占位符同样参与「format 时还缺什么」的计算；optional 只豁免 formatMessages 的缺值检查，不豁免清单登记。值形态上 formatMessages 也留了余地：数组走逐元素 coerce，单条非数组值会被包成单元素数组（chat.ts:155-160）——`history` 传一条消息而不是消息数组也能工作，只是类型上不推荐。

### 本课小结

- BasePromptTemplate extends Runnable：prompt 获得 Runnable 全部能力，invoke 以 runType \"prompt\" 进回调树，formatPromptValue 产出的 PromptValue 与模型端 generatePrompt 会师。
- fromMessages 三步归一：展平嵌套模板、汇聚 partialVariables、推导「format 时还缺什么」的变量清单（跳过 BaseMessage 与 partial 已覆盖项）。
- coerce 优先级表：实例原样返回 → placeholder 元组转 MessagesPlaceholder（一律 optional）→ [role, template] 转 role 模板类；mustache placeholder 需显式声明格式。
- stop 保留字在构造期拦截；fromTemplate 的胶水行展示两个世界的衔接方式。
