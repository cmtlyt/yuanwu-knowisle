### 从「追加消息」到「版本快照」

L105 说新 agent 的心脏是 #graph，那么图的记忆存在哪？本课给出答案。核心结论：**持久化地基从「消息级追加存储」（BaseChatMessageHistory）换代为「图状态版本快照」（BaseCheckpointSaver），粒度升级让断点恢复、重放与会话隔离成为协议内建能力，而不是应用层的手工工程。**这是两代架构差异里最容易被低估的一处：看起来都是「存对话」，实际存的东西完全不同。

先看旧地基的形状。BaseChatMessageHistory 是一组围绕「单条消息」的方法集：

```ts
export abstract class BaseChatMessageHistory extends Serializable {
  public abstract getMessages(): Promise<BaseMessage[]>;
  public abstract addMessage(message: BaseMessage): Promise<void>;
  public abstract addUserMessage(message: string): Promise<void>;
  public abstract addAIMessage(message: string): Promise<void>;
  public async addMessages(messages: BaseMessage[]): Promise<void> {
    for (const message of messages) {
      await this.addMessage(message);
    }
  }
  public abstract clear(): Promise<void>;
}
```

*— langchain-core/src/chat_history.ts:10-38（commit 7704471）*

它的世界模型是：一个会话 = 一串消息的有序列表，操作只有追加、读取、清空。注意默认的 `addMessages` 是循环逐条调用 `addMessage`——连批量追加都是消息粒度的。这个抽象本身没毛病，问题在于**它能表达的状态只有消息**：agent 执行途中的中间变量、结构化输出、工具结果、多字段状态，都装不进这个模型。

### 新地基的五方法契约

BaseCheckpointSaver 的契约面完全不同：

```ts
export abstract class BaseCheckpointSaver<V extends string | number = number> {
  serde: SerializerProtocol = new JsonPlusSerializer();

  abstract getTuple(config: RunnableConfig): Promise<CheckpointTuple | undefined>;
  abstract list(config: RunnableConfig, options?: CheckpointListOptions): AsyncGenerator<CheckpointTuple>;
  abstract put(config, checkpoint, metadata, newVersions): Promise<RunnableConfig>;
  abstract putWrites(config, writes: PendingWrite[], taskId: string, taskPath?: string): Promise<void>;
  abstract deleteThread(threadId: string): Promise<void>;
}
```

*— langgraphjs/libs/checkpoint/src/base.ts:180-243（commit fa426b2，有裁剪）*

五个方法按职责分三组。**读写快照**：put 写入某个超步结束后的完整 checkpoint（含 channel_values/channel_versions/versions_seen 三字典，L90 详讲），getTuple 取 thread 的最近快照，list 历史遍历（时间旅行的基础）。**中间写入**：putWrites 是旧体系完全没有的能力——任务执行途中把 PendingWrite 先落盘，如果进程崩溃，恢复时这些写入按序回放。它的注释值得原文引用：实现方必须按 writesSortKey 顺序返回 pendingWrites，因为「live execution applies a superstep's writes in that order, so replaying in any other order can rebuild a different value for an order-sensitive reducer」——**写入顺序是协议的一部分，不是实现细节**。**会话管理**：deleteThread 按 thread 一键清理全部快照与写入。

serde 字段也值得强调：默认 `new JsonPlusSerializer()`，意味着存进 checkpoint 的 BaseMessage/Document/BigInt/Map 都能无损往返——这是「图状态」可以直接被持久化的前提，旧体系里每个 chatHistory 实现都要自己发明序列化方案。

### 写排序键：把「注释要求」升级为「导出的比较函数」

putWrites 的顺序敏感性在上文引过注释原文，但 commit fa426b2 的源码里这件事比注释更进一步——排序被做成了**协议层导出的工具**（langgraphjs/libs/checkpoint/src/base.ts:112-158，commit fa426b2）：

```ts
/** Sort key for the writes of one superstep: `(task_path, task_id, idx)`. */
export type WritesSortKey = readonly [string, string, number];

export function writesSortKey(
  taskPath: string,
  taskId = "",
  idx = 0
): WritesSortKey {
  return [taskPath, taskId, idx];
}
```

*— langgraphjs/libs/checkpoint/src/base.ts:112-133（commit fa426b2，有裁剪）*

注释块里有两条精确规范。其一，比较器按 code point 比较字符串，并特意注明要匹配 Python 的 `str` 顺序（astral 字符在 UTF-16 code unit 顺序下与之不同）——TS 与 Python 两线 saver 的写入顺序必须逐字节一致，注释直接写明「不要用 `<`、`localeCompare` 或默认 sort 来排这个键」。其二，**没有 taskPath 的写入（图输入、Command 更新、早于该列的历史数据）用空字符串，排序最先**——这恰好对应 live execution 里「输入最先被应用」的事实，协议与实现行为对齐。配套地，`getTuple` 的契约注释要求实现方持久化 taskPath 并按 writesSortKey 顺序返回 pendingWrites（base.ts:216-226），基类还提供了一个默认实现示范如何沿 `getTuple` + `parentConfig` 链回溯收集中间写入（base.ts:246-265）——CheckpointTuple 的 `parentConfig` 字段（base.ts:102）就是这条链表的指针。把排序从「实现方自觉」变成「全链路唯一比较函数」，注释原话是让 live execution 与每个 saver **cannot drift apart**——这是分布式系统里「确定性重放」的最小完备设计，也是旧 BaseChatMessageHistory 完全不需要面对的问题域。

### MemorySaver：最小起点的进阶路线

具体实现的起点是 MemorySaver：

```ts
export class MemorySaver extends BaseCheckpointSaver {}
```

*— langgraphjs/libs/checkpoint/src/memory.ts:106（commit fa426b2）*

一个空类继承全部行为，数据存进程内存。它的定位对标旧世界的 `InMemoryChatMessageHistory as ChatMessageHistory`（memory/index.ts:10 的 re-export）：**开发期最小依赖、生产期替换实现**。旧世界的替换路径是「找一个新的 ChatMessageHistory 实现」，新世界是「换一个 checkpointer」（Postgres/Redis/SQLite saver 各自是独立包）——但接口契约不变，这是五方法抽象的价值。

### 三组代差的正面对照

| 维度 | BaseChatMessageHistory（旧） | BaseCheckpointSaver（新） |
|---|---|---|
| 持久化粒度 | 一条 BaseMessage | 一个超步结束后的完整图状态快照（三字典） |
| 能表达的状态 | 仅消息序列 | 任意图状态：messages 只是其中一个 channel |
| 中间写入 | 无 | putWrites + taskPath 排序，支撑崩溃恢复与重放 |
| 历史遍历 | 无 | list 生成器遍历 CheckpointTuple（时间旅行） |
| 会话隔离 | 靠实例分离/sessionId 惯例 | thread_id 协议级一等公民 + deleteThread |
| 序列化 | 各实现自理 | JsonPlusSerializer 统一 |

两点补充避免误读。第一，**旧抽象没有死**：BaseChatMessageHistory/BaseListChatMessageHistory 仍在 core（chat_history.ts:10,40），需要「纯消息存储」的场景（比如自己维护一份对话日志、给非 LangGraph 系统供消息）依然可以用它——1.x 的分类法是「checkpointer 管图状态持久化，message history 管消息存储」，两者不是替代关系而是分工关系。第二，thread_id 是经由 `RunnableConfig.configurable` 传入的（`{ configurable: { thread_id: "..." } }`），这个约定贯穿 LangGraph 的 getTuple/list/put——你会在 L121/L122 的走查代码里反复见到。

### 本课小结

- 旧地基管「追加消息」，新地基管「图状态版本快照」：checkpoint 三字典 + putWrites 中间写入 + list 历史遍历，粒度全面升级。
- BaseCheckpointSaver 五方法契约（getTuple/list/put/putWrites/deleteThread）+ 默认 JsonPlusSerializer，写入顺序是协议一部分。
- MemorySaver（memory.ts:106）是空类继承，对标旧 ChatMessageHistory 的「开发起步、生产换装」路线。
- BaseChatMessageHistory 抽象未死，与新地基是分工而非替代；多用户隔离从惯例升级为 thread_id 协议。
