### 七行依赖表，七个架构决策

L02 展示了 core 的 dependencies 全貌，本课把七行逐一对应到消费它们的源码文件。方法仍然是最朴素的取证：在 `libs/langchain-core/src/` 里 grep 包名。每个依赖都对应一个架构决策——**core 选择把哪些能力做成编译期内置，哪些留给上层**。

```json
"dependencies": {
  "@cfworker/json-schema": "^4.1.4",
  "@standard-schema/spec": "^1.1.0",
  "js-tiktoken": "^1.0.12",
  "langsmith": ">=0.11.0 <1.0.0",
  "mustache": "^4.2.0",
  "p-queue": "^6.6.2",
  "zod": "^4.6.6"
}
```

*— libs/langchain-core/package.json:26-33（commit 7704471）*

### mustache：只服务一处——模板插值

```ts
// src/prompts/template.ts 消费 mustache
import mustache from "mustache";
```

*— libs/langchain-core/src/prompts/template.ts（commit 7704471）*

全 core 只有 prompts/template.ts（与其测试文件）引用 mustache。它支撑 PromptTemplate/ChatPromptTemplate 的 mustache 模板格式——`{{variable}}` 风格的插值与列表迭代，是 f-string 之外的第二种模板格式（两种格式的实现与参数类型提取见 L24）。为什么选 mustache 而不是 handlebars？看 classic 的依赖表你会找到答案：**handlebars 是 classic 的硬依赖**（L02 取证，libs/langchain-classic/package.json L219）。1.x 把更轻的 mustache 带进 core，把更重的 handlebars 留在博物馆——依赖表本身就是新旧分界的一部分。

### p-queue：batch 并发与全局回调单例的底座

p-queue 的两个引用点非常关键：

```ts
// src/utils/async_caller.ts —— AsyncCaller 的并发队列
import PQueue from "p-queue";
```

*— libs/langchain-core/src/utils/async_caller.ts（commit 7704471）*

第一处是 **AsyncCaller**：所有模型/工具 batch 调用的并发限流器，maxConcurrency 最终变成 PQueue 的并发配置，失败重试的指数退避也在这里实现（L28 深拆 batch 工程）。第二处是 **singletons/callbacks.ts**：全局回调管理器的单例初始化。一个并发原语包被放进核心 dependencies，说明 core 把「并发纪律」当作一等公民能力，而不是上层可选优化。

### js-tiktoken：token 计数落在两个文件

```ts
// src/language_models/base.ts:1
import type { Tiktoken, TiktokenModel } from "js-tiktoken/lite";
```

*— libs/langchain-core/src/language_models/base.ts:1、libs/langchain-core/src/utils/tiktoken.ts:1-6（commit 7704471）*

js-tiktoken 是纯 JS 实现的 tokenizer（无需 native 绑定），且注意 import 路径带 `/lite` 后缀——core 只取轻量子集。消费点两处：utils/tiktoken.ts 封装编码缓存与计数工具；language_models/base.ts 用它给 BaseChatModel/BaseLLM 提供 token 计数能力（get_num_tokens 等接口）。**选纯 JS 而非 WASM 方案是浏览器兼容决策**——core 的 browser 构建目标要求这层无 native 依赖。

### zod ^4.6.6 与 @standard-schema/spec：类型互操作双保险

```json
"zod": "^4.6.6"
```

*— libs/langchain-core/package.json:33（commit 7704471）*

zod 是 core 里语义最重的依赖：工具输入 schema、agent 的 state/context schema、结构化输出的 responseFormat 全部以 zod 对象为第一公民。版本直接上 v4（^4.6.6），但用户存量代码里仍有大量 v3 实例——core 的解法是 **interop 层**：utils/types 下的 InteropZodType/InteropZodObject 等类型与判别工具，同时接受 v3 与 v4 实例并抹平 API 差异（L101 展开 interop 细节）。配套的 `@standard-schema/spec ^1.1.0` 是社区规范包：zod v4 原生实现了 Standard Schema 接口，core 的 standard_schema 工具（src/utils/standard_schema.ts）据此让任意遵循规范的 schema 库都能接入。

### @cfworker/json-schema：Zod 之外的第二校验引擎

```ts
// src/utils/json_schema.ts:2,18
import { dereference, type Schema } from "@cfworker/json-schema";
export { deepCompareStrict, Validator } from "@cfworker/json-schema";
// src/output_parsers/transform.ts:1
import { deepCompareStrict } from "@cfworker/json-schema";
```

*— libs/langchain-core/src/utils/json_schema.ts:2-18、libs/langchain-core/src/output_parsers/transform.ts:1、libs/langchain-core/src/tools/index.ts:6（commit 7704471）*

消费点三个：utils/json_schema.ts 直接 re-export 其 Validator（JSON Schema 实例校验器）与 deepCompareStrict（严格比较），作为 Zod 互操作之外的通用校验出口；StructuredTool 用它校验 JSON Schema 形式的工具输入（当 schema 以 JSON Schema 而非 zod 给出时，L21）；output_parsers/transform.ts 在结构化输出解析侧消费 deepCompareStrict 做比对。选 @cfworker 的理由同 js-tiktoken：**体积小、纯 JS、无 node 特有依赖**。注意它在依赖表里排在第一位——工具输入校验是 agent 安全的第一道闸，core 不敢把它做成可选。

### langsmith：唯一的「平台级」硬依赖

```json
"langsmith": ">=0.11.0 <1.0.0"
```

*— libs/langchain-core/package.json:30（commit 7704471）*

七个依赖里唯一语义可疑的是 langsmith——可观测平台客户端为什么是硬依赖？因为 **Tracer 家族（L92）直接构造 langsmith 的 RunTree 做上报**，回调体系在 core 里是同步集成的：哪怕你从不配 LANGSMITH_API_KEY，Tracer 的类型与回调管理器也在运行。这是「可观测性默认内置」哲学的代价——core 永远背着这个客户端。主包同样声明了相同的 langsmith 范围（libs/langchain/package.json:79），两包共享同一实例。

### 依赖决策的四条设计准则

把七个依赖放回一张表，可以看出 core 选依赖的准绳：

| 依赖 | 职责 | 选型准则 |
|---|---|---|
| zod | schema 一等公民 | 直接上 v4 + interop 兼容 v3 |
| @standard-schema/spec | schema 规范接口 | 1KB 规范包换生态互换性 |
| mustache | 模板插值 | 轻量（handlebars 留给 classic） |
| p-queue | 并发纪律 | 成熟小库，非自研 |
| js-tiktoken | token 计数 | 纯 JS 保浏览器兼容 |
| @cfworker/json-schema | 第二校验引擎 | 纯 JS、零 node 依赖 |
| langsmith | 可观测上报 | 平台集成默认内置 |

**四条准绳：纯 JS 无 native、轻量不重叠、规范优先于实现、平台能力默认在。** 对照 classic 的依赖表（handlebars、js-yaml、jsonpointer、openapi-types、yaml）能看出代际差：classic 的依赖大多服务「装载与解析旧格式」，core 的依赖全部服务「运行时纪律」。

### 本课小结

- mustache → prompts/template.ts（模板插值，handlebars 是 classic 的历史包袱）；p-queue → async_caller.ts + singletons/callbacks.ts（并发纪律）。
- js-tiktoken 与 @cfworker/json-schema 都为「纯 JS、浏览器兼容」而选，后者是 Zod 之外的第二条校验引擎。
- zod ^4.6.6 直上 v4，interop 层兼容 v3 实例；@standard-schema/spec 让非 zod 的 schema 库也能接入。
- langsmith 是唯一的平台级硬依赖（>=0.11.0 <1.0.0），Tracer 家族直接消费 RunTree。
