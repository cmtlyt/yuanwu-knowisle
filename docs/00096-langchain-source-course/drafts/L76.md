### 定锚：确定性不是风格问题，是协议

L75 看到 tick 把收尾工作全部委托给 `_applyWrites`。这个函数（algo.ts:308-464，约 160 行）承担了 BSP 模型里最微妙的责任：**多个并行任务对同一组通道的写入，应用顺序必须处处一致**——本次进程如此，checkpointer 重放历史 checkpoint 时也如此，换一台机器重放还是如此。核心结论：**排序键不是任务 id、不是完成时间，而是序列化的任务路径；它与存储层排序同源，所以「live 执行 = 可重放」**。

*— pregel/algo.ts:328-334（commit fa426b2）*

函数头部的长注释值得整段精读，它交代了三个事实。**其一**，排序键是「序列化的完整 task path」，与每个 saver 存储写入时的 `writesSortKey` 完全相同，因此 live 执行与 checkpointer 重放不可能漂移。**其二**，到达这里的路径不带任务 id——调用输入路径在 `_prepareSingleTask` 与 `acceptPush` 里被截成 `slice(0, 3) + true/false`，这消除了「同一逻辑节点在两次运行中拿到不同任务 id」的不确定性。**其三**，注释直接点名了历史 bug：

```ts
// Note: no DeltaChannel-specific reordering here. Concurrent writes to a
// DeltaChannel apply in task-path order, exactly like every other channel
// and exactly like the savers replay them (`writesSortKey`); the task-id
// re-sort this replaces (langgraphjs#2544) made live order match a task-id
// replay instead, which permuted parallel writers checkpoint by checkpoint.
```

*— pregel/algo.ts:386-390（commit fa426b2）*

旧实现按 task id 重排序，后果是**同一组并行写者的归并次序随 checkpoint 逐个漂移**——reducer 不满足交换律时（比如消息列表、字符串拼接），每次保存的快照都可能是不同排列的结果。修复后的注释还补充了一个细节：嵌套父索引场景下旧的「三元素数组比较」会把 `10` 排在 `2` 之前（字符串序陷阱），序列化 path 比较器顺带修正了这一点。**平局时保持插入顺序**——sort 是稳定排序，键里携带默认的 task-id/idx 平局分量，对齐 Python 的 `sorted`。

### 管线第二段：versions_seen、消费与分组

```ts
let bumpStep = false;
const channelsToConsume = new Set<string>();
for (const task of tasks) {
  if (task.triggers.length > 0) bumpStep = true;
  checkpoint.versions_seen[task.name] ??= {};
  for (const chan of task.triggers) {
    if (chan in checkpoint.channel_versions) {
      checkpoint.versions_seen[task.name][chan] = checkpoint.channel_versions[chan];
    }
    if (!RESERVED_SET.has(chan)) {
      channelsToConsume.add(chan);
    }
  }
}
let consumedVersion: number | string | undefined;
for (const chan of channelsToConsume) {
  if (chan in onlyChannels && onlyChannels[chan].consume()) {
    if (getNextVersion !== undefined) {
      consumedVersion ??= getNextVersion(maxVersion);
      checkpoint.channel_versions[chan] = consumedVersion!;
    }
  }
}
```

*— pregel/algo.ts:340-371（commit fa426b2）*

单遍扫描完成三件事。**versions_seen 先记**：每个任务把自己触发通道的当前版本记为「已见」——这是下一次 shouldInterrupt 比较的基线，先于任何写入应用。**消费通道收集**：触发通道里非保留名的进入 consume 集合（barrier 的 seen 清空、LastValueAfterFinish 的读后即焚都由 consume() 驱动）。**版本一次性铸造**：`consumedVersion ??= getNextVersion(maxVersion)` 保证本批被消费的通道共享同一个新版本号，注释解释这是 Python 对齐——否则支持随机小数的 saver 会给同批通道不同版本，updateState 的「Ambiguous update」检查会误判。保留名集合 `IGNORE`（NO_WRITES/PUSH/RESUME/INTERRUPT/RETURN/ERROR/ERROR_SOURCE_NODE，algo.ts:296-304）则在按通道分组写入时被剔除——这些是协议哨兵，不是通道数据。

`triggersNextStep` 用「更新通道是否还触发下游节点」来**预判**这是不是最后一个超步；若没有后续，所有通道的 `finish()` 被调用——NamedBarrierValueAfterFinish 与 LastValueAfterFinish 的门控开启都挂在这个钩子上（L72 的屏障三兄弟由此获得「图收尾才放行」能力）。断点判定则完全站在 checkpoint 上：

断点 = 「有通道版本前进」∧「目标节点被触发」的合取。`"*"` 通配会放过带 TAG_HIDDEN 的内置写手（START/control branch），避免控制流噪声触发断点。注意它比较的是 `versions_seen[INTERRUPT]` 这个**专用键**，不是任何任务自己的 seen——断点是图级视角，与节点的读视图无关。

### 本课小结

- **排序键 = 序列化 task path**，与 saver 的 writesSortKey 同源；#2544 的教训是 task id 排序会让并行写者归并序随 checkpoint 漂移。
- 管线次序：排序 → 记 versions_seen → 收集消费通道（版本一次性铸造）→ 按通道分组（剔保留名）→ update 应用（错误包装）→ bumpStep 步进通知 → finish 钩子。
- `update([])` 是通道协议的步进分支，Topic/EphemeralValue 的生命周期依赖它；finish() 是「预判无后续」时的收尾广播。
- shouldInterrupt 完全基于 checkpoint 的版本比较，`"*"` 通配排除 TAG_HIDDEN。
