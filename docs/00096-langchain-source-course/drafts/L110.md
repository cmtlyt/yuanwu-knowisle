### 最戏剧性的一组映射：摘要记忆变成中间件

Memory 族迁移里最有代表性的案例是摘要记忆：旧 ConversationSummaryMemory 是一个挂链上的记忆类，新 summarizationMiddleware 是执行环上的可组合切面。核心结论：**「摘要记忆」这个概念没死，它换了一整个架构住址——从「链对象的隐藏变量 + 手动调用」搬进「agent 执行环的 hook 切面 + 声明式参数」，语义一一对应但实现彻底重构。**本课逐参数对照，commit 7704471 取证。

### 旧世界：预测、累积、注入三步

先看旧类的骨架（summary.ts:127 及其父类）：

```ts
export class ConversationSummaryMemory extends BaseConversationSummaryMemory {
  buffer = "";

  get memoryKeys() {
    return [this.memoryKey];   // 默认 "history"
  }
  // 父类核心：predict_new_summary(messages, prevSummary) 用 LLMChain 调模型
}
```

*— langchain-classic/src/memory/summary.ts:127-133（commit 7704471，有裁剪）*

旧摘要记忆的工作流是三步循环：每次 saveContext 后把新一对 Human/AI 消息交给 `predict_new_summary` 的 LLMChain → 模型把「上轮摘要 + 新消息」压缩成新摘要写进 buffer → 下一轮 loadMemoryVariables 时把 buffer 字符串填进模板的 {history} 占位符。配套的 ConversationSummaryBufferMemory（summary_buffer.ts:59）再加一条「buffer 超长时回退到原始消息」的策略。注意摘要**真的在调模型**，且 buffer 单变量累积——没有消息结构，只有一段文本。

### 新世界：trigger/keep 两端旋钮

新中间件的参数面（summarization.ts:160-205 的 schema 摘录）：

```ts
// 触发条件：fraction / tokens / messages 三维
trigger: z.union([contextSizeSchema, z.array(contextSizeSchema)]).optional(),
// 保留条件：fraction / tokens / messages 三维
keep: keepSchema.optional(),
// token 计数器与摘要提示词
tokenCounter: tokenCounterSchema.optional(),
summaryPrompt: z.string().default(DEFAULT_SUMMARY_PROMPT),
summaryPrefix: z.string().optional(),
trimTokensToSummarize: z.number().optional(),
```

*— langchain/src/agents/middleware/summarization.ts:171-186（commit 7704471，schema 裁剪）*

默认值三件套（summarization.ts:65-66）：`DEFAULT_MESSAGES_TO_KEEP = 20`、`DEFAULT_TRIM_TOKEN_LIMIT = 4000`、`DEFAULT_FALLBACK_MESSAGE_COUNT = 15`。内置提示词 DEFAULT_SUMMARY_PROMPT（summarization.ts:36）是一个完整的「Context Extraction Assistant」角色设定，要求模型只输出提取的上下文。触发逻辑的语义要记牢：**单条件对象内部三维 AND，数组条件之间 OR**（JSDoc 原例：`trigger: [{ tokens: 5000, messages: 3 }, { tokens: 3000, messages: 6 }]`）。

参数合法性由 Zod schema 在运行时把关（summarization.ts:78-100，commit 7704471），三条约束值得记下：fraction 必须在 (0, 1] 区间（错误消息原文 "Fraction must be greater than 0" / "less than or equal to 1"）；tokens 与 messages 必须为正数，messages 还必须是整数（"Messages must be an integer"）；整个对象带一个 refine——**三维里至少要给一个**，全空的 trigger 会在 parse 阶段报 "At least one of fraction, tokens, or messages must be provided"。这些校验发生在中间件构造时而不是第一次摘要时，配置错误在启动期就暴露。tokenCounter 的形态约束也在 schema 里（summarization.ts:70-73）：一个接受 BaseMessage 数组、返回 number 或 Promise<number> 的函数——返回同步还是异步都收，但签名形状必须吻合，传错形态（比如传了个模型实例）会在构造期报 Zod 错误。

### 逐参数对照表

| 旧 ConversationSummaryMemory 语义 | 新 summarizationMiddleware 参数 | 备注 |
|---|---|---|
| 每轮都摘要（手动驱动） | trigger: { tokens/messages/fraction } | 新版是条件触发，不是每轮必摘 |
| buffer 累积 + 预测 | 摘要整体重生成 + REMOVE_ALL_MESSAGES 替换历史 | 机制不同：增量累积→条件全量替换 |
| memoryKey 输出变量 | 无变量——直接改写 messages 状态 | 隐式变量协议退役 |
| 摘要 prompt 可自定义 | summaryPrompt / summaryPrefix | 默认 DEFAULT_SUMMARY_PROMPT |
| summary_buffer 的超长回退 | trimTokensToSummarize + 内置配对保护 | SEARCH_RANGE_FOR_TOOL_PAIRS=5 保 AI/Tool 配对 |
| —（无对应） | keep: { messages/tokens/fraction } | 保留多少近期原文，旧版无精细旋钮 |

有两行要特别讲。**触发时机**：旧版「每轮 saveContext 后摘要」是时间驱动，新版是条件驱动（beforeModel hook 检查 trigger），这更省调用也更需要你理解自己的对话量级。**替换机制**：旧版往模板塞 buffer 字符串，新版用 `RemoveMessage` + `REMOVE_ALL_MESSAGES` 清空旧历史再注入摘要消息——这就是 L104 说的「状态显式化」在摘要场景的落地：所有改写在 messages 状态里可见、可回放。

### 改写实战

```ts
import { createAgent, summarizationMiddleware } from "langchain";

// 简版：默认提示词 + 默认参数，开箱即用
const agent = createAgent({
  model: "openai:gpt-4o",
  middleware: [
    summarizationMiddleware({
      trigger: { tokens: 4000, messages: 20 },  // AND：两个条件都满足才触发
      keep: { messages: 20 },                    // 触发时保留最近 20 条原文
    }),
  ],
  checkpointer: new MemorySaver(),
});

// 对照旧 ConversationSummaryMemory 的自定义摘要指令：
const customized = createAgent({
  model: "openai:gpt-4o",
  middleware: [
    summarizationMiddleware({
      trigger: [
        { tokens: 3000, messages: 6 },   // OR：任一满足即触发
        { tokens: 6000 },
      ],
      summaryPrompt: "你是项目会议记录员，提取决定、待办、未解决问题，忽略寒暄。",
      summaryPrefix: "以下是此前讨论的摘要：",
    }),
  ],
});
```

验证清单：构造一段超过 trigger 的对话，确认摘要消息出现在历史中且旧消息被移除（getState 检查）；确认 trigger 未达到时中间件零干预；确认 AI/Tool 配对没被切断（故意在工具调用后触发摘要）。三个断言各对应一个源码机制：第一个对应 RemoveMessage+REMOVE_ALL_MESSAGES 的替换实现，第二个对应 beforeModel hook 里的条件评估——**不触发就零开销**，这正是条件驱动相对旧版「每轮必摘」的成本优势；第三个对应 SEARCH_RANGE_FOR_TOOL_PAIRS 的回扫窗口。落地为可执行的验证脚本：

```ts
import { createAgent, summarizationMiddleware } from "langchain";
import { MemorySaver } from "@langchain/langgraph/checkpoint";

const agent = createAgent({
  model: "openai:gpt-4o",
  middleware: [summarizationMiddleware({ trigger: { tokens: 500 }, keep: { messages: 4 } })],
  checkpointer: new MemorySaver(),
});

const config = { configurable: { thread_id: "verify-1" } };
for (let i = 0; i < 12; i++) {
  await agent.invoke({ messages: [{ role: "user", content: `第 ${i} 轮：补充一些上下文文本。` }] }, config);
}
const state = await agent.getState(config);
// 断言 1：消息总数被压缩（远小于 12 轮的原始消息数）
console.log("消息条数:", state.values.messages.length);
// 断言 2：历史开头是摘要前缀，而非原始第一条
console.log("首条:", JSON.stringify(state.values.messages[0]?.content).slice(0, 60));
// 断言 3：AI/Tool 配对完整——扫描 tool_calls 与 ToolMessage 的 tool_call_id
const ids = state.values.messages.flatMap((m: any) => m.tool_calls?.map((c: any) => c.id) ?? []);
const replied = new Set(state.values.messages.filter((m: any) => m.type === "tool").map((m: any) => m.tool_call_id));
console.log("配对完整:", ids.every((id: string) => replied.has(id)));
```

旧参数到新参数的机械对照也顺手记一下，迁移时按此改写而不是照抄旧名：`maxTokensBeforeSummary: 4000` 改为 `trigger: { tokens: 4000 }`；`messagesToKeep: 10` 改为 `keep: { messages: 10 }`。中间件运行时会对旧参数名抛出过渡告警（summarization.ts:314 的提示逻辑），这是官方留的迁移护栏，别把它当 bug 报掉。配置层面的选型经验收个尾：短对话（常态低于 trigger 阈值）不需要这个中间件，trimMessages 就够——中间件的 hook 本身有调用开销，摘要触发的模型调用也是真实成本；高频长对话才值得开，且 trigger 阈值要按对话量级实测调参，照抄默认的 4000/20 组合在大多数业务里要么太松要么太紧。

### 内部走读：配对保护、默认前缀与废弃参数的运行时处理

参数面之外，中间件内部有三个值得逐行看的机制，迁移调试时都用得上。

**配对保护的实现常量**。summarization.ts:68（commit 7704471）定义 `const SEARCH_RANGE_FOR_TOOL_PAIRS = 5;`，用法在 :781-784：确定摘要替换的截断点后，在 `cutoffIndex ± 5` 的窗口内回扫 AI 消息与其 ToolMessage 的 tool_call_id 配对，发现配对被切断就把截断点外移。这意味着 keep 边界附近的完整性是中间件内置的，不需要你在业务层写「检查配对」的补偿逻辑——但窗口只有 5 条，极端场景（一次模型调用串起超过 5 个工具调用）要单独验证。

**默认摘要前缀**。`const DEFAULT_SUMMARY_PREFIX = "Here is a summary of the conversation to date:"`（summarization.ts:64）。summaryPrefix 参数未提供时，摘要消息在历史里的开头就是这个英文前缀——排查「历史里哪条是摘要」时按它识别；要做中文前缀就在 summaryPrefix 里给。

**废弃参数不是抛错，是转换加告警**。summarization.ts:310-330 的运行时处理值得原文走读：检测到 `maxTokensBeforeSummary !== undefined` 时先 `console.warn("maxTokensBeforeSummary is deprecated. Use trigger: { tokens: value } instead.")`，然后**只在 trigger 未显式给出时**转换为 `trigger = { tokens: userOptions.maxTokensBeforeSummary }`；messagesToKeep 对 keep 同理。三个推论：其一，「抄旧名」不会崩——有过渡护栏；其二，新旧参数混用时新参数优先，旧值被忽略且可能静默偏离预期；其三，告警是 console.warn 不是异常，生产日志里要专门盯。迁移策略上，正确的做法仍是按新参数面一次性改写，把护栏留给确实来不及改的存量调用。

### 本课小结

- 摘要记忆的迁移是「架构住址」的变化：链上的记忆类 → beforeModel hook 的 middleware；参数面从 memoryKey/predict_new_summary 换成 trigger/keep/summaryPrompt，构造期 Zod 校验（fraction 区间、整数约束、至少一维）让配置错误在启动期暴露。
- 默认值：keep 20 条、trim 4000 tokens、fallback 15 条、配对回扫窗口 5 条；单条件 AND、数组条件 OR。
- 替换机制换代：增量 buffer 累积 → RemoveMessage+REMOVE_ALL_MESSAGES 全量替换，历史操作全程可见可回放。
- 旧参数名 maxTokensBeforeSummary/messagesToKeep 已 @deprecated，运行时转换为告警加静默映射（新参数优先），抄名不抄义会在 deprecated 警告里撞墙。
- 下一课收掉 Memory 族尾巴：EntityMemory/CombinedMemory/VectorStoreRetrieverMemory 的 1.x 化身——它们没有现成中间件，要自组。
