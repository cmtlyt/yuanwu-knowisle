### 定位：工具执行层的洋葱

L54 解决「模型调用怎么改」，本课解决「工具执行怎么拦」。wrapToolCall 是六 hook 中唯一包裹**单次工具执行**的 hook：模型决定调工具后，ToolNode 执行每个 tool_call 前都会先穿过中间件洋葱。它与 ToolNode 的联动比 wrapModelCall 与 AgentNode 的联动更深——因为工具执行天然带着两类不确定性（参数错、工具崩），ToolNode 为此设计了一套「中间件错误默认致命、工具错误默认喂回」的非对称错误策略，这是本课的核心考点。

一句话结论：**wrapToolCall = ToolCallRequest 洋葱 + ToolMessage/Command 出口**，短路返回一条 ToolMessage 就等于替工具回答了模型。

### ToolCallRequest 与执行入口

ToolNode 侧的接线在 runTool：构造 request 后，若存在 wrapToolCall 就 `await this.wrapToolCall(request, baseHandler)`，错误交给 #handleError 并标记 isMiddlewareError=true（ToolNode.ts:433-452）；没有中间件才走「直接执行 + 默认错误处理」路径。还有个容易漏的前提：**这个节点按需创建**——ReactAgent 只在有客户端工具或有 wrapToolCall 中间件时才建 ToolNode（ReactAgent.ts:403-414），纯服务端工具的 agent 里你的 wrapToolCall 根本没有舞台。

runTool 的两分支结构值得画一遍，它就是「错误处理归口」的物理布局。有 wrapToolCall 时：`try { return await this.wrapToolCall(request, baseHandler) } catch { return this.#handleError(e, call, true) }`——注意第三参 true 就是 isMiddlewareError 标记，**无论错误实际来自中间件代码还是洋葱内层的工具执行**，只要从 wrapToolCall 调用点冒出来就先按「中间件来源」对待，再由 #handleError 的 cause 链解包还原真实身份。无 wrapToolCall 时：先查工具缺失给优雅降级消息（455-463），再 try/catch baseHandler 走 false 分支的 #handleError（465-475）。还有一个注释级边界：baseHandler 里那句「When wrapToolCall middleware is present, this handler does NOT catch errors」（ToolNode.ts:345）——baseHandler 自己的错误捕获在有洋葱时被有意关闭，避免同一错误被两层 try/catch 重复处置。两分支最终汇于同一个 #handleError，但来源标记不同：这就是「工具错误可自愈、中间件错误须人查」这条非对称策略的接线位置。

### MiddlewareError 的包装纪律与 cause 链下钻

#handleError 开头的注释是本课最重要的一段工程文档（ToolNode.ts:250-261），值得整段读：可恢复的工具错误（如入参 schema 校验失败）会被重包装为 MiddlewareError、原始错误挂在 `.cause` 上——**每层 wrapToolCall 中间件包一次，嵌套几层就包几层**。所以 ToolNode 看到的错误可能穿着多层 MiddlewareError 外衣，下钻循环 `while (MiddlewareError.isInstance(unwrapped)) unwrapped = unwrapped.cause` 走到根，若根是 ToolInvocationError 就解包还原，让 handleToolErrors 的自愈路径继续生效；真中间件错误默认致命。三个推论。其一，多层洋葱不会丢失错误身份——包装层数与解包循环天然对齐。其二，中间件自己的 try/catch 会打断包装纪律：如果你在 wrapToolCall 里 catch 了错误又 rethrow 一个全新的 Error，MiddlewareError 外衣就没了，解包循环找到的根不是 ToolInvocationError，自愈失效——**想透传就原样 rethrow，别造新壳**。其三，toolRetry/toolError（L58）都遵守这条纪律，它们的 bubble-up 检查放在 catch 第一行，正是为了在包装发生之前就把控制流信号放出去。

### 实战一：缓存 + 鉴权中间件

```ts
import { createAgent, createMiddleware, ToolMessage } from "langchain";

const cache = new Map<string, ToolMessage>();

const guard = createMiddleware({
  name: "GuardMiddleware",
  wrapToolCall: async (request, handler) => {
    const { toolCall } = request;
    // 鉴权短路：无权限时直接替工具回答
    if (!isAuthorized(request.runtime.context, toolCall.name)) {
      return new ToolMessage({
        content: "Unauthorized to call this tool",
        tool_call_id: toolCall.id!,
        status: "error",
      });
    }
    // 缓存命中短路
    const key = `${toolCall.name}:${JSON.stringify(toolCall.args)}`;
    if (cache.has(key)) return cache.get(key)!;
    // 放行：进内层（下一个中间件或真实工具）
    const result = await handler(request);
    if (ToolMessage.isInstance(result)) cache.set(key, result);
    return result;
  },
});

const agent = createAgent({
  model: "openai:gpt-4o",
  tools: [searchTool, calculator],
  middleware: [guard],
});
const out = await agent.invoke({ messages: [{ role: "user", content: "查天气" }] });
```

这段覆盖了 wrapToolCall 的三种出口：**短路回答**（鉴权失败）、**短路命中**（缓存）、**放行**（handler(request)）。注意缓存键里 toolCall.id 不能进 key——它每次都不同。

把缓存键的设计再掰细一点，这是实战里最容易出错的位置。键的成分按稳定性排序只有三类可用：工具名（稳定）、args 的规范化序列化（稳定，前提是模型对同一意图生成一致参数）、runtime 里的租户/用户标识（稳定且必要——多租户场景下不进 key 就是数据串门）。三类不可用：toolCall.id（每次不同）、state 全量（太大且含历史）、Date.now() 类时变值（缓存永久 miss）。args 序列化还有个隐患：模型两次调用参数顺序不同时 `JSON.stringify` 的键序可能不一致，严格的做法是按键排序后再序列化。另外缓存存 ToolMessage 实例时要注意共享可变对象的风险——命中方拿到的与存入方是同一个对象，任何消费者原地改 content 都会污染缓存；存 `new ToolMessage({...cached})` 的副本更稳。鉴权短路返回的 error ToolMessage 也有一处讲究：status: "error" 让模型把它当失败处理并可能换路径，而不是当工具结果消费——**短路消息的 status 选择决定了模型下一步行为**，这是幂等设计在模型对话层的表现。

### 实战二：动态工具补位 + 错误分级

ToolNode 的 baseHandler 支持 request.tool 覆盖注册表查找（ToolNode.ts:355-363），于是可以为运行时才决定的工具补实现；同时按「错误来源」分级处理。

```ts
import { isGraphBubbleUp } from "@langchain/langgraph";

const faultLine = createMiddleware({
  name: "FaultLineMiddleware",
  wrapToolCall: async (request, handler) => {
    // 动态工具补位：agent 创建时没声明 dynamic_tool
    if (request.toolCall.name === "dynamic_tool" && !request.tool) {
      return handler({ ...request, tool: myDynamicTool });
    }
    try {
      return await handler(request);
    } catch (e) {
      if (isGraphBubbleUp(e)) throw e;   // 控制流信号：绝不吞
      return new ToolMessage({           // 真工具错误：转 error ToolMessage
        content: `tool failed: ${String(e)}`,
        tool_call_id: request.toolCall.id ?? "",
        name: request.toolCall.name,
        status: "error",
      });
    }
  },
});
```

`isGraphBubbleUp` 的直接 rethrow 不是装饰——内置 toolRetryMiddleware 在 catch 的第一行就做了同样的事（toolRetry.ts:292-294），因为 interrupt/resume 信号以异常形式穿过工具层，吞掉它们会让 HITL 永久卡死。

### 错误的非对称策略：读 ToolNode 的 #handleError

```ts
if (isGraphInterrupt(error) || isGraphDrained(error)) {
  throw error;                       // 断点/drain 永远重抛
}
if (this.signal?.aborted) {
  throw error;                       // 取消信号向上冒泡
}
if (isMiddlewareError) {
  let unwrapped: unknown = error;
  while (MiddlewareError.isInstance(unwrapped)) {
    unwrapped = unwrapped.cause;     // 沿 cause 链下钻
  }
  if (ToolInvocationError.isInstance(unwrapped)) {
    effectiveError = unwrapped;      // 是参数校验错 → 按工具错误处理
    errorFromMiddleware = false;
  }
}
if (errorFromMiddleware && this.handleToolErrors !== true) {
  throw effectiveError;              // 真·中间件错误默认致命
}
```

三个要点：其一，默认 handleToolErrors 只兜「工具执行」的错并转成带 `Please fix your mistakes.` 提示的 error ToolMessage（ToolNode.ts:119-140），让模型看到错误自行修正参数；其二，中间件错误**默认致命**，因为中间件逻辑是你写的，静默喂回会掩盖 bug；其三，中间件若 rethrow 了被 MiddlewareError 包住的 ToolInvocationError，ToolNode 会沿 cause 链解包还原「参数错 → 自纠」路径。并行执行也在这里收口：多个 tool_call 经 Promise.all 同时进洋葱，每个 call 各自包一层，互不共享短路结果。

### 并行语义与计数器陷阱

还有一层容易被漏看的执行粒度：ToolNode 对一条 AIMessage 里的**每个 tool_call 独立调用一次 runTool**（ToolNode.ts:537-541 的 Promise.all），所以三个并行调用会让整条 wrapToolCall 洋葱链跑三遍。后果有二。其一，中间件里的计数器与日志按调用次数放大——这与 wrapModelCall「每轮模型调用一次」的粒度完全不同，把同一份监控代码从模型层搬到工具层时数字会突然变大数倍。其二，闭包级缓存跨调用共享，缓存键里混入 toolCall.id 会让缓存永不命中（id 每次不同）。把粒度想清楚，还能反推一个架构问题：为什么 L63 的 per_call 审批必须挂在 wrapToolCall 而不是 afterModel——因为只有逐调用的洋葱位置才能给每个 tool_call 单独发 interrupt、单独校验答复；afterModel 那个位置看到的只是「一包调用」，这正是 batched 模式选择它的原因。两种模式的分野，在 ToolNode 的并行执行模型里就已经埋下伏笔。

### 本课小结

- wrapToolCall 的舞台按需搭建：有客户端工具或有 wrapToolCall 中间件才有 ToolNode。
- 三种出口：短路 ToolMessage（鉴权/缓存/限流）、补位动态工具（tool 覆盖）、放行 handler(request)。
- 错误非对称：工具错误默认转 error ToolMessage 喂回模型自纠；中间件错误默认致命上抛；`handleToolErrors: true` 才会把中间件错误也转消息。
- 图级控制流信号（interrupt/drain）与 abort 信号永远重抛——自己写容错时先 `isGraphBubbleUp` 再谈重试。
