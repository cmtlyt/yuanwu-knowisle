### 转发层：最薄也最关键的 78 行

L03 数过主包根导出面的六组导出，本课换个视角：**这六组导出各自承担什么版本稳定性角色**。把 78 行 index.ts 按「实现来源」分三类——core 转发、主包自有、export * 聚合——你会发现一个包如何用「转发」这个零成本语法，同时做到对用户稳定、对依赖灵活。

### 三类导出的分类学

```ts
// 类一：core 转发（6 组中的 4 组）
export { BaseMessage, AIMessage, SystemMessage, HumanMessage, ToolMessage,
  filterMessages, trimMessages } from "@langchain/core/messages";
export { Tool, DynamicTool, StructuredTool, DynamicStructuredTool } from "@langchain/core/tools";
export { context } from "@langchain/core/utils/context";
export { InMemoryStore } from "@langchain/core/stores";
export { type DocumentInput, Document } from "@langchain/core/documents";

// 类二：主包自有实现
export { initChatModel } from "./chat_models/universal.js";
export { tool, type HeadlessTool, ... } from "./tools/headless.js";

// 类三：export * 聚合（重心所在）
export * from "./agents/index.js";
export * from "./agents/middleware/index.js";
```

*— libs/langchain/src/index.ts（commit 7704471，按实现来源重新分组摘录）*

**类一（core 转发）**的主语是「门牌」：主包不拥有这些符号，只提供入口。**类二（自有实现）**只有两个成员——initChatModel 与 headless tool，它们是主包对 core 能力的真实增量。**类三（聚合）**把主包的重心（agents + 20 个 middleware）整面倒出。三类导出的比例本身就说明主包的架构姿态：**大部分 API 面是 core 的镜像，小部分是 harness 增量，核心价值在 agents 面内聚**。

### 转发为什么能隔离版本演进

re-export 的机制值得钉死：`export { AIMessage } from "@langchain/core/messages"` 编译产物里不包含 AIMessage 的实现，只包含一个指向 core 包的再导出引用。于是形成这样的稳定性链条：

```text
用户代码  ──import──▶  langchain 根面（契约层，签名稳定）
                          │ re-export（零复制）
                          ▼
                      @langchain/core/messages（实现层，可独立演进）
```

core 升级（1.4.0 → 1.4.1）时，只要它对外的符号集合与类型签名兼容，主包导出面就自动「继承」了修复与优化——**主包不需要重新审查内部实现，因为它根本没有内部实现**。反过来，主包要调整产品重心（比如某个消息类不再主推），只需要改 index.ts 的白名单清单，core 与用户代码都不受影响。两层各自变更、契约层缓冲——这就是「转发层作为版本稳定策略」的全部含义。

还有一个容易被忽略的运行时收益：**转发不产生新对象**。用户从主包拿到的 AIMessage 与从 core 拿到的是同一个类对象（`langchain.AIMessage === core.AIMessage` 为 true），所以无论从哪个门牌导入，instanceof、序列化、类型判断全部天然一致。对照反模式：如果主包写成 `class AIMessage extends CoreAIMessage` 的包装类，每包装一层就多一个物理类——L05 的判型方案会被包装层撕开裂缝。1.x 全线坚持纯转发，包装为零。

### 白名单的挑选逻辑：谁有资格进根面

对比 core 的 74 个子路径与主包白名单的十几个符号，能反推出进根面的标准：

| 进了根面 | 没进根面 | 差异维度 |
|---|---|---|
| BaseMessage 五类 + 各 Chunk | RemoveMessage、FunctionMessage、ChatMessage | 高频对话循环 vs 低频/特化场景 |
| filterMessages / trimMessages | mergeMessageRuns 等其余消息工具 | 常用消息整理 vs 长尾工具 |
| Tool/StructuredTool 等五原语 | tool() 工厂（由主包自有 tool 接管） | 类与类型直接给，工厂用增强版 |
| InMemoryStore / Document | VectorStore、Embeddings 基类 | 最小数据入口 vs 完整 RAG 体系 |
| （无） | RunnableSequence/RunnableMap 等组合原语 | 组合层整体引导去 core/runnables |

规律清晰：**根面给「写标准 agent 流程的最短路径」，其余引导子路径精确导入**。这不是偷懒，是导出面契约的面积控制——根面每个符号都是主包的兼容承诺，面积越小，未来演进越自由。classic 的 100 子路径（L07）与 core 的 74 子路径没有这个顾虑：博物馆不做兼容演进，原语库按模块承诺。

### export * 聚合与子路径双轨

```ts
export { createMiddleware } from "./middleware.js";
export { MIDDLEWARE_BRAND } from "./middleware/types.js";
export { toolStrategy, providerStrategy, /* … */ } from "./responses.js";
export type { Runtime } from "./runtime.js";
```

*— libs/langchain/src/agents/index.ts:710-726（commit 7704471，节选）*

agents/index.ts 自身也是一个「内层转发面」：createAgent 重载 + 一批显式 re-export（types/errors/nodes/responses 的符号）。主包根面的两条 `export *` 把这层内面整块提升，于是出现双轨导入路径：`import { createAgent } from "langchain"` 与 `import { createAgent } from "langchain/agents"`（经由子路径产物）都成立——**根面给便利，子路径给精确，运行时同一对象**。middleware 同理：`from "langchain"` 或 `from "langchain/agents/middleware"`。

### browser 镜像：同一策略的第二个实例

```text
libs/langchain/src/browser.ts
├── 同样的消息白名单（来自 @langchain/core/messages）
├── initChatModel、tool/headless 转发
├── export * from "./agents/index.js" 与 middleware/index.js
└── stores/documents/testing 转发
```

*— libs/langchain/src/browser.ts 目录结构实测（commit 7704471）*

browser.ts 没有任何对 index.ts 的引用，而是把同一份导出清单**独立复写**了一遍。为什么不用 `export * from "./index.js"`？因为两条产物线的打包器会按 exports 的 browser 条件直接解析到 browser.ts，镜像文件让两条线的依赖分析完全独立——Node 线不该出现的浏览器兼容分支不会经由 index.ts 混进来。代价是维护两份清单（改根面要同步改两处），这是用可维护性换隔离性的显式取舍。

### 易混淆点：re-export、聚合导出与 default 导出三兄弟

转发层的三个语法成员经常被混为一谈，值得并排放清楚。**其一，命名 re-export**（`export { AIMessage } from "@langchain/core/messages"`）：主包 index.ts 消息组的形态，符号直通，连名字都不变——这是契约层最严格的形态，core 里叫什么主包对外就叫什么。**其二，聚合 re-export**（`export * from "./agents/index.js"`）：把一个模块的命名导出整面转发，但有两个语言级边界要注意——`export *` **不转发 default 导出**，且遇到重名符号时会**静默丢弃**而不是报错（ESM 规范行为）。所以聚合的下游文件必须保证导出名互不冲突：agents/index.ts 与 middleware/index.js 各自是一块独立命名空间，两条 export * 并存的前提就是两边符号集不相交。**其三，default 导出**：整个主包根面**一个 default 都没有**——这不是疏忽而是立场，命名导入（`import { createAgent } from "langchain"`）让 IDE 补全、tree-shaking、循环依赖检测全部有据可依，default 的「随便叫什么」恰恰是导出面契约的反面。三个语言事实叠在一起就是一条审查标准：读任何库的 index.ts 时，看到命名 re-export 是契约承诺，看到 export * 要去查上游符号集，看到 default 导出则要警惕这个库的 API 稳定性姿态。

### 判断题：一个 API 该从哪导入

给你一条判据链：**先查主包根面 → 再查主包子路径（./chat_models/universal、./tools、./storage/*、./hub、./load）→ 最后查 core 子路径（74 个）→ 永远不进 classic（除非迁移）**。两个高频易错点：Runnable 组合原语与 prompt 模板基类都在 core；initChatModel 虽然也有 core 无关的独立子路径 ./chat_models/universal，但根面同样直接可取。

### 本课小结

- 主包导出面三类：core 纯转发（门牌）、自有实现（initChatModel + headless tool）、export * 聚合（agents + middleware 重心）。
- re-export 零复制：同一运行时对象多门牌，core 独立发版不破坏主包契约；包装类是明确反模式（会破坏判型）。
- 白名单逻辑：agent 主流程最短路径进根面，长尾与组合层引导 core 子路径；导出面面积即承诺面积。
- browser.ts 是根面的独立镜像而非引用转发，两条产物线依赖分析互不污染。
- 下一课拆主包的两个自有实现：initChatModel 的 provider 动态装载与 headless tool 的客户端委托——「唯二新增面」的完整解剖。
