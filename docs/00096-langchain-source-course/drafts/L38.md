### 开篇：重载分派轴上的四种输入

上一课我们把 14 个重载分成了一张总表；本课聚焦表里最重要的分派轴——`responseFormat` 的输入形态。这是全模块「口径最窄」的一课：只讲形态分类与类型/运行时两条线的联动，策略类（ToolStrategy/ProviderStrategy）的内部机制划界给 L96-L98。核心结论先行：**responseFormat 不仅决定「要不要结构化输出」，还同时决定类型层 Response 泛型的精确度、以及运行时状态 schema 里 structuredResponse 通道的有无——两条线用同一个布尔开关联动**。

### 形态一：Zod 对象——唯一「全精确」的路径

重载 1 是 14 个重载里唯一能从输入一路精确推到输出的 Zod 单对象形态：

```ts
// Overload 1: With responseFormat as single InteropZodType
export function createAgent<
  StructuredResponseFormat extends Record<string, any> = Record<string, any>,
  TStateSchema extends StateDefinitionInit | undefined = undefined,
  ContextSchema extends AnyAnnotationRoot | InteropZodObject =
    AnyAnnotationRoot,
  const TMiddleware extends readonly AnyAgentMiddleware[],
  const TTools extends readonly (ClientTool | ServerTool)[],
  const TStreamTransformers extends ReadonlyArray<() => StreamTransformer<any>>,
>(
  params: CreateAgentParams<
    StructuredResponseFormat,
    TStateSchema,
    ContextSchema,
    InteropZodType<StructuredResponseFormat>
  > & {
    responseFormat: InteropZodType<StructuredResponseFormat>;
    middleware?: TMiddleware;
    tools?: TTools;
    streamTransformers?: TStreamTransformers;
  }
): ReactAgent<AgentTypeConfig<StructuredResponseFormat, ...>>;
```

*— libs/langchain/src/agents/index.ts:176-211（commit 7704471）*

关键在 `InteropZodType<StructuredResponseFormat>` 这个参数位置：泛型 `StructuredResponseFormat` 不是从字段直接推断，而是**从 Zod schema 的输出类型反查**——`z.object({ name: z.string() })` 的输出类型是 `{ name: string }`，于是 `agent.invoke()` 返回状态里的 `structuredResponse` 就精确到 `{ name: string }`。这是 L19 讲过的 `withStructuredOutput` 能力契约在 agent 层的延续：Zod 实例本身就是「类型 + 运行时校验」的双载体，TS 只需要顺着它的泛型参数把 `T` 提出来。

### 形态二：Zod 数组——ExtractZodArrayTypes 的联合推导

传 Zod schema 数组时走重载 2，Response 泛型变成一个条件类型的结果：

```ts
// Overload 2: With responseFormat as array of InteropZodTypes (infers union type)
export function createAgent<
  StructuredResponseFormat extends readonly InteropZodType<any>[],
  ...
>(
  params: CreateAgentParams<
    ExtractZodArrayTypes<StructuredResponseFormat> extends Record<string, any>
      ? ExtractZodArrayTypes<StructuredResponseFormat>
      : Record<string, any>,
    ...
  > & {
    responseFormat: StructuredResponseFormat;
    ...
  }
): ReactAgent<AgentTypeConfig<ExtractZodArrayTypes<...>, ...>>;
```

*— libs/langchain/src/agents/index.ts:214-253（commit 7704471）*

`ExtractZodArrayTypes` 定义在 types.ts，是一个教科书式的递归条件类型：`T extends readonly [InteropZodType<infer A>, ...infer Rest]` 先用元组模式拆出第一个元素的输出类型 `A`，再对 `Rest` 递归调用自己，最后 `A | ExtractZodArrayTypes<Rest>` 合成联合。语义上这是「多个候选输出形态」：比如抽取任务里既可能产出联系方式（ContactInfo）也可能产出公司信息（CompanyInfo），模型在运行时通过 `extract-` 前缀的工具调用命中其中一个候选——所以最终值是联合中的一个个体，**不是数组**。注意这个条件类型还套了一层 `extends Record<string, any>` 守卫：递归结果若不是对象形状就退回 `Record<string, any>`，防止边缘输入污染类型。

### 形态三：JsonSchema / SerializableSchema——运行时有效，类型退化

重载 3-5 覆盖 `JsonSchemaFormat` 的单对象、数组、联合三种写法；重载 6-7 覆盖 `SerializableSchema` 的单对象与数组。五份签名结构完全一致，唯一差异是 responseFormat 字段类型，而它们共享同一个结果——Response 泛型固定为 `Record<string, unknown>`：

```ts
// Overload 3: With responseFormat as JsonSchemaFormat (JSON schema object)
export function createAgent<
  TStateSchema extends StateDefinitionInit | undefined = undefined,
  ...
>(
  params: CreateAgentParams<
    Record<string, unknown>,   // <-- Response 泛型：固定宽泛
    TStateSchema,
    ContextSchema,
    JsonSchemaFormat
  > & {
    responseFormat: JsonSchemaFormat;
    ...
  }
): ReactAgent<AgentTypeConfig<Record<string, unknown>, ...>>;
```

*— libs/langchain/src/agents/index.ts:256-290（commit 7704471）*

这不是偷懒，是类型系统边界：JSON Schema 是无标记的普通对象字面量，TS 没有任何机制从 `{ type: "object", properties: { name: { type: "string" } } }` 反推出 `{ name: string }`。对比 Zod 路径的反查能力，差异根源在**输入载体是否自带类型信息**。运行时层面这五种形态完全正常——responses.ts 的 `transformResponseFormat`（L98）会把它们归一化成统一的内部表示。`SerializableSchema` 形态是给 Zod 之外的标准 schema 库（如 Standard Schema 兼容实现）留的逃生舱，同样只能宽泛类型。选型结论：**要精确类型就用 Zod；用 JSON Schema 的场景（例如已有 OpenAPI 片段）接受类型退化，必要时手动断言**。

### 形态四：无 responseFormat——哨兵类型与双线剔除

「没有结构化输出」在类型层由哨兵类型 `ResponseFormatUndefined` 表达。重载 11 用 `Omit<CreateAgentParams<...>, "responseFormat">` 直接抹掉字段，重载 12 允许显式写 `responseFormat?: undefined`——两条路径的返回类型都带 `ResponseFormatUndefined`。这个哨兵真正的威力在 ReactAgent.ts:100-114 的 `MergedAgentState`：

```ts
type MergedAgentState<Types extends AgentTypeConfig> = InferSchemaValue<
  Types["State"]
> &
  (Types["Response"] extends ResponseFormatUndefined
    ? Omit<
        BuiltInState<MessageStructure<ToolsToMessageToolSet<Types["Tools"]>>>,
        "jumpTo"
      >
    : Omit<
        BuiltInState<MessageStructure<ToolsToMessageToolSet<Types["Tools"]>>>,
        "jumpTo"
      > & {
        structuredResponse: Types["Response"];
      }) &
  InferMiddlewareStates<Types["Middleware"]>;
```

*— libs/langchain/src/agents/ReactAgent.ts:100-114（commit 7704471）*

条件分支是精确镜像：哨兵命中时状态类型只有 messages 等基础字段；否则追加 `structuredResponse: Types["Response"]`。运行时由 annotation.ts:146-149 做同样判断——`if (hasStructuredResponse) { outputFields.structuredResponse = new UntrackedValue<any>(); }`，用 `UntrackedValue` 表示这个字段不需要 reducer 归并、由 extract 工具直接写入。类型层与运行时层用同一个语义开关保持同步，这是 1.x 类型系统的代表性手法。

### 隐藏的第五形态：wrapModelCall 触发的动态通道

还有一个容易漏掉的来源。ReactAgent 构造器在计算状态 schema 前先探测中间件能力：

```ts
const hasDynamicStructuredResponse = Boolean(
  this.options.middleware?.some((middleware) => middleware.wrapModelCall)
);
const { state, input, output } = createAgentState<
  Types["State"],
  Types["Middleware"]
>(
  this.options.responseFormat !== undefined || hasDynamicStructuredResponse,
  this.options.stateSchema as Types["State"],
  this.options.middleware as Types["Middleware"]
);
```

*— libs/langchain/src/agents/ReactAgent.ts:245-255（commit 7704471）*

只要任何一个中间件实现了 `wrapModelCall`，即使没传 responseFormat，`createAgentState` 的第一个参数也是 true，structuredResponse 通道照挂。原因：wrapModelCall 允许中间件改写模型请求并动态注入结构化响应抽取逻辑，通道必须在编译期预置。这解释了两个现象：其一，用 summarization 这类只读中间件不会触发（它不实现 wrapModelCall）；其二，调试「为什么没传 responseFormat 也有 structuredResponse」时，答案往往在中间件列表里。类型层对应重载 11 的注释「with proper middleware state typing」——无 responseFormat 的签名专门为中间件类型合并做了保留。

### 本课小结

- **四形态一句话**：Zod 对象全精确（重载 1）、Zod 数组联合推导（重载 2 + ExtractZodArrayTypes）、JsonSchema/SerializableSchema 运行时有效但类型退化为 `Record<string, unknown>`（重载 3-7）、无 responseFormat 走 ResponseFormatUndefined 哨兵（重载 11/12，13 为兜底）。
- **双线联动**：类型层 MergedAgentState 的条件分支与运行时 annotation.ts 的 `hasStructuredResponse` 开关共用同一语义，structuredResponse 有无在两层一致。
- **隐藏形态**：任一中间件实现 wrapModelCall 会隐式开启 structuredResponse 通道（hasDynamicStructuredResponse），与显式形态取或。
