### 类型工具箱的两块地基

前两课讲了 createAgent 的重载与类型级 reduce，它们都建立在地基之上：responseFormat 的每个重载都要表达「任意版本的 Zod schema」（InteropZodType），每个返回类型都要打包六个维度的类型信息（AgentTypeConfig）。本课补齐这两块地基。核心结论：**InteropZodType 用鸭子接口换 O(1) 类型比较，是一次真实性能事故的修复；AgentTypeConfig 用六槽位打包 + ~agentTypes 品牌反查，构成用户侧类型推断的完整闭环**。本课难度降为 2 级，但 zod.ts 头部那段注释值得全文精读——它是少见的把「为什么这样设计」写进源码的范例。

### 为什么不 import zod：一次性能事故的修复

```ts
// @langchain/core's public API exposes types like `InteropZodType` (a union
// of Zod v3 and v4 schema types) ... When those types were defined in terms of the
// *real* Zod type imports (`z3.ZodType`, `z4.$ZodType`), they worked fine as
// long as every package in the workspace resolved the exact same Zod version.
//
// In practice that assumption breaks. Zod 4 re-exports Zod 3 under `zod/v3`,
// but different packages can still resolve to different *copies* of Zod ...
// The real Zod types are massive: ~3,400+ lines of deeply-nested,
// mutually-recursive generics ... A structural comparison walks every branch
// of this tree for *every* callsite that touches an `InteropZodType`.
// ...
// We replace every Zod type that appears in an *exported* signature with the
// minimal structural interface defined below.
```

*— libs/langchain-core/src/utils/types/zod.ts:23-55（节选，commit 7704471）*

事故链条完整：monorepo 里各包可能解析到不同的 zod 副本；真实 Zod 类型是 3400+ 行深嵌套互递归泛型（`ZodType → ZodTypeDef → ZodEffects → ZodType → …`）；结构相似但名义不同的类型触发 TypeScript 全量结构比较，且**每个触碰 InteropZodType 的调用点都比一遍**——后果是 LSP 无响应、tsc 耗尽默认堆 OOM、报 Type instantiation is excessively deep。修复方案是：**所有导出签名里的 Zod 类型全部换成最小结构接口**，接口只捕获 core 运行时真正读取的成员，没有 zod 包 import，可赋值性判断降为 O(1)。同时 zod.ts:16-19 的注释强调：内部类型 import（`zod/v4/core`）只用于函数体里的 cast，绝不出现在导出签名里，避免泄漏进下游 .d.ts。这是「结构类型换名义类型、比较成本换兼容广度」的教科书案例。

### 两套鸭子接口与配套条件映射

```ts
export interface ZodV3Like<Output = any, Input = Output> {
  readonly _type: Output;
  readonly _output: Output;
  readonly _input: Input;
  readonly _def: ZodV3TypeDef;
  readonly description?: string;
  parse(data: unknown, params?: any): Output;
  safeParse(data: unknown, params?: any): { success: boolean; data?: Output; error?: unknown };
  parseAsync(data: unknown, params?: any): Promise<Output>;
  safeParseAsync(data: unknown, params?: any): Promise<{ success: boolean; data?: Output; error?: unknown }>;
  optional?(): ZodV3Like<Output | undefined, Input | undefined>;
  "~standard"?: any;
}

export interface ZodV4Like<Output = any, Input = Output> {
  _zod: ZodV4Internals<Output, Input>;
  "~standard"?: any;
}

export type InteropZodType<Output = any, Input = Output> =
  | ZodV3Like<Output, Input>
  | ZodV4Like<Output, Input>;
export type InteropZodObject = ZodV3ObjectLike | ZodV4ObjectLike;
```

*— libs/langchain-core/src/utils/types/zod.ts:63-81, 98-101, 169-173（commit 7704471）*

两套接口的成员清单直接暴露了两代 zod 的内部结构差异：v3 的判别属性是 `_def`（带 `typeName`），输出类型藏在 `_output`/`_type`；v4 的判别属性是 `_zod`（其 `def.type` 是小写类型名）。接口成员就是 core 运行时会读的全部——v3 列出 parse/safeParse/parseAsync/safeParseAsync 四个方法，v4 只要一个 `_zod`。互操作不止是 union：**配套的条件映射把 v3/v4 的 API 差异在类型层抹平**，如 `InteropZodObjectShape` 对 v3 读 `T["shape"]`、对 v4 读 `T["_zod"]["def"]["shape"]`（zod.ts:187-193），`InteropZodDefault/InteropZodOptional` 同理按版本分支（zod.ts:175-185）。运行时配套一族 interop 函数：`interopParseAsync` 判 v4 走 `zod/v4/core` 的 `parseAsync`、判 v3 走 `schema.parseAsync`、否则抛错（zod.ts:401-412）——类型层 union 与运行时分派一一对应。

### 运行时守卫：互斥属性的判别

```ts
export function isZodSchemaV4(schema: unknown): schema is ZodV4Like<unknown, unknown> {
  if (typeof schema !== "object" || schema === null) { return false; }
  const obj = schema as Record<string, unknown>;
  if (!("_zod" in obj)) { return false; }
  const zod = obj._zod;
  return typeof zod === "object" && zod !== null && "def" in zod;
}

export function isZodSchemaV3(schema: unknown): schema is ZodV3Like<unknown, unknown> {
  if (typeof schema !== "object" || schema === null) { return false; }
  const obj = schema as Record<string, unknown>;
  if (!("_def" in obj) || "_zod" in obj) { return false; }
  const def = obj._def;
  return typeof def === "object" && def != null && "typeName" in def;
}
```

*— libs/langchain-core/src/utils/types/zod.ts:225-263（commit 7704471）*

判别是**互斥属性**式的：v4 看 `_zod`（且其上必须有 `def`），v3 看 `_def` 但**显式排除**同时带 `_zod` 的对象——`"_zod" in obj` 为真时直接判非 v3（zod.ts:253）。这个排除很重要：zod v4 兼容层可能让对象同时暴露两代属性，先查 v4 再查 v3 的调用顺序（如 `isInteropZodSchema` 里 v4 优先，zod.ts:295）与 v3 的排除条件共同保证判定唯一。L96-L98 里反复出现的 `isInteropZodObject` 就是对这两个守卫再叠一层对象判定（`isZodObjectV3` 查 `_def.typeName === "ZodObject"`、`isZodObjectV4` 查 `_zod.def.type === "object"`，zod.ts:596-630）的组合。**鸭子接口 + 互斥守卫 + interop 函数族，三层构成完整的 v3/v4 互操作层**——没有一处 import zod 的类型。

### AgentTypeConfig：六槽位指纹与反查族

```ts
export interface AgentTypeConfig<
  TResponse extends Record<string, any> | ResponseFormatUndefined = ...,
  TState extends StateDefinitionInit | undefined = ...,
  TContext extends AnyAnnotationRoot | InteropZodObject = ...,
  TMiddleware extends readonly AnyAgentMiddleware[] = ...,
  TTools extends readonly (ClientTool | ServerTool)[] = ...,
  TStreamTransformers extends ReadonlyArray<() => StreamTransformer<any>> = ...,
> {
  Response: TResponse;
  State: TState;
  Context: TContext;
  Middleware: TMiddleware;
  Tools: TTools;
  StreamTransformers: TStreamTransformers;
}

export interface DefaultAgentTypeConfig extends AgentTypeConfig {
  Response: Record<string, any>;
  State: undefined;
  Context: AnyAnnotationRoot;
  Middleware: readonly AnyAgentMiddleware[];
  Tools: readonly (ClientTool | ServerTool)[];
  StreamTransformers: readonly [];
}

export type ResolveAgentTypeConfig<T> = T extends {
  "~agentTypes": infer Types;
} ? Types extends AgentTypeConfig ? Types : never
  : T extends AgentTypeConfig ? T : never;
export type InferAgentType<T, K extends keyof AgentTypeConfig> =
  ResolveAgentTypeConfig<T>[K];
export type InferAgentResponse<T> = InferAgentType<T, "Response">;
export type InferAgentState<T> = InferSchemaValue<InferAgentType<T, "State">> &
  InferMiddlewareStates<InferAgentType<T, "Middleware">>;
```

*— libs/langchain/src/agents/types.ts:93-142, 284-314, 366-367（裁剪，commit 7704471）*

六个槽位是 agent 的**类型指纹**：L99 看到每个 createAgent 重载的返回类型都是 `ReactAgent<AgentTypeConfig<...>>`，六维信息（响应/状态/上下文/中间件/工具/流转换器）被打包进单个类型参数——注释明说这个模式「简化类型签名，新增类型参数不必改多个函数签名」（types.ts:48-53）。`DefaultAgentTypeConfig` 给出全默认形状。反查族是闭环的另一半：ReactAgent 实例上带 `"~agentTypes"` 品牌属性（L40 讲过它的骨架），`ResolveAgentTypeConfig` 从实例抽回指纹，或直接接受指纹本身；`InferAgentType<T, K>` 按键取单维，其上是六个语义化 shorthand——`InferAgentResponse/State/Context/Middleware/Tools/StreamTransformers`。特别注意 **State 维度有 schema 与合并态两个入口**：`InferAgentStateSchema` 直通原始 stateSchema（types.ts:339），`InferAgentState` 则把 agent 自身 state 的值类型与所有中间件 state 交叉合并（types.ts:366-367），与 invoke 的完整返回状态对应；Context 同理（types.ts:408-411）。用户侧 `InferAgentState<typeof agent>` 能拿到中间件贡献的字段，靠的正是 L99/L100 两课的 const 泛型保真与类型级 reduce——模块八的类型系统在这里合龙。

### 本课小结

- InteropZodType 是鸭子接口 union 而非 zod 类型 import：真实 Zod 类型 3400+ 行递归泛型在多副本场景下会拖垮编译器，最小结构接口把可赋值性判断降为 O(1)。
- v3/v4 判别属性互斥：v3 看 `_def.typeName`（且不得有 `_zod`），v4 看 `_zod.def`；interopParseAsync 等函数按同一路径在运行时分派。
- AgentTypeConfig 六槽位（Response/State/Context/Middleware/Tools/StreamTransformers）是 agent 的类型指纹；~agentTypes 品牌支撑 ResolveAgentTypeConfig 反查，六个 InferAgent* shorthand 按键取单维。
- InferAgentState（合并中间件）与 InferAgentStateSchema（原始 schema）的区分是用户侧最常见的混淆点。
- 模块八到此收束；下一课 L102 进入模块九：从 Chain 王国到 Runnable+Graph 的迁移世界观。
