工具体系三课的收官。前两课解决了「工具怎么执行、怎么声明」，这一课解决「工具怎么接入 agent 的运行时」：为什么工具函数的第二个参数能拿到对话状态、上下文配置、持久化存储甚至流式写出器。答案是一个类型定义加一条链路——**ToolRuntime 是形状，注入是链路**。本课证据来自 `tools/types.ts` 与 `tools/index.ts`（commit 7704471），并会为模块四的 ToolNode（L46）与 wrapToolCall（L55）预埋两条线头。

### 七个字段的交叉类型

先看完整定义：

```ts
export type ToolRuntime<
  TState = unknown,
  TContext = unknown,
> = RunnableConfig & {
  /**
   * The current graph state.
   */
  state: TState extends InteropZodObject
    ? InferInteropZodOutput<TState>
    : TState extends Record<string, unknown>
      ? TState
      : unknown;
  toolCallId: string;
  toolCall?: ToolCall;
  config: ToolRunnableConfig;
  context: TContext extends InteropZodObject
    ? InferInteropZodOutput<TContext>
    : TContext extends Record<string, unknown>
      ? TContext
      : unknown;
  store: BaseStore<string, unknown> | null;
  writer: ((chunk: unknown) => void) | null;
};
```

*— langchain-core/src/tools/types.ts:541-581 裁剪（commit 7704471）*

七个字段可以按来源分三组。**第一组来自工具链自身**：`toolCallId`（必有 string）与 `toolCall?`（完整调用对象）——它们由 L21 的 config 挂载机制供给。**第二组来自 langgraph 的 Runtime**：`state`（当前图状态）、`context`（运行时上下文）、`store`（持久化存储）、`writer`（自定义流式写出器）——这四个是 agent 世界的入口。**第三组是基底**：`RunnableConfig &` 交叉让 runtime 顶层直接有 callbacks/tags/metadata/runId，同时多出的 `config: ToolRunnableConfig` 字段保留了原始调用配置的独立视图。注释里特意强调了跨语言差异：*"No Annotated wrapper is needed - just use runtime: ToolRuntime as a parameter"*——Python 线靠 Annotated 类型注解标记注入点，TS 线靠**函数签名的类型形状**，两种语言各自的类型系统承担了同一个契约角色。

### 注入链路：从 toolCall 到 runtime

类型只是形状，值从哪来？把 L21 埋的两处代码串起来看。第一处在 `StructuredTool.invoke`：

```ts
if (_isToolCall(input)) {
  toolInput = input.args as Exclude<...>;
  enrichedConfig = {
    ...enrichedConfig,
    toolCall: input,
  };
}
```

*— langchain-core/src/tools/index.ts:190-198（commit 7704471）*

第二处在 `call()` 的 toolCallId 提取：

```ts
let toolCallId: string | undefined;
// Extract toolCallId ONLY if the original arg was a ToolCall
if (_isToolCall(arg)) {
  toolCallId = arg.id;
}
// Or if it was provided in the config's toolCall property
if (!toolCallId && _configHasToolCallId(config)) {
  toolCallId = config.toolCall.id;
}
```

*— langchain-core/src/tools/index.ts:285-293（commit 7704471）*

到这里为止，config 里已经有了 `toolCall` 与推导出的 `toolCallId`——但还缺 state/context/store/writer。补齐它们的是 **agent 侧**：当工具被 createAgent 的 ToolNode 调起时，节点从图运行时里取当前 state 与 Runtime 对象（context/store/writer），与 config 里已有的工具链字段合并成完整的 ToolRuntime，作为函数第二参数传入。这个分工解释了两个字段的可空设计：**直接 invoke 工具时（无图环境），store 与 writer 自然为 null，state 也拿不到真实值**——工具必须能在「裸调用」与「agent 内调用」两种环境里工作，可空联合类型正是这种双环境兼容的类型表达。类型注释里的官方示例把七个字段一次展示全：`runtime.state.messages`、`runtime.toolCallId`、`runtime.config.runId`、`runtime.context?.userId`、`await runtime.store?.mset([[\"key\", \"value\"]])`、`runtime.writer?.(\"Processing...\")`——一份示例就是一张 API 面。

### 泛型推断与可空边界

ToolRuntime 的两个泛型参数 `TState`/`TContext` 默认都是 `unknown`，真正的类型来源是 `tool()` 的 fields：

```ts
const greet = tool(
  async ({ name }, runtime: ToolRuntime<typeof stateSchema>) => {
    const messages = runtime.state.messages;   // 有类型
    const userId = runtime.context?.userId;    // 有类型
    await runtime.store?.mset([["key", "value"]]);
    runtime.writer?.("Processing...");
    return `Hello! User ID: ${runtime.state.userId || "unknown"} ${name}`;
  },
  {
    name: "greet",
    schema: z.object({ name: z.string() }),
    stateSchema,   // z.object({ messages, userId? })
  }
);
```

*— langchain-core/src/tools/types.ts:495-528 文档示例（commit 7704471）*

`ToolRuntime<typeof stateSchema>` 把 Zod 对象的类型喂给条件类型：`TState extends InteropZodObject ? InferInteropZodOutput<TState> : ...`——走 `InferInteropZodOutput` 拿到 schema 的**输出类型**（含 transform 之后的形状）。这里有个值得咀嚼的细节：条件类型的三分支意味着 `state` 永远不会是 `any`——没传 schema 就是 `unknown`，类型系统强迫消费端要么提供 schema、要么显式收窄，杜绝了「顺手 any」的退化。另一个细节是示例里 `runtime.context?.userId` 用了可选链而 `runtime.state.messages` 没有——因为 context 的供给依赖 agent 的 contextSchema 配置，文档示例选择了保守写法；而 state 在有 stateSchema 的前提下被当作必有值对待。可空边界的实际规则：**store/writer 按 null 处理，state/context 按类型收窄处理，两层机制并行**。

### 两条线头：ToolNode 与 wrapToolCall

本课停在 core 层，但 ToolRuntime 的完整故事在模块四与模块五：`AgentNode` 产出带 id 的 tool_calls 后，`ToolNode`（L46）负责把图状态、Runtime 与 config 合并成真正的 ToolRuntime 实例再调工具；middleware 的 `wrapToolCall`（L55）则在调用点外再包一层，能看到同样的 runtime 上下文。此外有一个与 L19 呼应的观察：`withStructuredOutput` 的隐藏 extract 工具走的是 provider 协议层，**不经过** ToolRuntime 注入——结构化输出的「工具」没有函数体，自然没有运行时。理解了这一点，「工具调用」与「工具执行」的边界就清晰了：前者是模型协议，后者才轮到 runtime 登场。

### 本课小结

- ToolRuntime = RunnableConfig 交叉 { state, toolCallId, toolCall?, config, context, store, writer }：类型即契约，TS 无需 Annotated 式标记。
- 注入链路分两段：core 侧（invoke 挂 toolCall、call 抽 toolCallId）+ agent 侧（ToolNode 合并图状态与 Runtime）；直接 invoke 工具时 agent 侧字段缺位，store/writer 为 null 是设计而非缺陷。
- state/context 的条件类型三分支（Zod 对象 → InferInteropZodOutput / Record → 原样 / 其他 → unknown）强迫显式收窄，杜绝 any 退化。
- toolCallId 与 ToolMessage.tool_call_id 同源，是请求-响应关联键；runId 是回调树的另一套身份，不要混淆。
- 工具体系完结；下一课转入 Prompt 与解析组：PromptTemplate 如何用类型体操把字符串模板变成类型安全的参数表。
