### 定锚：主循环所有权易主

数据层就位后，本课改写工单助手的 Agent 层——迁移映射表里行为变化最剧烈的一行。旧栈的 AgentExecutor 是手写 while 循环，新栈的 createAgent 返回的 ReactAgent 内部是一张编译好的 LangGraph 图（`#graph: CompiledStateGraph`，ReactAgent.ts:181；invoke 委托 `#graph.invoke`，:1223-1245）。**主循环的所有权从应用代码（Executor 类）移交给运行时（图内核），这是 Agent 层迁移的本质，其余一切映射都由此派生。** 本课交付：参数面逐项映射、协议族退役方案、以及两侧同剧本的行为对齐断言。

### AgentExecutor 参数面盘点：每个开关都要找新家

  earlyStoppingMethod: StoppingMethod = "force";
  handleParsingErrors: boolean | string | ((e) => string) = false;

对照 createAgent 的参数面（agents/index.ts:76-106：llm/model、tools、prompt、responseFormat、stateSchema、middleware）逐项落位，产出本课的核心交付物——**middleware 补位表**：

| Executor 参数（executor.ts 锚点） | 1.x 承接物 | 断言关注点 |
|---|---|---|
| agent（协议类实例） | model + tools（协议层消失） | 工具名/参数等价 |
| tools | tools | 同上 |
| maxIterations=15 | 图级 recursionLimit + toolCallLimitMiddleware | 上限触发时的状态形状 |
| handleParsingErrors | toolErrorMiddleware / toolRetryMiddleware | 错误是否回喂为 ToolMessage |
| returnIntermediateSteps | 图状态流（stream）/ getState 历史 | 中间消息可从状态读出 |
| earlyStoppingMethod="force" | 无直接对应，终止由图条件边决定 | 风险清单项，不强行映射 |

映射的两个细节容易走偏。**其一**，maxIterations 的计数口径是「模型调用轮数」，recursionLimit 数的是「图超步」，一轮模型调用 + 一轮工具执行在图上至少两个超步——等价换算不是 1:15 抄数，要用剧本实测上限触发点后定值。**其二**，handleParsingErrors 在旧栈解析的是协议文本解析错误（AgentAction/AgentFinish 二元返回的解析），1.x 里这一整层消失（原生 tool_calls 免解析），toolError/toolRetry 接管的是**工具执行**错误——两者错误域不同，补位是语义近似而非精确等价，验收时用「工具抛错剧本」单独验证。

agent 字段一行的映射还藏着一个类型级变化：`agent: BaseSingleActionAgent | BaseMultiActionAgent` 的单/多动作二分（RunnableSingleActionAgent 与 RunnableMultiActionAgent 分别在 classic agents/agent.ts:214 与 :295）在 1.x 主线不存在——单动作轮吐一个动作、多动作轮吐一组动作的区分，被模型原生并行 tool_call 取代：一轮想吐几个 tool_calls 是模型能力决定的事，运行时不预设二分。这对剧本设计的直接影响已写进 pitfall：两侧同构要求「每轮至多一个 tool_call」，否则旧栈单动作协议与 1.x 并行 tool_calls 的消息序列天然不同构，参数断言会被噪声失败淹没。反过来，若业务真依赖并行工具调用（旧栈靠 MultiActionAgent 手工实现），迁移是净收益——原生 tool_calls 一次并行触发，省掉了多动作协议的往返轮次，这类「迁移后变强」的点也该记进复盘表。

「主循环易主」的源码证据再钉一次——invoke 路径的实现只有参数归一与委托：

### 协议族的解剖台：AgentAction/AgentFinish 与五个输出解析器

「协议层消失」要解剖到类型级才算讲透。旧协议的核心是一对二元返回类型：AgentAction 表示「模型要求调工具」（携带 tool/toolInput/log）、AgentFinish 表示「模型给最终答案」（携带 returnValues/log）——每次模型调用后，输出解析器把协议文本解析成二者之一，主循环据此决定继续还是收尾。这一层在 classic 里按协议各有一个实现类：mrkl 的 ZeroShotAgentOutputParser（mrkl/outputParser.ts:12）、structured_chat 的 StructuredChatOutputParser（structured_chat/outputParser.ts:19，另有 WithRetries 变体 :100）、openai_functions 的 OpenAIFunctionsAgentOutputParser（openai_functions/output_parser.ts:47）、openai_tools 的 OpenAIToolsAgentOutputParser（openai_tools/output_parser.ts:43）、xml 的 XMLAgentOutputParser（xml/output_parser.ts:26）。五个解析器解析五种文本格式，产出同一对 AgentAction/AgentFinish——**这就是「协议族」三个字的准确含义：五花八门的输出格式 + 统一的动作二元组**。

退役方案的关键在消费链路的另一半。AgentAction/AgentFinish 类型定义虽在 core（classic agents/index.ts:100-104 re-export），但全仓库只剩 classic 的解析器与主循环消费它们——core 里它已经是 0.x 兼容残留。1.x 侧这对二元组被什么取代了？答案是 AIMessage 上的原生 tool_calls 字段：模型返回的 AIMessage 要么带非空 tool_calls（等价 AgentAction）、要么不带（等价 AgentFinish），**分支判断从「解析文本产出一个类型」退化成「读一个字段是否为空」**。这就是解析器层可以整体删除的原因：不是解析器写得不好，而是模型端的原生结构化输出让「解析」这个步骤失去了存在对象。改写验收里 grep AgentAction 能验空，正是基于「core 只剩 classic 消费、应用侧无合法用途」这个事实。

还有一个迁移细节要写进退役方案：StructuredChatAgent 支持多输入工具的 JSON 块描述（其协议文本里 args 规范比 ZeroShot 的单字符串 Action Input 更结构化），依赖这层描述质量的工具，迁移后要把描述信息搬进 tool() 的 schema 字段 describe——协议里的描述责任由 schema 的 describe 字段接管，这是行为面差异（模型读到的「怎么调工具」说明书换了载体），代码层面看不到但断言 A2 的参数等价能测出来。

### AgentExecutorIterator：旧循环的第二具尸体

主循环易主还有第二个证据点。旧栈的循环拆成了两个类：AgentExecutor 本体之外，还有 AgentExecutorIterator（executor.ts:47-58）——extends Serializable、持有 agentExecutor + inputs + config，把「模型→工具→回环」的手写循环暴露成可逐轮推进的迭代器。它的存在说明旧循环是纯应用层逻辑：逻辑在应用代码里，才可能被另一个类手动驱动；1.x 的循环在图内核的 tick() 里（L75 的 BSP 超步），应用无法也不需要「手动推一格」。迁移判读：**应用若消费过 AgentExecutorIterator（逐轮拿 step 的用法），改写时消费端要换成图状态流或 getStateHistory——不是换实现，是换消费范式**；若只用过 executor.call 的一次性调用，invoke 直接对位。这两个类的命运放在一起看，「主循环所有权从应用代码移交运行时」的结论就有了一体两面的证据。

### 行为对齐断言：同一剧本，两侧验证

Agent 层的等价断言用剧本回放法。剧本设计对应工单助手的业务流：第 1 轮调 search_ticket(T-1024)，第 2 轮调 create_ticket(升级)，第 3 轮纯文本收尾。两侧驱动代码骨架：

```ts
// 1.x 侧：FakeToolCallingModel 公开导出（langchain/src/agents/index.ts:722）
import { createAgent, tool, FakeToolCallingModel } from "langchain";
import { z } from "zod/v3";

const searchTicket = tool(
  ({ ticketId }) => `Ticket ${ticketId}: status=open, priority=mid`,
  { name: "search_ticket", description: "Search a ticket",
    schema: z.object({ ticketId: z.string() }) }
);

const model = new FakeToolCallingModel({
  toolCalls: [
    [{ name: "search_ticket", args: { ticketId: "T-1024" },
       id: "call_1", type: "tool_call" }],
    [{ name: "create_ticket", args: { title: "escalate T-1024" },
       id: "call_2", type: "tool_call" }],
    [],                                  // 第 3 轮无 tool_calls → 出环
  ],
});

const agent = createAgent({ model, tools: [searchTicket, createTicket] });
const result = await agent.invoke({
  messages: [{ role: "user", content: "查 T-1024 并建升级工单" }],
});

// 断言 A1：消息序列类型
// expect(result.messages.map(m => m.type))

// 断言 A2：逐轮工具名与参数
// expect(result.messages[1].tool_calls?.[0].name).toBe("search_ticket");
// expect(result.messages[1].tool_calls?.[0].args)
//   .toEqual({ ticketId: "T-1024" });
```

### 对齐验收与遗留面

Agent 层改写完成的判定：补位表六行全部落位（earlyStoppingMethod 行标注「无对应物，风险清单跟踪」）、协议族 grep 验收为空、五个断言全绿。遗留面两条要在交付说明里写明：**其一**，若旧协议依赖 StructuredChatAgent 的多输入工具描述格式，迁移后描述责任转移到 tool() 的 schema describe 上，参数描述质量决定模型调用质量，这是行为面而非代码面的差异；**其二**，模型从协议文本解析转向原生 tool_calls 后，不同 provider 的 tool_calls 实现差异（invalid tool_calls 桶，L12 讲过 AIMessage 的 invalid 桶）进入失效面，验收剧本应包含一个「模型吐无效 tool_call」的负例剧本，断言两侧各自的降级行为。

negative 剧本的构造方法值得补一句：FakeToolCallingModel 的剧本完全由应用控制，吐一个带不存在的工具名的 tool_call（如 `name: "no_such_tool"`）即可模拟 invalid 桶场景——1.x 侧预期行为是 ToolNode 层产生错误 ToolMessage（或被 toolErrorMiddleware 接管），旧栈侧预期是协议解析产出的 action 找不到对应工具时走 handleToolRuntimeErrors 路径。两侧各自的「降级行为成立」就是这条断言的通过标准，差异本身归档风险清单。至此 Agent 层迁移收口，下一课做 Capstone A 的总验收与复盘。

### 本课小结

- **主循环易主**：Executor 手写 while → ReactAgent 内部 #graph；createAgent 实现体只有 `return new ReactAgent(params)` 一行。
- **协议族解剖**：五套协议 = 五种输出格式 + 统一的 AgentAction/AgentFinish 二元组；1.x 用 AIMessage.tool_calls 是否为空取代类型分支，解析器层失去存在对象。
- **补位表六行**：agent/tools 直接落参数面，maxIterations→recursionLimit+toolCallLimit（计数口径不同，实测定值），handleParsingErrors→toolError/toolRetry（错误域从协议解析变为工具执行），returnIntermediateSteps→图状态流，earlyStoppingMethod 无对应物进风险清单；单/多动作二分由原生并行 tool_call 取代。
- **旧循环两具尸体**：AgentExecutor 主循环与 AgentExecutorIterator 逐轮推进——后者消费过的应用要换图状态流消费范式，不是换实现。
- **协议族退役**：agentType 字符串变模型标识，输出解析器层消失，`AgentAction/AgentFinish` 只剩 classic 消费。
- **剧本回放对齐**：FakeToolCallingModel 剧本 + 五条断言（序列类型/逐轮参数/上限行为/工具抛错/中间步骤）+ invalid tool_call 负例剧本，结构先于参数，漂移点断「各自既定行为」而非硬凑等价。
