### 定位：六 hook 里唯一能「改写模型请求」的入口

模块五前半（L51–L53）把 AgentMiddleware 接口和六个 hook 的类型铺完了；从本课开始逐个 hook 落地。wrapModelCall 是六个 hook 里**唯一直接包住「模型调用本身」的**：beforeModel/afterModel 只能改 state，而 wrapModelCall 拿到的是即将发给模型的完整请求对象，还能决定要不要放行、改完再放行、甚至换一个模型再放行。内置 20 个中间件里有 7 个靠它实现（modelRetry、modelFallback、contextEditing、dynamicSystemPrompt、piiRedaction、modelRouter 的换模型段、toolEmulator 的模型捕获段），掌握它等于掌握半个内置生态的读法。

一句话结论：**wrapModelCall = 洋葱中间件 + 不可变请求改写**——你收到 request，构造一个新 request 传给 handler，返回 AIMessage 或 Command。

### ModelRequest 解剖：你能改什么

先看 handler 拿到的请求对象长什么样。

```ts
export interface ModelRequest<
  TState extends Record<string, unknown> = Record<string, unknown>,
  TContext = unknown,
> {
  model: LanguageModelLike;
  messages: BaseMessage[];
  /** @deprecated Use {@link ModelRequest.systemMessage} instead. */
  systemPrompt: string;
  systemMessage: SystemMessage;
  toolChoice?: "auto" | "none" | "required"
    | { type: "function"; function: { name: string } };
  tools: (ServerTool | ClientTool)[];
  state: TState & AgentBuiltInState;
  responseFormat?: TResponseFormat;
  runtime: Runtime<TContext>;
  modelSettings?: Record<string, unknown>;
}
```

*— libs/langchain/src/agents/nodes/types.ts:15-118（commit 7704471，有裁剪）*

逐字段过一遍可改写的面：`model` 换模型（modelFallback 就干这个）；`messages` 增删改消息（summarization 的近亲 piiRedaction 在这里脱敏）；`systemMessage` 改系统提示（dynamicSystemPrompt、todoListMiddleware 的注入点）；`tools` 增删工具（llmToolSelector 的过滤点）；`toolChoice` 强制/禁止工具调用；`responseFormat` 动态开关结构化输出；`modelSettings` 携带 provider 专属绑定参数——注意源码注释说「The model is re-bound on each request, so these settings can vary per invocation」，也就是每次请求都会重新 bindTools，modelRetry 正是靠塞 `maxRetries: 0` 关掉模型内建重试（modelRetry.ts:192-195）。

`systemPrompt` 单独说：它在 ModelRequest 里保留但是遗留通道，handler 入参类型特意把它和 systemMessage 一起 Omit 后再以可选形式放回（middleware/types.ts:219-225），注释写明「allow to reset the system prompt or system message」。新代码一律走 `systemMessage`，它是个 SystemMessage 实例，支持 `concat` 字符串或带 cache_control 的内容块。

### 组合顺序：第一个中间件在最外层

多个 wrapModelCall 如何叠？源码注释给了一行答案。

```ts
/**
 * Wrap the base handler with middleware wrapModelCall hooks
 * Middleware are composed so the first middleware is the outermost wrapper
 * Example: [auth, retry, cache] means auth wraps retry wraps cache wraps baseHandler
 */
// ...
/**
 * Build composed handler from last to first so first middleware becomes outermost
 */
for (let i = wrapperMiddleware.length - 1; i >= 0; i--) {
  // ...wrappedHandler = middleware.wrapModelCall 包住 innerHandler
}
```

*— libs/langchain/src/agents/nodes/AgentNode.ts（commit 7704471，有裁剪）*

实现从数组末尾向前折叠，所以 `[auth, retry, cache]` 的调用链是 auth → retry → cache → baseHandler。这个顺序有实际后果：**鉴权/日志类中间件放数组前面，它们能看到重试与缓存之后（其实是之前）的完整行为**；而像 toolEmulator 这种「想偷看最终模型」的，靠 wrapModelCall 捕获 `request.model` 再在 wrapToolCall 里用。另外同一层里 AgentNode 还会校验工具改动：新增客户端工具而没有中间件提供 wrapToolCall 时直接抛错，防止「模型能选、图里没法执行」的悬空工具。

### 新增与替换：工具改动的两道校验门

每个包装层里的 handler 其实是 handlerWithValidation——在内层 handler 之前先做工具改动分类（AgentNode.ts:575-630）。分类规则把 modifiedTools 与静态注册表逐名对照：**added** 是注册表里没有的全新名字；**replaced** 是同名但实例不同（`original != null && original !== tool`）。两类的待遇截然不同：added 只有在某个中间件实现了 wrapToolCall 时才放行，否则抛 "You have added a new tool in \"wrapModelCall\" hook of middleware \"X\": ... This is not supported unless a middleware provides a \"wrapToolCall\" handler to execute it."；而 **replaced 一律拒绝**，错误消息直接写明 "This is not supported."——没有豁免条件。为什么替换不给活路？注释里写得很清楚：「Replaced tools are always rejected to preserve ToolNode execution identity」——ToolNode 按注册实例执行（L46 的 override 链以注册表为底），如果 wrapModelCall 里换了个同名不同实现的工具，模型看到的描述/参数 schema 与实际执行体就会错位，这是执行身份一致性问题，比「没有执行者」更隐蔽也更危险。**改工具行为的正道是 wrapToolCall 的 request.tool 覆盖（L55）**，它发生在执行现场，身份不会错位。

### systemPrompt 与 systemMessage 的同步机制

handlerWithValidation 里还有一段少有人读的双通道校准（AgentNode.ts:630-659）：每层包装开始前记录 baselineSystemMessage，handler 收到请求时检测 `req.systemPrompt !== currentSystemMessage.text` 与 `req.systemMessage !== currentSystemMessage` 两个变更信号。规则有三条。**一：同一请求里两个都改直接抛错**——"Cannot change both systemPrompt and systemMessage in the same request."，这堵住了双通道互相矛盾的可能。**二：改了 systemPrompt（遗留 string 通道）会被物化成新 SystemMessage**，normalizedReq 里两个字段同步重算。**三：改了 systemMessage 也会回写 systemPrompt**。所以虽然 systemPrompt 已废弃，框架并没有让它「半死不活」——两条通道被强制保持镜像，改哪个最终都以 SystemMessage 为准。这解释了 L56 里 modelRetry 等内置件只敢用 systemMessage.concat 的原因：走官方正道，永远不触碰镜像同步的边界。

### 响应校验与 Command 透传

洋葱层的出口同样有守卫：每个中间件返回后，AgentNode 检查 `isInternalModelResponse(middlewareResponse)`，不合法就抛 `Invalid response from "wrapModelCall" in middleware "X": expected AIMessage or Command, got ${typeof ...}`（AgentNode.ts:712-719）——L53 的报错归口表里「洋葱端」那一行就来自这里。另一个精妙设计是 **Command 对中间件不可见**：内层 handler 返回 Command（如结构化输出重试路径）时，包装层把它收进 collectedCommands 收藏夹，而给中间件的返回值替换成跟踪中的 lastAiMessage——注释原话「Normalize Commands so middleware always sees AIMessage from handler()」。也就是说中间件永远以为自己在处理普通 AIMessage，Command 的控制流语义由框架在外层收集并继续传播。给中间件写返回值断言时注意这一点：你 return 的 Command 不会出现在下一层中间件的视野里，但它确实生效。还有一条 downstreamErrors 机制（660-670）：内层抛出的错误被记录在案，外层 catch 时原样 re-throw 而不再包一层——错误归因不会被洋葱扭曲。

### 实战一：改写系统提示 + 动态换模型

下面把两个最小可用的 wrapModelCall 中间件接进同一个 agent 跑通。

```ts
import { createAgent, createMiddleware } from "langchain";

// 1) 追加系统提示：模仿 todoListMiddleware 的注入方式
const tone = createMiddleware({
  name: "ToneMiddleware",
  wrapModelCall: (request, handler) =>
    handler({
      ...request,
      systemMessage: request.systemMessage.concat(
        "\nAlways answer in Simplified Chinese."
      ),
    }),
});

// 2) 按 context 动态换模型 + 关结构化输出：模仿 modelFallback 的换模型姿势
const routing = createMiddleware({
  name: "RoutingMiddleware",
  wrapModelCall: async (request, handler) => {
    const cheap = request.runtime.context?.cheapMode === true;
    const model = cheap
      ? await request.runtime.context.loadCheapModel()
      : request.model;
    return handler({ ...request, model, responseFormat: undefined });
  },
});

const agent = createAgent({
  model: "openai:gpt-4o",
  middleware: [routing, tone], // routing 在外层，先决定模型
  tools: [],
});

const res = await agent.invoke(
  { messages: [{ role: "user", content: "总结这段代码" }] },
  { context: { cheapMode: true } }
);
```

两个中间件演示了改写的两类典型：**追加式改写**（systemMessage.concat，tone）与**替换式改写**（展开新对象覆盖 model/responseFormat，routing）。数组顺序决定 routing 先执行——它在外层，能拦截 tone 之后的整个调用。

这段代码还暗含一个 L53 生命周期理论的演示点：routing 里读的 `request.runtime.context?.cheapMode` 之所以有类型提示，是因为 createMiddleware 的 const 泛型把 contextSchema 推断进 hook 签名（NormalizeContextSchema 接住 parse 后的输出类型）；而这里的 cheapMode 实际由**每个包装层各自 interopParse**（AgentNode.ts:509-515），runtime 对象经 `Object.freeze` 冻结后再交给 hook（524-531）。同时注意 `responseFormat: undefined` 这个改写维度：routing 关掉结构化输出的意图是「降级到便宜模型时不做结构化提取」——responseFormat 在 ModelRequest 上是可选的，展开覆盖 undefined 是合法写法，效果等价于这轮请求没有结构化输出诉求（extract- 提取工具不会被装配）。三个可改写维度（model/responseFormat/systemMessage）在一次改写里同时用上，wrapModelCall 的表达力可见一斑。

### 实战二：带重试与日志的洋葱观察

```ts
const logger = createMiddleware({
  name: "LoggerMiddleware",
  wrapModelCall: async (request, handler) => {
    const t0 = Date.now();
    console.log("[model] tools =", request.tools.map((t) => t.name));
    const response = await handler(request); // 内层：retry -> baseHandler
    console.log(`[model] done in ${Date.now() - t0}ms`);
    return response;
  },
});

const retryOnce = createMiddleware({
  name: "RetryOnceMiddleware",
  wrapModelCall: async (request, handler) => {
    try {
      return await handler(request);
    } catch (e) {
      return handler({ ...request, toolChoice: "none" }); // 降级重试
    }
  },
});

// [logger, retryOnce]：logger 在最外层，能观测到重试前后的完整耗时
const agent2 = createAgent({ model, middleware: [logger, retryOnce] });
```

这个例子验证洋葱语义：logger 的计时覆盖了 retryOnce 的失败重试，因为它是外层。如果把顺序反过来，logger 计到的就只有「成功那一次」的时间。

顺带把 retryOnce 的降级重试拆开看：catch 之后 `handler({ ...request, toolChoice: "none" })` 重放的是**同一份消息与工具清单，但禁止工具调用**——模型被迫给出纯文本回答，这是「模型卡在工具循环里」时的标准逃生姿势。toolChoice 是 ModelRequest 上的可选字段（nodes/types.ts:70-73），取值 "auto"/"none"/"required" 或指定函数名，语义由 provider 层翻译成对应 API 参数。还要留意重试的手工版与 L56 的 modelRetry 的差别：手工版这里重试次数、退避、可重试判定全要自己写，而 modelRetry 把这些固化成了带默认值的 RetrySchema——实战里降级重试应当优先用内置件，手工 handler({ ...request }) 改写只在需要**改变请求内容**（而不只是重放）时才亲自出手。这两个例子的四行观察，就是「洋葱顺序决定观测面」与「改写维度决定行为」两句话的全部实证。

### 本课小结

- wrapModelCall 的契约是 `(request, handler) => AIMessage | Command`；request 共 10 个可改写字段，systemPrompt 已废弃，改系统提示用 `systemMessage.concat`。
- 多个 wrapModelCall 洋葱组合，**数组第一个在最外层**（AgentNode 从尾向头折叠），顺序直接影响日志/重试的观测面。
- 改写一律「展开新对象传 handler」，return handler 的结果；新增客户端工具必须有配套 wrapToolCall，否则 AgentNode 抛错。
- modelSettings 每次请求重新 bindTools，是做 per-request 头部注入与关闭模型内建重试的通道。
- 下一课看它的镜像兄弟 wrapToolCall：同样是洋葱，但包的是工具执行，与 ToolNode 的错误处理深度联动。
