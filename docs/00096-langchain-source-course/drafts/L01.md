### 三个包，一张地图

本课是 132 课的第一课，任务很小但地位特殊：**在你读任何一行实现代码之前，先搞清楚「代码在哪个仓库、哪个包、哪个版本」**。1.x 的 TS 线把过去一整个 npm 包拆成了三个包加一个外部内核，网上旧教程与 AI 生成的示例几乎都在这个坐标上翻车——所以本课的全部内容都是取证题：答案不在文档里，在 package.json 里。

一句话核心结论：**1.x 的 TS 线 = 主包 langchain（agent harness）+ 底座 @langchain/core（原语）+ 博物馆 @langchain/classic（旧 API 隔离区），外加一个外部依赖 @langchain/langgraph（编排内核）**。三个包在同一个仓库 langchain-ai/langchainjs 的 libs/ 目录下，本课程所有源码摘录都锚定 commit 7704471。

### 逐文件走读：三个 package.json 的头部

先看主包的「身份证」：

```json
{
  "name": "langchain",
  "version": "1.6.6",
  "description": "Typescript bindings for langchain",
  "type": "module",
  "engines": { "node": ">=20" }
}
```

*— libs/langchain/package.json:1-9（commit 7704471）*

再看底座与博物馆的对应字段：

```json
// @langchain/core
{
  "name": "@langchain/core",
  "version": "1.4.1",
  "description": "Core LangChain.js abstractions and schemas"
}

// @langchain/classic
{
  "name": "@langchain/classic",
  "version": "1.0.61",
  "description": "Old abstractions from LangChain.js"
}
```

*— libs/langchain-core/package.json:1-5、libs/langchain-classic/package.json:1-5（commit 7704471）*

三个 description 就是三份官方定位声明：主包自称「Typescript bindings」，core 自称「abstractions and schemas」，classic 自称「Old abstractions」。**「old」这个词出现在官方描述里，说明隔离是刻意设计而不是临时措施**。同时注意一个容易踩的细节：仓库目录叫 `langchain-classic`，但 npm 包名是 `@langchain/classic`——写依赖时以 name 字段为准。

### 主包 src 顶层：产品重心已经写在目录名里

```text
libs/langchain/src/
├── agents/        # createAgent、ReactAgent、nodes/、middleware/（20 个中间件）
├── chat_models/   # initChatModel 万能模型入口
├── prompts/       # 少量 prompt 支持
├── storage/       # 存储子路径
├── tools/         # headless tool 扩展
├── hub/  load/    # Hub 拉取与序列化加载
├── index.ts       # 导出面（L03 逐行走读）
└── browser.ts     # 浏览器条件导出的镜像面
```

*— libs/langchain/src/ 目录实测（commit 7704471）*

对比 0.x 时代主包动辄几十个顶层目录（chains、memory、output_parsers、embeddings……都在 src 顶层），1.x 主包只剩 **8 个目录**，其中 `agents/` 是绝对重心：20 个内置中间件、6 类节点、ReactAgent 类全部住在这里。旧教程里的 `LLMChain`、`BufferMemory`、`AgentExecutor` 不在这个包里，也不在任何 1.x 主线包里——它们被整体搬进了 classic。

### classic 的 src 顶层：一座三层博物馆

```text
libs/langchain-classic/src/
├── chains/  memory/  agents/  output_parsers/  indexes/
├── evaluation/  experimental/  sql_db.ts  smith/  schema/
├── document_loaders/  document_transformers/  embeddings/
├── retrievers/  vectorstores/  stores/  cache/  callbacks/
├── chat_models/  prompts/  tools/  text_splitter.ts  hub/  load/
└── index.ts   # 内容只有一句 console.warn
```

*— libs/langchain-classic/src/ 目录实测（commit 7704471）*

目录几乎原封不动保留了 0.x 的形状，连 `experimental/`（BabyAGI、AutoGPT、GenerativeAgents 这些实验品）都一起打包进了博物馆。最耐人寻味的是它的根入口 `src/index.ts`——整个文件只有三行：

```ts
console.warn(
  `[WARNING]: The root "langchain" entrypoint is empty. Please use a specific entrypoint instead.`
);
```

*— libs/langchain-classic/src/index.ts:1-3（commit 7704471）*

**classic 不提供根入口**：你 `import ... from "@langchain/classic"` 得到的是一条警告，一切旧 API 都必须走子路径导入（如 `@langchain/classic/memory`）。这是用包结构强制你面对「你在用旧 API」这个事实。

### core 的 src 顶层：原语仓库与外部内核

```text
libs/langchain-core/src/
├── runnables/  messages/  tools/  retrievers/
├── language_models/  prompts/  output_parsers/
├── callbacks/  tracers/  caches/  documents/
├── document_loaders/  vectorstores.ts  embeddings.ts
├── load/  indexing/  memory.ts  structured_query/
└── utils/  types/  stores.ts  agents.ts  decisions/
```

*— libs/langchain-core/src/ 目录实测（commit 7704471）*

core 里有 Runnable、消息、工具、回调、追踪——但**没有图**。编排内核（Pregel、Channel、checkpoint）住在另一个仓库 langgraph-ai/langgraphjs 的 `libs/langgraph-core` 里，经 `@langchain/langgraph` 被主包依赖。那边的 src 顶层同样值得先看一眼地形：`pregel/`（algo/loop/runner/stream/checkpoint/io 等，BSP 超步内核的全部实现）、`channels/`（LastValue、BinaryOperatorAggregate、Topic、Delta、AnyValue、EphemeralValue、UntrackedValue、NamedBarrier、DynamicBarrier 等 11 种通道实现）、`graph/`（StateGraph 与 schema 归一化）、`prebuilt/`（预构建 agent 模板）。这四个目录就是模块六的完整地图，出处见 langgraphjs 仓（commit 锚 fa426b2）的目录实测。所以正确的分层心智图是：

| 层 | 包 | 一句话职责 |
|---|---|---|
| 应用层 | langchain@1.6.6 | agent harness：createAgent + middleware |
| 原语层 | @langchain/core@1.4.1 | 消息/工具/Runnable/回调/追踪 |
| 博物馆 | @langchain/classic@1.0.61 | 0.x 旧 API 的隔离区，只读不演进 |
| 编排内核 | @langchain/langgraph | Pregel 图运行时（独立仓库） |

### 再下一层：agents/ 里住着什么

主包 8 个目录里 `agents/` 是重心，值得再下探一层，因为后续模块四、五的全部内容都长在这棵目录树上：

```text
libs/langchain/src/agents/
├── index.ts          # createAgent 的 13+ 个类型重载 + 唯一实现体
├── ReactAgent.ts     # class ReactAgent：内核类，invoke()/stream() 委托 #graph
├── nodes/            # AgentNode / ToolNode / BeforeModelNode / AfterModelNode
│                     # / BeforeAgentNode / AfterAgentNode + middleware.ts
├── middleware.ts + middleware/   # createMiddleware 工厂 + 20 个内置中间件文件
├── state.ts  runtime.ts  responses.ts  types.ts  model.ts
└── annotation.ts  constants.ts  errors.ts  utils.ts  withAgentName.ts
```

*— libs/langchain/src/agents/ 目录实测（commit 7704471）*

三个读法。**其一**，`index.ts` 是重载陈列室：createAgent 在这里堆了 13+ 个类型重载而实现体只有一行（`return new ReactAgent(params)`），重载数量本身就是 responseFormat 形态多样性的量化证据（L37 展开）。**其二**，`ReactAgent.ts` 是唯一的内核类，其 `invoke()` 声明在 L1223 附近、`stream()` 在 L1312 附近，二者都只是委托给内部的 `#graph`——「Agent 即编译图」这句话在文件层面就能验证，不需要等运行时。**其三**，`middleware/` 下的文件名就是 1.x 能力清单的目录索引：summarization、contextEditing、dynamicSystemPrompt、modelRetry、modelFallback、modelCallLimit、toolRetry、toolError、toolEmulator、toolCallLimit、pii、piiRedaction、hitl、modelRouter、llmToolSelector、providerToolSearch、todoListMiddleware、autoMode……0.x 时代散落在各处的「executor 开关」，在 1.x 全部收敛成这个目录里的中间件文件（模块五逐个走读）。

### 三组易混淆的名字，一张辨析表

第一课最容易记错的就是名字，把三组混淆钉死能省掉后面大量回头查证：

| 你想要的东西 | 仓库目录 | npm 包名 | 常见错误 |
|---|---|---|---|
| agent harness 主包 | `libs/langchain` | `langchain` | 误写成 @langchain/langchain（不存在） |
| 原语底座 | `libs/langchain-core` | `@langchain/core` | 误写成 langchain-core（无此包） |
| 旧 API 博物馆 | `libs/langchain-classic` | `@langchain/classic` | 误写成 langchain-classic（无此包） |
| 编排内核 | langgraphjs 仓 `libs/langgraph` | `@langchain/langgraph` | 误以为它在 langchainjs 仓里 |

这张表的依据全部来自三个 package.json 的 name 字段实测（libs/langchain/package.json:2、libs/langchain-core/package.json:2、libs/langchain-classic/package.json:2，commit 7704471）。规律是：**npm 包名是否带 @langchain 作用域与目录名无关**——主包没有作用域（历史最久、名字最先注册），core 与 classic 带作用域。另一个高频混淆是与 Python 线互相污染：Python 主线的版本号（如 1.5.0/1.8.0）与 TS 线完全独立，两边各自发版，搜资料时先确认语言再确认版本，否则读到的 API 形态可能差一个世代。

还有一条实用判据送给后面的课：**判断一个 API 属于哪个包，用「它需不需要图」来分**。消息、工具、Runnable、回调这些纯数据与协议概念全在 core；一旦涉及状态图、checkpoint、interrupt（如 headless tool 的挂起），实现要么在 langgraph 内核要么在主包对它的封装里。这条判据在 L09 拆 headless tool 的 `await import("@langchain/langgraph")` 时会再次出现。

### 本课小结

- 三个包一个仓库：`libs/langchain`、`libs/langchain-core`、`libs/langchain-classic` 是 langchainjs monorepo 的三个成员；npm 包名分别是 langchain、@langchain/core、**@langchain/classic**（目录名 ≠ 包名）。
- 版本基线（源码 package.json 实测）：langchain 1.6.6 / core 1.4.1 / classic 1.0.61。
- 主包 1.x 的产品重心是 agent harness，src 顶层只剩 8 个目录；旧 Chain/Memory/AgentExecutor 全部隔离进 classic，且 classic 根入口只有一句警告。
- 编排内核 @langchain/langgraph 来自独立仓库，主包 dependencies 直接声明依赖它——「LangChain 与 LangGraph 二选一」的旧认知失效。
- 下一课我们顺着 dependencies 与 peerDependencies 字段继续取证：**依赖方向**——谁依赖谁、core 为什么敢自称零内部依赖底座。
