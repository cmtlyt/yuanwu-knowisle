### 一、最轻的一课：为什么存在「纯搬家」API

前面几课都在做「结构迁移」——协议消失、形态升级、开关重组。但 classic 里有相当一部分 API 的迁移动作轻到只有一行：**改 import**。本课把这部分一次性打包处理，同时讲清另一类特殊存在——报错占位文件的「报错史」。先建立三类档案（本课的核心清单）：

| 类型 | 证据 | 迁移动作 |
|---|---|---|
| 报错占位 | classic prompts/index.ts:1-7、src/index.ts:1-3（根入口） | 直接改 import 到新家，占位文件不要留引用 |
| re-export 空壳 | text_splitter.ts:1、storage/in_memory.ts:1、load/serializable.ts:1 | 改 import 到真正来源（独立包或 core） |
| 同名下沉 | core output_parsers 的 String/Json/Structured 等族 | 改 import，零逻辑变化 |

### 二、报错史现场：一个入口的死亡记录

报错占位是 0.x 大拆分留下的活化石。classic prompts 入口的完整原文：

```ts
/* #__PURE__ */ console.warn(
  [
    `[ERROR]: The "langchain/prompts" entrypoint was removed in LangChain version 0.2.0.`,
    ``,
    `Instead, please import from "@langchain/core/prompts".`,
  ].join("\n")
);
```

*— langchain-classic/src/prompts/index.ts:1-7（commit 7704471）*

逐行解读：`/* #__PURE__ */` 注解告诉打包器这个调用无副作用、可在 tree-shaking 时删除——作者默认你**不该**导入这个文件；文案里写死的版本号 0.2.0 说明 Prompt 族搬去 core 是 0.2 时代的事，1.0 只是把这个占位从 langchain 包搬进 classic 包继续服役；提示语直接给出新家路径，等于官方把迁移答案写在了报错里。同样结构还有 classic 根入口 src/index.ts:1-3（WARNING 文案：「The root 'langchain' entrypoint is empty」）。

实操对照实验：新旧两行 import 的运行结果。

```ts
// 旧：打印 ERROR 提示后什么也拿不到
import { PromptTemplate } from "langchain/prompts";
// → [ERROR]: The "langchain/prompts" entrypoint was removed in LangChain version 0.2.0.
//   Instead, please import from "@langchain/core/prompts".

// 新：core 里的正式实现
import { PromptTemplate } from "@langchain/core/prompts"; // core prompts/prompt.ts:113
import { ChatPromptTemplate } from "@langchain/core/prompts"; // core prompts/chat.ts:924
```

Prompt 族的新家在 core 一应俱全：PromptTemplate（prompt.ts:113）、ChatPromptTemplate（chat.ts:924）、MessagesPlaceholder（chat.ts:101）、FewShotPromptTemplate（few_shot.ts:106）、PipelinePromptTemplate（pipeline.ts:73）、StructuredPrompt（structured.ts:46），还有 core 独有的新类 DictPromptTemplate（dict.ts:10）。**搬家课不丢东西，还添了新货**。

### 三、同名下沉族盘点：OutputParser 的幸存名单

OutputParser 一侧的迁移分两半。幸存的一半是通用解析器族，全部在 core 原样同名：StringOutputParser（string.ts:22）、JsonOutputParser（json.ts:12）、四个列表解析器（list.ts:64/104/159/179：CommaSeparated/Custom/Numbered/MarkdownList）、StructuredOutputParser 与 JsonMarkdownStructuredOutputParser（structured.ts:34/158，L116 已实操）、XMLOutputParser（xml.ts:38）、BytesOutputParser（bytes.ts:7）、StandardSchemaOutputParser（standard_schema.ts:9）。牺牲的另一半是 agent 专用解析器（classic agents/ 下的五套，L113 讲过）——它们不在 core，也没有新家。

现在把本课第一个目标落地：写一个归档脚本，扫出项目里所有待搬 import 并分类。

```ts
// scripts/audit-imports.mjs —— 搬家对照清单生成器
import { readFileSync, readdirSync, statSync } from "node:fs";
import { join } from "node:path";

// 三类档案：报错占位入口 / 空壳转发来源 / 同名下沉的新家
const REPLACEMENTS = [
  { from: /^langchain\/prompts$/,     to: "@langchain/core/prompts", kind: "报错占位" },
  { from: /^langchain\/text_splitter$/, to: "@langchain/textsplitters", kind: "空壳转发" },
  { from: /^langchain\/storage\/in_memory$/, to: "@langchain/core/stores", kind: "空壳转发" },
  { from: /^langchain\/output_parsers$/, to: "@langchain/core/output_parsers", kind: "同名下沉" },
  { from: /^langchain\/agents\/(mrkl|structured_chat|xml|openai_functions)/, to: "NO_MATCH", kind: "agent 解析器（无新家，见 L113）" },
];

function* walk(dir) {
  for (const name of readdirSync(dir)) {
    const p = join(dir, name);
    const s = statSync(p);
    if (s.isDirectory()) yield* walk(p);
    else if (/\.(ts|tsx|js|mjs)$/.test(name)) yield p;
  }
}

const report = {};
for (const file of walk(process.argv[2] ?? "src")) {
  const src = readFileSync(file, "utf8");
  for (const line of src.split("\n")) {
    const m = line.match(/from\s+["']([^"']+)["']/);
    if (!m) continue;
    for (const r of REPLACEMENTS) {
      if (r.from.test(m[1])) {
        (report[r.kind] ??= []).push({ file, spec: m[1], to: r.to });
      }
    }
  }
}
console.table(Object.entries(report).flatMap(([kind, rows]) => rows.map(r => ({ kind, ...r }))));
```

跑 `node scripts/audit-imports.mjs src` 得到一张按类型分组的迁移清单。注意脚本的故意设计：agent 解析器一族映射成 NO_MATCH——脚本的价值不只是生成替换规则，更是**把「不能改 import」的边界也显式化**，防止有人机械套用公式。

### 四、零逻辑迁移实操与等价断言

按清单改造一条 Prompt + OutputParser 链，验证「只改 import、行为不变」：

```ts
// ── 迁移前（0.x 形状）────────────────────────────
import { ChatPromptTemplate } from "langchain/prompts";            // 报错占位
import { StringOutputParser } from "langchain/output_parsers";     // 旧路径
import { ChatOpenAI } from "@langchain/openai";

const prompt = ChatPromptTemplate.fromMessages([
  ["system", "把用户输入改写成一句广告语。"],
  ["human", "{text}"],
]);
const chain = prompt.pipe(new ChatOpenAI({ model: "gpt-4o" })).pipe(new StringOutputParser());
const before = await chain.invoke({ text: "一副轻得像没戴的眼镜" });
```

```ts
// ── 迁移后（1.x 形状）────────────────────────────
import { ChatPromptTemplate } from "@langchain/core/prompts";      // core prompts/chat.ts:924
import { StringOutputParser } from "@langchain/core/output_parsers"; // core output_parsers/string.ts:22
import { ChatOpenAI } from "@langchain/openai";

const prompt = ChatPromptTemplate.fromMessages([
  ["system", "把用户输入改写成一句广告语。"],
  ["human", "{text}"],
]);
const chain = prompt.pipe(new ChatOpenAI({ model: "gpt-4o" })).pipe(new StringOutputParser());
const after = await chain.invoke({ text: "一副轻得像没戴的眼镜" });

// 等价断言：类型同为 string、非空；结构完全一致，仅 import 来源变化
import { expect, it } from "vitest";
it("迁移前后行为等价", async () => {
  expect(typeof after).toBe("string");
  expect(after.length).toBeGreaterThan(0);
});
```

改造过程没有任何逻辑行变化——这正是搬家族的定义。配合第三节的清单脚本，这类 API 的迁移可以完全 codemod 化：脚本归档 → 人工确认 NO_MATCH 例外 → 批量替换 → 断言回归。做完这一步，你的项目里就只剩下「结构性迁移」的存量了，即 L107-L115 已经讲过或后面走查课要处理的那些。

### 五、解析器双层的协议细节：parse 与 parseResult

搬家课不只是背名单——把通用解析器的内部协议看一眼，能解释「为什么 agent 专用解析器不能跟着搬」。core 的 BaseOutputParser（output_parsers/base.ts:105）是双层设计：外层 `parse` 负责输入归一化，内层 `parseResult` 才是真正的解析逻辑：

```ts
export abstract class BaseOutputParser<RunOutput, ParseOutput> {
  // :31  抽象内层：从 ChatGeneration[] 解析
  abstract parseResult(generations, callbacks?): Promise<RunOutput>;
  // :38-49  parseResultWithPrompt 只是外层转发
  // :65-86  外层 parse 的输入归一化：
  //         纯文本 → 包成 [{ text: input }] 再调 parseResult
  //         BaseMessage → 按 message 形态调 parseResult
}
```

*— langchain-core/src/output_parsers/base.ts:31-86（commit 7704471，节选注释）*

这个双层结构正是 L113 见过的旧 agent 解析器分化的根源：普通解析器只实现 parseResult 就够（输入总是文本），而 ToolCallingAgentOutputParser 之所以把 `parse(text)` 写成直接抛错，是因为它只认 BaseMessage 形态的输入——双层协议允许「只支持消息输入」的解析器显式拒绝文本。通用解析器（String/Json/Structured 族）在 core 的实现与 classic 完全同构，迁移才可能「零逻辑变化」。另外记住报错通道的位置：OutputParserException 定义在 base.ts:170（台账证据 29），它在 core 的幸存名单里，是解析器轨道的统一异常类型——迁移后链上抛出的解析错误类型不变，错误处理代码不用动。

双层结构外还要看一层：解析器的 Runnable 家谱。BaseLLMOutputParser（base.ts:15）`extends Runnable<string | BaseMessage, T>`——parse 的两种输入形态（纯文本、BaseMessage）就写在这个泛型签名里，也是 L116 提到「parser 能直接 pipe 进链」的类型学依据。往下还有两个流式专类：BaseTransformOutputParser（output_parsers/transform.ts:20）逐 chunk 转换输出，BaseCumulativeTransformOutputParser（transform.ts:69）在 :119 用 `accGen.concat(chunkGen)` 把 chunk 累积合并后再解析——StringOutputParser 走前者、StructuredOutputParser 走后者的分派由此而来。迁移时若你的旧链在流式场景下用了这些解析器，改 import 后流式行为不变：流式分派逻辑在 core 与 classic 是同一份下沉实现。这份家谱也再次解释了搬家课的边界：**解析器的「能力面」（文本/消息双输入、流式/非流式）全部随实现下沉 core，随协议退役的只有「给旧 agent 当输出解析器」这一个用途**——同一个类在两个历史舞台上的角色要分开评价。

### 六、幸存名单补遗与三个误用边界

补两个容易漏的幸存项。其一，StandardSchemaOutputParser（core output_parsers/standard_schema.ts:9）是 core 的新增项，对接 Standard Schema 协议（Zod/Valibot 等统一接口）——搬家课的「添新货」不止 DictPromptTemplate 一处。其二，BytesOutputParser（bytes.ts:7）与 XMLOutputParser（xml.ts:38）都在 core，字节数据流与 XML 流式解析这两个偏门场景同样有新家。

三个误用边界。**边界一：报错占位不影响打包，但影响语义**——`/* #__PURE__ */` 注解让占位文件在 tree-shaking 后不进产物，所以「打包没报体积警告」不能当作「迁移完成」的判据，要靠第三节脚本扫 import。**边界二：同名下沉族只保证签名同构，不保证行为扩展**——core 版实现是 classic 版的下沉原样，但 core 是活跃开发区（如 StructuredOutputParser 的 getFormatInstructions 在 core structured.ts:87 的实现细节可能随版本演进），回归测试要跑在 core 版本上而不是凭「同名即无差异」跳过。**边界三：classic 根入口的 WARNING（src/index.ts:1-3）与 prompts 入口的 ERROR 是两件事**——前者只是提示用具体子入口，后者表示能力已整体搬走；审计脚本里两者要分开归档，前者可能只是老习惯，后者是必须改写的引用。

**边界四：codemod 的替换顺序有讲究。** 批量替换要按「先具体后通配」排序：`langchain/agents/...` 这类 NO_MATCH 规则必须排在 `langchain/...` 通配规则之前评估，否则会把 agent 解析器的 import 也替换到不存在的新家，制造编译错误。实操顺序建议三步：先跑审计脚本生成分类清单 → 人工确认 NO_MATCH 例外与报错占位 → 再执行机械替换并对替换过的文件跑 tsc。替换脚本本身十分钟就能写，但「替换后编译通过」才是搬家课真正的验收线——ESM 解析错误在运行时才爆，tsc 检查是唯一能在提交前兜住的关口。

### 本课小结

- 三类搬家族：报错占位（prompts/index.ts:1-7）、re-export 空壳（text_splitter.ts:1 / storage/in_memory.ts:1 / load/serializable.ts:1）、同名下沉（core output_parsers 通用族）。
- 报错文案是官方写好的迁移答案：0.2.0 移除、新家路径直达；`/* #__PURE__ */` 注解暗示这些占位本就不该被引用。
- agent 专用解析器不适用改 import 公式（无新家），清单脚本要把这类 NO_MATCH 显式标出。
- Prompt 族的新家 core prompts 什么都有，还新增了 DictPromptTemplate——core 不只是收容所，也是活跃开发区。
- 下一课转向检索层：BaseRetriever 抽象下沉 core 与 12 个花式 retriever 留守 classic 的分层格局。
